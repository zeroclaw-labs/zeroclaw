## Finding 2 — blocking, and the scope of the fix IS decided: read carefully

The reviewer's complaint: `CompatFamilySpec` proves chat-wire compatibility,
not that a family exposes `GET {base}/models` with `data[].id` and
`context_length` in the shape this reader expects. The blanket boolean
currently marks every compat family eligible; several would silently return
`None` because they don't actually match that shape (or, per the review,
NEAR AI uses a different catalog path and shape entirely).

The reviewer offered two paths: declare #9747 (a separate, unmerged
"centralize endpoint metadata" refactor) as parent and rebase onto its
endpoint contract, or carry an equivalent complete endpoint authority in this
PR.

**Take neither, and here is the actual decision: narrow the eligibility
instead of widening it blindly.** #9747 is still `REVIEW_REQUIRED` and
unmerged — it is a moving target, and rebasing #9854 onto an in-review PR
means this PR's mergeability depends on someone else's review cycle finishing
first, plus a second rebase if #9747 changes shape before it lands. That's a
worse position than #9854 is already in. Carrying an "equivalent complete
endpoint authority" here means duplicating #9747's work inside this PR, which
invites exactly the drift the reviewer is trying to prevent.

So: change the blanket `CompatFamilySpec` opt-in into an explicit,
per-family capability — a family is eligible for this generic
context-window-discovery path only if it is verified to expose
`GET {base}/models` returning `data[].id` and `context_length` in the
expected shape, AND its auth doesn't need the request/auth-policy rerouting
that Finding 1 requires (or Finding 1's fix already covers it end to end).
Concretely: instead of `SERVES_MODEL_CONTEXT_CATALOG` defaulting to
`CompatFamilySpec`'s blanket `true`, make each family opt in explicitly, and
audit the actual eligible set against a live-shaped fixture (not just a
boolean unit test — the review specifically calls out that "the existing
boolean tests do not exercise the behavior this PR claims to repair").

This will likely shrink the set of families this PR fixes. That's correct and
intended — smaller and true beats broad and silently wrong. If you find a
family where you genuinely cannot tell whether the catalog shape matches
without live network access, exclude it and say so in your report rather than
guessing yes.

If, once you're in the code, this approach turns out to be materially harder
or worse than I'm assuming from the outside — say because the capability
signal doesn't have anywhere sensible to live, or the existing trait

report the obstacle with what you see as the alternatives, rather than
