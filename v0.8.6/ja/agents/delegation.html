委譲とサブエージェント

SubAgentは、親エージェントによって生成される一時的な子runであり、デフォルトで親のアイデンティティを継承します。つまり、同じエージェントエイリアス、同じSecurityPolicy、同じメモリ許可リスト、同じ設定済みモデルプロバイダー、同じツールレジストリを引き継ぎます。トレーシングスパンagent.<alias>.subagent.<run_id>を通じて子として監査可能です。

SubAgentは独立した設定の概念ではありません。スキーマに[subagents.*]ブロックは存在しません。すべてのSubAgentのアイデンティティは、それを生成した親のエージェントループによって決まります。

spawn_subagent と delegate の使い分け

2つのツールが近くにあります。これらは互換性がありません。

  • spawn_subagent: 同一エージェントを独自のアイデンティティで再度実行し、特定のサブタスクに集中させます。子エージェントは親の完全な権限範囲から、絞り込まれた分を差し引いたものを参照します。アイデンティティを変更せずに、内部のサブタスクをメインの会話履歴から切り離してスコープを限定したい場合に使用します。
  • delegate: リクエストを（エイリアスで指定された）別の設定済みエージェントに引き渡します。ターゲットエージェントは自身のアイデンティティとモデルプロバイダーの下で実行されますが、委譲はゲートされます。呼び出し元のリスクプロファイルで delegation_policy mode = "allow" を設定する必要があります（デフォルトは "forbidden"）、ターゲットは同一プロファイルのピアとして、または明示的な delegates エントリとして到達可能でなければなりません。明示的なエントリでは mode = "bounded" または mode = "independent" を選択し、これにより呼び出し元のツール上限が引き続き適用されるかどうかが決まります。別の設定済みスペシャリストが作業を担当すべき場合に使用します。以下の Delegation gating を参照してください。

このページでは spawn_subagent を最初から最後まで説明します。delegate は crates/zeroclaw-runtime/src/tools/delegate.rs にあり、別のサーフェスです。

SubAgentがインスタンス化される仕組み

2つのスポーン箇所がSubAgentSpawn（crates/zeroclaw-runtime/src/subagent/mod.rs:97）に集約されます：

  1. エージェントループから: モデルは prompt 文字列を指定して spawn_subagent ツールを呼び出します。このツールは、レジストリ内の他のツールと同様に登録されています（crates/zeroclaw-runtime/src/tools/mod.rs、SpawnSubagentTool::new）。
  2. cron から: JobType::Agent ジョブは run_agent_job（crates/zeroclaw-runtime/src/cron/scheduler.rs）を通じて実行され、同じ SubAgentContext を構築しますが、子をトップレベル実行（SubAgent ではない）としてフラグ付けするため、それ自体が 1 階層分のサブエージェントを生成できます。

両方のパスで以下が呼び出されます:

#![allow(unused)]
fn main() {
SubAgentSpawn::for_agent(config, parent_alias)?     // 親アイデンティティを解決する
    .build(SubAgentOverrides::default())?           // 任意の絞り込みを検証する
}

for_agent は親の risk_profile と [agents.<alias>.workspace.read_memory_from] を読み取って継承された許可リストを構築します。親自身のエイリアスは常に追加されるため、SubAgent は常に親自身のメモリ行を参照できます。build はオプションの絞り込みを適用し（下記の権限の継承を参照）、検証済みの SubAgentContext を返します。

ライフサイクル

同期、インプロセス、単一の tokio ランタイム。プロセス境界を越えるものはありません。

  1. 親のツールループが spawn_subagent をディスパッチします。ツールは prompt 引数を読み取り、空の場合は拒否します。
  2. ツールは2つのガードを順番にチェックします:
    • 深さ1の上限。 呼び出し元の実行自体がSubAgentであった場合（AgentRunOverrides.is_subagent == true）、"spawn_subagent: a subagent may not spawn its own subagents (depth-1 cap)"を返して拒否します。SubAgentは再帰できません。
    • リスクプロファイルのツールゲート。 親の [risk_profiles.<alias>].deny_all_tools が true の場合、または allowed_tools が空でなく spawn_subagent を含まない場合、または excluded_tools が spawn_subagent を含む場合は、親のエイリアス名を含むメッセージを返して拒否すること。allowed_tools が省略されているか空の場合はツールは利用可能のまま（従来の無制限状態）となる。
  3. ツールは SubAgentSpawn::for_agent と build を呼び出します。失敗（不明な親エイリアス、エスカレートするオーバーライド）は ToolResult { success: false, error: "subagent spawn failed: ..." } として返されます。
  4. このツールは AgentRunOverrides { security, memory: None, is_subagent: true, suppress_memory_inject: true } を構築し（子の SubTurn オリジンはすでにエンジンのメモリ注入をスキップしますが、このフラグはオプトアウトを明示的にします）、subagent-<uuid> をキーとするトレーシングスコープ内で crate::agent::run（crates/zeroclaw-runtime/src/agent/loop_.rs、pub async fn run）を await します。親の tool 実行は、子が返るまでブロックされます。
  5. 子エージェントのループは完了まで実行されます。そのツールレジストリは新規に構築され、is_subagent_caller: true が自身の SpawnSubagentTool に流れ込むため、再帰しようとする試みはすべて同じ深さ1のゲートで拒否されます。
  6. 子プロセスは Result<String> を返します。親の spawn_subagent ツールがそれをラップします:
    • 成功: ToolResult { success: true, output: <child's final response>, error: None }。空の出力はリテラル "subagent completed without output" に置き換えられます。
    • 失敗: ToolResult { success: false, error: Some("subagent run failed: ...") }。
  7. 親の tool ループは、その ToolResult を会話コンテキストに含めて継続します。子の中間ターンやツール呼び出しは親の履歴に再生されず、最終的なレスポンスのみが表面化します。

アップストリームに還元されるもの

1 つ: 子の final assistant message を文字列として ToolResult.output でラップしたもの。

  • 子のツールコール、中間的な推論ターン、および子が実行したメモリ書き込みは、子のトレーシングスパン配下の構造化ログで観察できますが、親の会話履歴には入りません。
  • 子セッションはパス subagent-<uuid>（cron で生成された実行の場合は cron-<uuid>）の下に存在します。これは会話履歴のキーであり、ファイルシステム上の場所ではありません。これにより子の履歴が親の履歴から分離されます。
  • 子プロセスによって実行されたメモリ書き込みは、親のアイデンティティに書き込まれます（SQL/Postgresバックエンドでは同じエージェントUUID、Markdownでは同じワークスペースディレクトリ）。Cronで起動された実行では memory.auto_save が無効になるため、オプトインの書き込みは引き続き機能しますが、ルーチンの想起は蓄積されません。

同期的な委任には、親へのストリーミングや途中経過を返す経路がありません。長時間実行される SubAgent は、その全時間にわたって親のツール実行を停止させ、呼び出しごとのタイムアウト設定もありません。バックグラウンドの委任では、代わりに check_result と await_sessions を通じて上限付きのライブ進捗が報告されます(下記のバックグラウンド結果の形式にある progress フィールドを参照してください)。

実行ツリーの反復回数の上限

max_execution_tree_iterations を対象の [runtime_profiles.<alias>] エントリに設定すると、1 つのフォアグラウンド実行ツリー全体でのツールループの反復回数の合計を制限できます。

[runtime_profiles.default]
max_execution_tree_iterations = 12

フィールドは省略可能です。省略すると集計予算は無効になります。明示的な 0 は無効な値です。この予算は max_tool_iterations とは別のものであり、max_tool_iterations は引き続き各エージェントターンごとのローカルなループ上限として機能します。

1つの論理的なルートターンは、1つのアトミックなバジェットハンドルを所有します。フォアグラウンドの spawn_subagent、同期または並列で実行される上限付きの delegate ターゲット、および明示的なライブ SOP の子作業は、このハンドルから消費します。子は、残りスロットが2つ以上ある間だけ予約できます。ルートに最後のスロットしか残っていない場合は、そのスロットを既存のツールなし完了パスのために消費します。ビューを使い果たした子は失敗した ToolResult を返し、親のルートターンは処理を継続できます。同時実行される予約によってカウンターがラップアラウンドすることはありません。

独立したフォアグラウンドの delegate ターゲットは、呼び出し元の残りの割り当てではなく、自身のランタイムプロファイルのバジェットを使用します。ターゲットの上限を省略した場合、呼び出し元に実行ツリーのバジェットがあっても、その独立したターンはそのバジェットによる上限を受けません。デタッチされたバックグラウンドの delegate タスクおよびピアターンも、起動元のターンのバジェットを共有せず、受け手のランタイムプロファイルから新しいルートを生成します。

1回のターンでの複数回の呼び出し

エージェントループは、ターン単位の重複呼び出しガードを適用します。同一ターン内で同一の引数によって2回呼び出されたツールは、通常2回目の呼び出しがスキップされます。spawn_subagent と delegate は、このガードの対象外です。同じプロンプトで複数を起動すること（冗長性、サンプリング、ファンアウト）は、偶発的な繰り返しではなく意図的なパターンであるため、同一の呼び出しがそれぞれ実行され、それぞれの結果が返されます。この対象外措置がなければ、最初の同一呼び出しのみが実行され、その出力のみがモデルに到達することになります。

並列ツール実行が有効な場合（ランタイムプロファイルで parallel_tools = true）、1ターンに含まれる複数の spawn_subagent 呼び出しが同時に実行され、各子の最終応答がそれぞれ自身のツール呼び出しに紐付けられて親に返されます。delegate は parallel: [...] 引数による独自の明示的なファンアウトを備えており（output-strings セクションを参照）、このパスでは各ターゲットがそれぞれ専用のタスクとしてスポーンされ、すべての結果が集約されます。

ZeroCode トランスクリプト検査

フォアグラウンドのspawn_subagentとdelegateの呼び出しには、タスク、指定された場合は委任先の名前、保持された結果テキストを表示する展開可能なトランスクリプトカードがあります。並列委任は、既存のターゲットごとの結果ブロックを含む1回の呼び出しのままです。contextなどの追加引数は入力フィールドに引き続き表示されます。不正な形式またはサイズ超過の引数は、汎用ツールカードにフォールバックします。展開時もフィールドごとに8 KiBまたは100行というツール表示の上限が維持されます。Copyは元の保持済みエントリを使用し、その結果は既に16 KiBに制限されている可能性があります。

委任先の名前はカードの見出しに表示され、その後にタスクと Response セクションが続きます。一致する同期的な委任エンベロープの場合、返された回答が最初に表示され、プロバイダー/モデルのメタデータは展開された Details に残ります。その他の結果形式はそのまま維持されます。レスポンスがない場合は Result not recorded と表示されます。カードは、復元された履歴や返された診断テキストを含め、子が現在実行中であることや子が成功したことを主張しません。バックグラウンド起動や check_result や await_sessions などの管理アクションは汎用カードのままであり、起動の確認応答が子の完了として表示されることはありません。

ライブの子プロセス検査には、親のツール呼び出しIDに関連付けられたランタイムメタデータが依然として必要です。具体的には、子のタスク/セッションID、権威ある開始/終了状態と結果、タイムスタンプ、子のツールイベント、または認可された会話ログへのリンクです。現在の親ツール通知にはこれらのフィールドは含まれていません。ZeroCodeは、結果テキスト、トレースログ、プロンプトのマッチング、ターゲットのエイリアスからこれらを推測することはありません。ランタイムのコントロールプレーンがライフサイクルの管理者であり続けます。これは#8763の部分的な実装であり、ライブの子プロセス監視ではありません。

権限の継承

SubAgent は、spawn サイトが絞り込み用の SubAgentOverrides を指定しない限り、親の権限をそのまま継承します。現在、ツリー内の両方の spawn サイトは SubAgentOverrides::default()（すべてを継承）を渡しています。オーバーライドの仕組みは出荷済みで検証も完了しており、将来的に呼び出し元が指定する絞り込みパスは、ランタイムの変更なしで組み込めます。

軸ごとの継承:

  1. SecurityPolicy: Arc<SecurityPolicy> のクローンによって継承されます。オーバーライドパス（SubAgentOverrides::policy = Some(policy)）は SecurityPolicy::ensure_no_escalation_beyond（crates/zeroclaw-config/src/policy.rs）を実行し、親が持たない権限を追加するフィールドをすべて拒否します。検証される項目には、自律レベル、allowed_roots（rw + ro + write-only）、allowed_commands、workspace_only、親 ⊆ 子 方向での forbidden_paths、shell_env_passthrough、max_actions_per_hour、max_cost_per_day_cents、shell_timeout_secs、block_high_risk_commands、require_approval_for_medium_risk が含まれます。拒否時には正確な EscalationViolation が連鎖されるため、診断情報で問題のあるフィールドが特定されます。
  2. アクション／コストの予算: PerSenderTracker は親子間で Arc クローンによって共有されます。継承（そのまま）パス: 子は同じ Arc<SecurityPolicy> を保持するため、record_action() / record_cost() への書き込みは同じバケットに反映されます。オーバーライドパス: SubAgentSpawn::build は親の tracker フィールドを明示的に絞り込んだ子ポリシーにコピーします。SubAgent はスポーンによって max_actions_per_hour や max_cost_per_day_cents を回避することはできません。制限は共有されます。
  3. ツールレジストリ: 子のレジストリは、継承されたポリシーの下で tools::all_tools_with_runtime によって新規に構築されます。レジストリはその後 apply_policy_tool_filter（crates/zeroclaw-runtime/src/agent/loop_.rs）を通過し、いずれかのゲートで名前が拒否されたツールはすべて除外されます:
    • ポリシーの allowed_tools / excluded_tools（親の risk_profile から取得）。
    • agent::run に呼び出し側から渡される allowed_tools 引数。spawn_subagent はレジストリに存在しますが、子に対しては is_subagent_caller フラグが true に設定されているため、いかなる spawn 処理が行われる前に深度1の拒否が発動します。同じ is_subagent_caller フラグにより、子のレジストリからは model_switch が完全に除外されます。つまり、SubAgent は親のモデルをそのまま継承し（軸5を参照）、親の知らないうちにアクティブなモデルを切り替えられてはならないため、このツールはそもそも子には提供されません。
  4. メモリ許可リスト: 親の兄弟エージェントへの付与分（workspace.read_memory_from による）と、親自身のエイリアスを含みます。カテゴリ制限は厳密に維持され、SubAgent によって広げられることはありません。親自身のエイリアスは常に再追加されるため、SubAgent は常に親の行を参照できます。現在の SubAgentOverrides::allowed_agent_aliases オーバーライドは名前の部分集合として検証されるため、参照可能な付与済みの兄弟エージェントを絞り込むことしかできません。
  5. モデルプロバイダー: 親の [agents.<alias>] model_provider 解決から継承されます。Temperature は親のプロバイダーエントリ（config.model_provider_for_agent(parent_alias).and_then(|e| e.temperature)）から取得されます。この継承は単なるデフォルトではなく強制されます。model_switch は SubAgent のツールレジストリから除外されているため（axis 3 を参照）、SubAgent は自身のモデルを切り替えることができません。サブタスクを別のモデルで実行するには、そのモデルを model_provider に指定した兄弟エージェントへ delegate を使用してください。
  6. データレイヤーでの同一性: agents テーブル内の同じ UUID（SQL バックエンドの場合）、Markdown 用の同じワークスペースディレクトリ、同じシークレットストア。親と子の区別は純粋に可観測性のためのものです。つまり、別個のトレーシングスパンと、別個の会話履歴セッションキーです。

ユーザーが発火させる方法

これらのツールを自分で呼び出すことはありません。ボットがそのターン内で呼び出します。ユーザーとしては、リクエストの言い回しによってボットの選択に影響を与えます。特別なコマンドも、スラッシュ構文も、ユーザーが入力する JSON もありません。モデルが spawn_subagent を選ぶか delegate を選ぶかは、システムプロンプト、ツールの description テキスト（モデルから見えるもの）、そしてユーザーの言い回しによって決まります。言い回しは影響を与えるものであり、強制するものではありません。

決定論的に制御できるのは利用可能性です。親エージェントのレジストリに存在しないツールは選択されません。リスクプロファイルによる制限は[risk_profiles.<alias>].allowed_tools、[risk_profiles.<alias>].deny_all_tools、[risk_profiles.<alias>].excluded_toolsで行います。空でないallowed_toolsリストでは、モデルにそのツールを見せるためにspawn_subagentまたはdelegateを含める必要があります。allowed_toolsが省略されているか空の場合、excluded_toolsでツールが指定されていない限り、ツールの利用可能性は制限されません。deny_all_tools = trueは明示的な全拒否のゲートであり、両方のツールを非表示にします（空のallowed_toolsリストは_全拒否_ではありません）。設定を編集した後は、デーモンを再起動してください。

検証可能なエンドツーエンドの範囲:

  1. プロトコル所有のツール出力および拒否文字列は、リテラルな Rust コントラクトです。ユーザーに表示されるターミナル補完の失敗通知は Fluent カタログのコントラクトです。英語のソースは以下に記載されており、同じキーを定義する英語以外のカタログまたはディスク上のオーバーライドによって、表示が異なる場合があります。
  2. 動作を変更する実際の設定項目（allowed_tools、max_delegation_depth など）。
  3. 子の実行中に出力されるすべてをスコープする、構造化されたトレーシングスパンの形状です。

これらのドキュメントから検証できないこと:

  1. 特定のボットが、特定のモデルで、特定のシステムプロンプトのもとで、「サブエージェントをスポーンして……」と求められたときに、そのツールを選択するかどうか。言い回しが結果を左右し、その出力はさまざまです。ボットがツールを選択しない場合、最も信頼できる手段は、ボットのシステムプロンプトを明示的な指示で拡張することです（「集中的なサブタスクを求められたときは、spawn_subagent ツールを使用してください」）。
  2. ボットが最終的な返信であなたに書き込む正確なテキスト。ボットはツールの出力を読み取り、それを基に独自の返信を生成します。ツールの出力テキストは、引用、言い換え、または要約される場合があります。

spawn_subagent: モデルが認識する拒否文字列

これらは crates/zeroclaw-runtime/src/tools/spawn_subagent.rs から取得した正確なものです。モデルはこれらをツールのエラー文字列として受け取り、それに反応します。ユーザーに表示されるボットの返信は、モデルが次に書く内容であり、多くの場合その拒否を参照またはそのまま反映します。

  1. 空または欠落した prompt 引数: Missing or empty 'prompt' parameter
  2. 呼び出し元自体が SubAgent の場合 (深さ 1 の上限): spawn_subagent: a subagent may not spawn its own subagents (depth-1 cap)
  3. 親の risk-profile ツールゲートはspawn_subagentを除外しています: spawn_subagent: refused: agent '<parent_alias>' risk_profile does not list spawn_subagent in allowed_tools
  4. 不明な親エイリアス / spawn ビルドエラー: subagent spawn failed: <wrapped error>
  5. 子の実行がエラーを返しました: subagent run failed: <wrapped error>

成功した場合、ツールの出力は子の最終的なレスポンステキストそのものになります。子が空の文字列を返した場合、出力はリテラルのプレースホルダー subagent completed without output になります。成功時に grep で検索できる固定のプレフィックスはありません。

spawn_subagent: 実際に起動したかを確認する方法

ログをtailしてください。ツールが生成した子プロセスは、zeroclaw_scope という名前のtracingスパン（targetは zeroclaw_log_internal_scope）を発行する scope! 内で実行され、agent_alias=<parent> と session_key=<uuid> を保持します。子プロセスの実行中に発行されるすべてのログ行は、これらのフィールドを保持します。親自身のターンには独自の session_key があります。同じ agent_alias に対してターンの途中で新しい session_key 値が現れることが、SubAgentが実行されたことを示すシグナルです。子プロセスの会話履歴セッションパスは subagent-<uuid> です（tracingフィールドとは異なる、ファイルシステム的な識別子）。

Cron で起動されたエージェントジョブは、別のより明示的なスパン名 subagent（リテラル）を使用し、フィールド category="cron"、agent_alias=<owning agent>、cron_job_id=<id>、run_id=<uuid>、spawn_site="cron" を持ちます。Cron のパスは簡単に grep できます: grep 'spawn_site="cron"' zeroclaw.log。Cron で起動された実行はトップレベル（is_subagent=false）であることに注意してください。これらは自身で spawn_subagent を一度だけ呼び出す場合があります。

これは、エージェントループの spawn パスに対する弱いシグナルです。attribution_span!(tool) を経由してルーティングされる専用の「サブエージェント開始/完了」レコードは、コード側のフォローアップとして追跡されます。エージェントループがツール実行を attribution span でラップすると、そのツール内のすべての record! は自動的に tool=spawn_subagent を持つようになり、この問題は単純な grep で解決できるようになります。

委任ゲーティング

delegate は、ターゲットエージェントが実行される前に、crates/zeroclaw-runtime/src/tools/delegate.rs で次の順序で2つのゲートを適用します:

  1. delegation_policy.mode: 呼び出し元のリスクプロファイルが委任を許可している必要があります。[risk_profiles.<alias>].delegation_policy はデフォルトで { mode = "forbidden" } です。委任を許可するには mode = "allow" を設定してください。禁止されている場合の拒否は次のとおりです:

    呼び出し元「<caller>」は、リスクプロファイル「<caller_profile>」のdelegation_policyによって委任が禁止されています。[risk_profiles.<caller_profile>].delegation_policyのmode = "allow"を設定してください

    これはゲートウェイダッシュボードおよびzerocodeの Config → Risk profiles → <profile> → delegation_policy.mode（forbidden/allowの選択）で編集できます。

  2. 到達可能性: ターゲットエージェントは、Config::reachable_delegate_target_configs によって解決される呼び出し元の到達可能セットに含まれている必要があります。到達可能セットは、[agents.<caller>] 上のエージェントごとの2つのソースの和集合から、呼び出し元自身を除いたものです：

    • 同一プロファイルのピア: 呼び出し元のリスクプロファイルを共有する他のすべてのエージェント。delegate_same_risk_profile = true（デフォルト）の場合に含まれます。false に設定すると、呼び出し元はピアの自動許可から除外されます。

    • 明示的ロスター: delegates、呼び出し元がリスクプロファイルをまたいで委譲できるターゲットの、空でもよいリスト。文字列エントリは手動編集に便利で、境界付きターゲットを表します。オブジェクトエントリはモードを明示します：

      delegates = [
  "reviewer",
  { agent = "sysadmin", mode = "independent" },
]

      設定が保存されると、各エントリは mode = "bounded" または mode = "independent" を含むオブジェクト形式で書き込まれます。この設定形式は、デーモンおよび UI バイナリが委任モードをサポートするビルドにアップグレードされるまで展開しないでください。古いバイナリは delegates が文字列のみを含むことを想定しており、オブジェクトエントリがあるとそのバイナリにとって agents セクションが無効になります。その場合、耐障害性ローダーがセクションを破棄するため、修復用インターフェースは引き続き起動できます。 ターゲットがそのセット外にある場合、拒否は原因を示します。例:

    delegate ターゲット "<target>" は "<caller>" から到達できません: リスクプロファイルが異なります (caller は "<caller_profile>" を使用、target は "<target_profile>" を使用)。delegate_same_risk_profile は同じリスクプロファイルを持つエージェントにのみ到達します。意図したモードで明示的な [agents.<caller>].delegates エントリを追加するか、いずれかのエージェントの risk_profile を変更してください。

    委譲先ターゲット "<target>" は "<caller>" から到達できません: delegate_same_risk_profile が無効であり、ターゲットが [agents.<caller>].delegates に記載されていません

    デリゲート先の "<target>" は "<caller>" からアクセスできません: ターゲットエージェントが無効になっています

    境界付きのターゲットは、呼び出し元のアクション/コストトラッカーを継承し、有効な上限は各ホップで呼び出し元の値に制限されます。そのため、ターゲット自身のプロファイルで許可されている内容にかかわらず、呼び出し元のアクション予算がサブツリー全体を制約します。生成されたバックグラウンドワーカーと並列ワーカーは、最初の受付の前に送信元のレート制限バケットを復元するため、生成境界をまたいでも予算は送信元ごとに保たれ、スコープなしのバケットにフォールバックしません。コスト上限も各ホップで同じ方法で結合され、委任されたサブループ内で、ターゲットエージェント自身の日次支出に対して適用されます(下記のコスト追跡の段落を参照)。境界付きのターゲットが呼び出し元と同じリスクプロファイルを共有する場合、呼び出し元のセッションのワークスペース境界も継承します。クロスプロファイルの境界付きターゲットは、呼び出し元の委任先一覧とdelegation_policyを通じて到達可能であれば許可され、ターゲットの解決済みポリシーの下で実行されます。ただし、エージェント的なツールの利用可否は呼び出し元のツールレジストリによって制限されます。

    独立ターゲットは、mode = "independent" で明示的にリストされている場合にのみ利用できます。依然として delegation_policy.mode = "allow" と delegates を通じた到達可能性が必要ですが、一度選択されると、呼び出し元の非エスカレーション上限、セッションワークスペースのオーバーライド、またはアクション/コストトラッカーなしで、ターゲットエージェント自身のポリシーを解決します。

    削除されたサブループはすべて、有界・独立のいずれであってもコスト追跡の対象になります。委譲されたサブループは、ターゲットのエージェントエイリアスに帰属するコスト追跡スコープの下で実行され、そのトークン使用量は共有の日次コスト台帳にそのエイリアスの下で記録されます。ターゲットのホップごとの実効上限は [runtime_profiles.<target>].max_cost_per_day_cents から求められ（値が 0 の場合はグローバル上限を継承）、台帳上のターゲットエージェント自身の日次支出と比較されます。一方、プロセスグローバルの [cost] daily_limit_usd と月次上限は共有合計に対して引き続き適用されます。両者のうち低い方が優先されます。

    スコープの種類（[cost] track_per_agent によるエージェント単位または共有上限付き）、委譲実行がスコープされるかどうか（[cost] enabled）、およびその台帳行のエージェント単位の帰属は、委譲ツリーのルート委譲時に一度だけ決定され、以降のすべてのネストされたホップに継承されます。ネストされた委譲は委譲元の親からトラッカーを派生させるため、ツリーが開始されたモードがツリー全体を拘束します。実行中にこれらのフラグをリロードしても、スコープされた実行の追跡を解除したり、帰属されていない実行の帰属を途中から開始したりすることはできません。

    上限と価格マップは、すべてのホップで常に最新の状態が維持されます。派生トラッカーはベースのconfigハンドルを共有し、価格マップは解決済みのconfigから再構築されるため、オペレーターがグローバルの [cost] 上限をリロードすると、実行中の委譲は次回の予算チェック時にそれが反映されます。ターゲット自身の支出がその上限を超えている場合、委譲はターゲットのプロバイダーが呼び出される前に失敗し、その拒否はエージェント名を含むdelegateツールのエラーとして呼び出し元に返されます。

    祖先の上限は、その祖先が委譲したすべてのものにも及びます。有界なホップの予算スコープはすべて祖先チェーンを保持するため、有界な子孫の支出は、その子孫の台帳行が子孫自身のエイリアスに帰属したままであっても、それぞれの祖先のホップごとの上限に計上されます。独立したターゲットは、代わりに自身のホップごとの上限と共有のグローバル上限の下で実行されます。ツリーの実行モードは継承しますが、呼び出し元の上限やチェーンは継承しないため、呼び出し元の上限超過や子孫の累積値が独立ホップを制限することはありません。

    子孫の会計は、プロセスの稼働期間およびUTCの日単位で管理されます。台帳の日次合計とともにUTC深夜にロールオーバーし、デーモンを再起動すると子孫の支出は忘れられますが、各エージェント自身の台帳合計は保持されます。[cost] track_per_agent = false の場合、エージェント単位の日次合計は存在しないため、ホップごとの上限は共有の日次合計に対するチェックに縮退します。

    非エージェント型の委譲ターゲット（単一のモデル呼び出しでツールループを持たないもの）も同じスコープの下で実行されますが、そのディスパッチ経路はトークン使用量を報告しないため、現状では、これらの単一呼び出しは価格計算も予算チェックも行われません。

広告されるロースターは、ツールスキーマ内の agent パラメータの説明に含まれます。これは到達可能な集合を正確に列挙し、delegation_policy.mode = "allow" の場合にのみ表示されます。無効化されたエージェント（enabled = false）は、同一プロファイルのピアであっても、明示的な delegates エントリであっても、到達可能になることはありません。

境界付きエージェント委譲では、サブエージェントのツールは、呼び出し元の既にポリシーでフィルタリングされたレジストリから取得され、それがターゲット自身の allowed_tools と交差されます。ターゲットの allowed_tools が省略されているか空の場合は「継承」を意味します。サブエージェントは拒否されるのではなく、呼び出し元の委譲可能なレジストリ全体を使って実行されます（空のリストは旧来の無制限状態であり、全拒否ではありません）。deny_all_tools = true は明示的な全拒否ゲートであり、空の子レジストリになります。空でないリストは、そのレジストリと交差されます。いずれの場合も、呼び出し元のレジストリが上限となります。ターゲットのリスク・プロファイルが、呼び出し元に付与されていないツールを指定している境界付きのクロスプロファイル・ターゲットは、そのツールを受け取りません。

したがって、境界付き委譲はツールによる境界付けであり、完全な SecurityPolicy::ensure_no_escalation_beyond チェックではありません。その交差が空の場合でも、ターゲットは通常のエージェント型モデルのターンを、ツールなしで受け取ります。

delegate ツール自体も同じ範囲制限の形を踏襲します。ターゲットのリスクプロファイルで delegation_policy mode = "allow" が設定されていない限り、子レジストリから除外されます(デフォルトの "forbidden" では、現在のサブ委任なしの動作が維持されます)。また、呼び出し側のゲートも引き続き適用されます。呼び出し元の allowed_tools/excluded_tools で delegate が許可されている必要があり、ターゲットのツールポリシーで delegate が除外されていてはなりません。許可された場合、子の delegate インスタンスはターゲットのアイデンティティにバインドされます。その呼び出しは、delegation_policy、到達可能性、および公開されるロスターを、委任元の親ではなく、ターゲット自身のエイリアスおよび delegates 設定から解決します。さらに、許可された委任のホップごとに深度カウンターが増加します(下記参照)。

付与されたインスタンスには、承認とスコープに関する2つのルールが適用されます。1つ目として、このインスタンスはdelegate-onlyです。子インスタンスのIDは一時的なものであるため、タスク管理アクション（check_result、list_results、cancel_task、await_sessions）は拒否されます。タスク行には呼び出し元エイリアスの委任チェーンが記録されるため、子のすべての祖先はオーナーチェックを通過します。ただし、自身の delegate ツールがタスク管理を備えている祖先（通常はルートの委任エージェントです。境界付きの中間子もdelegate-onlyであるためです）のみがその許可に基づいて動作できます。そのため、子はタスクIDを、いずれかの該当祖先に到達するまで上位へ渡します。この境界を正確に理解してください。これは delegate API の範囲のみを限定します。基盤となる delegate_results/*.json アーティファクトは、タスクIDと出力のみを保持する通常のワークスペースファイルのままであり、オーナーチェックで制御される対象はタスク行に存在します。2つ目として、サブエージェントのループにはオペレーターの承認経路がありません。対象のリスクプロファイルが delegate について確認を求める場合（監視下のデフォルト、または always_ask に記載されたツールの場合）、子の承認ゲートは delegate 実装が実行される前に呼び出しを拒否し、オペレーターの判断が利用できなかったことを報告します。delegate 実装は、到達した呼び出しに対して独自のターゲットポリシーチェックを保持します。したがって、入れ子の委任には、ターゲットプロファイルが delegate を明示的に自動承認するか、完全自律モードで動作することが必要です。確認を求める呼び出し元プロファイルは、そのループ内で変わらず確認を求め続けます。

同じオペレーター不在の境界は、有界なエージェント型の子プロセスにおけるツール呼び出しにも適用されます。子ループは、ディスパッチの接合点で、ターゲットのリスクプロファイルに基づいて新しい非対話型の承認マネージャーを作成します。承認プロンプトが必要な呼び出しは、ツール実装が実行される前に拒否されます。一方、auto_approve に明示的に記載された呼び出し（または完全自律モードで許可された呼び出し）は続行できます。呼び出し元が所有し、継承されたコマンドツール（shell、schedule、cron_add、cron_update、cron_run）については、このターゲットプロファイルによる判断はツールの呼び出しのみを承認します。呼び出し元のコマンドポリシーが消費するコマンド固有の承認を提供したり、上書きしたりするものではありません。呼び出し元のコマンドポリシーが引き続き優先されるため、これらのツールは同ポリシーの承認要件を引き続き適用します。継承された呼び出し元による上限付きのレジストリは変更されません。承認は、機能フィルタリングを通過した呼び出しを評価するものであり、追加のツールを付与したり、呼び出し元の承認セッションを転送したりするものではありません。

独立したエージェント的委任では、サブエージェントのツールは、対象エージェント自身の設定済みポリシーとランタイムレジストリから構築されます。これは、その対象との新しいチャットを開くのに似ています。親のレジストリは上限として使用されません。delegate ツールはその子レジストリから削除されます。独立した委任は、別の delegate 呼び出しを経由して再帰することはありません。

委譲の深さは、委譲元の親エージェントの runtime_profile.max_delegation_depth によって上限が定められます。許可された各委譲ホップは、その上限を次の委譲先エージェント自身のプロファイル上限と比較して小さい方（min）に絞り込んだ値を持ちます。これにより、親の上限はそのサブツリー全体に適用され、連鎖では上限が厳しくなることはあっても緩むことはありません。上位エージェントに委譲を1ホップだけ許可し、それ以上のサブ委譲を行わせない場合は、1 に設定します。

エージェント型ターゲットツールポリシー

ターゲットエージェントの [runtime_profiles.<target>].agentic = true の場合、delegate は親の利用可能なツール（mode = "bounded"）またはターゲット自身のランタイムレジストリ（mode = "independent"）のいずれかからターゲットサブループのツールレジストリを構築します。ターゲットのリスクプロファイルがそのレジストリをフィルタリングします:

  1. [risk_profiles.<target_profile>].allowed_tools フィールドが省略されているか空の場合、選択されたレジストリは制限されないままになります。deny_all_tools = true は明示的な全拒否ゲートであり、空の子レジストリを生成します。
  2. allowed_tools リストに値が指定されている場合、完全に一致するツール名のみが保持されます。
  3. [risk_profiles.<target_profile>].excluded_tools は常に結果から差し引かれます。
  4. delegate は、境界付きサブ委任が許可されていない限り、子レジストリから削除されます。delegation_policy mode = "allow" を設定したリスク・プロファイルを持つ境界付きターゲット（かつ呼び出し側のゲートがそのツールを許可しているもの）は、ターゲットに紐付けられた delegate 専用インスタンスを受け取ります。このインスタンスは、ターゲットのプロファイルが委任について確認を求める場合には、さらに委任を拒否します。独立した子レジストリは、常に delegate を削除します。

このポリシーは呼び出し元ではなくターゲット側に存在します。同一プロファイルのピアは共有リスクプロファイルを使用します。明示的なクロスプロファイルの委任は、到達可能性と委任ポリシーのゲートを通過した後、ターゲットのリスクプロファイルを使用します。境界付きエージェント委任は、呼び出し元で上限が設定されたツールレジストリとターゲットのツールポリシーの積集合のみを受け取ります。独立したエージェント委任は、ターゲットが所有するツールレジストリを受け取ります。ターゲットのリスクプロファイルが欠落している場合は、サブループが開始する前に拒否されます。実行可能な子ツールがゼロになるように設定されたプロファイルであっても、ツールなしの通常のモデルターンは許可されます。

対象に設定された Reliable プロバイダーチェーンで、ネイティブツール対応の候補とテキストのみの候補が混在している場合、strict_tool_parsing = false では、到達可能なすべてのフォールバックでツールを実行できるよう、エージェントターン全体で 1 つのテキスト/XML ツールプロトコルを使用します。有効なツールが残っていて strict_tool_parsing = true の場合、厳格なパースではそのテキスト/XML フォールバックプロトコルが禁止されるため、ZeroClaw はプロバイダーへのリクエストを行う前に混在チェーンを拒否します。均一なチェーンは変更されません。すべてネイティブのチェーンではネイティブツールトランスポートを使用し、意図的にすべてテキストにしたチェーンでは設定されたテキストツールポリシーに従います。
