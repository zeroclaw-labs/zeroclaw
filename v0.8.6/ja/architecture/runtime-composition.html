ランタイム構成契約（提案）

ステータス: 提案段階、未実装。本ページは、いかなる呼び出し元も移行する前に、#10993 が求めているコンポジション API の提案です。同 Issue の最初の受け入れ項目と、#7432 R1 の設計部分を実現するものです。これに付随する唯一のコードは crates/zeroclaw-runtime/src/composition.rs の型スケルトンであり、現時点ではどこからも利用されていません。

目標は、RFC #5574 が Phase 2 D1 に対して定めたもので、エンベッダーが自ら提供する機能を用いて実行できるエージェントランタイムを作ることです。そのランタイムは「Telegram、Discord、Anthropic、あるいは特定のツール実装についての知識を一切持たない」ものであり、バイナリは薄い配線レイヤーになります。

現在のランタイムの状況

c44909b1ed の master で、cargo metadata と、#[cfg(test)] モジュールおよびテストファイルを除外した本番コード用の grep を使って計測しました。

構築はランタイムの外側でも、ランタイムと並行して行われます。これは依存関係の問題だけでなく、2つ目の信頼できる情報源（真実の源）でもあります。

  • Gateway（zeroclaw-gateway/src/lib.rs）は、独自に耐障害性のあるプロバイダー、メモリバックエンド、オブザーバー、そして2つのツールレジストリを構築し、その後 agent::process_message を呼び出します。
  • Channels orchestratorは送信者ごとのプロバイダーキャッシュ（get_or_create_provider）を保持しており、それはcreate_resilient_model_provider_from_refで構築され、all_tools_with_runtimeを直接呼び出します。

  • src/main.rs は複数のコマンド向けにプロバイダーを構築し、SOP エンジン向けにメモリを構築したうえで、agent::run と daemon::run を呼び出します。

DaemonRegistry が既に行っていること

daemon::DaemonRegistry（#7430 で導入）はサブシステムのスターターを登録します。対象は gateway、channels orchestrator、local socket、WSS、relay、enrollment、MQTT です。また、共有の SOP エンジンと監査ロガーも保持します。providers、memory、tools、observers は登録しません。これはプロセスの構成を扱うものであり、機能の構成を扱うものではありません。

Proposal

二つのレジストリ — ライフタイムが二種類あるため

RFC #5574 では、register_channel、register_tool、set_provider、set_memory、set_observer を持つ単一の Registry を提案していました。現在のコードには寿命の異なる2つのものがあり、それを1つの型にまとめると、その違いが見えなくなってしまいます。

ランタイムは両方を保持します。サブシステムのスターターは、独自に構築する代わりに世代の capabilities を受け取ります。これにより channels オーケストレーターにおける並行構築が取り除かれます。ゲートウェイは例外で、そのスターターは v0.9.0 のゲートウェイ分割で削除されるため、このコントラクトへの移行は行われません(ステップ 4)。

  • A session can モデルを切り替える mid-conversation (try_apply_model_switch)…

    Let me translate carefully: “A session can switch model mid-conversation (try_apply_model_switch), and a delegate resolves a different agent’s provider and memory.”

ランタイムは、sources に対して、エージェントと世代を指定して必要なものを要求します。ソースは、どのようにビルドしてキャッシュするかを決定します。ランタイムは、いつ要求するか、どのエージェントに対して、解決済みのどのポリシーのもとで要求するかを決定します。

所有権とライフタイムのルール

  1. ランタイムは解決を担い、ソースは構築を担う。 ランタイムは、リクエストがどのエージェント、どのプロバイダー参照、どの生成を対象とするかを決定します。ソースがその判断のためにアンビエントな状態を読み取ることはありません。
  2. 機能は世代ごとに不変です。 配線を変更する設定適用では新しい RuntimeCapabilities が構築されます。ターンは開始時に受け取った Arc を完了まで保持するため、リロードによって実行中のターンの下からプロバイダーが入れ替わることはありません。
  3. 返される handle は、ある scope の間だけ借用される。 provider や memory の handle は、それを要求した session または turn に属する。ソース側は instance をキャッシュして共有してよいが、呼び出し元は session の範囲を超えて handle を保持してはならない。
  4. エージェントごと・世代ごとに1つのストア。 同じ世代内で同じエージェントに対する2つのメモリ要求は、必ず同じ基盤ストアに到達しなければなりません。現在のコードは同じ設定から構築することで、これを暗黙的に保証しています。本契約は、これをソースの義務として明文化するものです。
  5. オブザーバーは世代ごとにプロセス単位で存在します。 ソースではなくインスタンスであり、エージェントごとに解決されるものではないためです。
  6. アウトバウンドのみ。 ChannelSource は、ランタイムが送信するチャネル（エイリアス指定の返信、スケジュール配信、承認プロンプト）を対象とします。受信ターンは RuntimeIngress を介して到着し、このコントラクトは対象外です。

セキュリティポリシーはランタイムが管理します

この問題では、解決済みのセキュリティポリシーを境界をまたいで明示的に保つ必要があります。ルールは次のとおりです：

  • ランタイムは各エージェントの SecurityPolicy と RuntimeAdapter を解決し、それらを ToolRequest に渡します。ネイティブソースは、渡された値に基づいてツールを構築することが求められる信頼された実装です。これらを Rust のトレイトに渡しても、プロセス内のコードが機械的に制限されるわけではありません。ソースは任意のネイティブツールを返せるため、ランタイムへの受け入れ審査、ポリシーによるフィルタリング、呼び出しごとのゲート制御と承認は、それぞれ独立した要件として残ります。
  • ポリシーに対してツールを構築しても、何かが許可されるわけではありません。構築後も、ランタイムは従来どおりすべての呼び出しを制御し、承認を行います。
  • ランタイムは、コアツールを追加することも、ポリシーで除外されたツールを削除することもあります。ソースが返したからといって、ポリシーで禁止されたツールを追加することは決してありません。

最初の実装スライスにおけるパリティテストでは、代表的な設定内のすべてのエージェントについて、有効なツールセットと承認動作が変更されていないことを示す必要があります。

DaemonRegistry の位置づけ

DaemonRegistry は置き換えられるのではなく、組み込まれています：

  • その役割と現在の登録方法は維持されます。
  • channels、cron、SOP、RpcContext のスターターは generation の RuntimeCapabilities にアクセスできるようになり、独自に providers、memory、tools を構築しなくなります。このシグネチャ変更は独立したスライスとして扱います（下記のステップ4）。gateway スターターは capabilities を受け取りません。v0.9.0 のカットで削除され、その routes が RPC へ移行するため、gateway 自体の構築も不要になります。
  • 共有SOPエンジンと、現在それが保持している監査ロガーは、機能形状の状態です。本提案ではこれらはそのままの場所に残し、機能世代の背後へ移動する作業はフォローアップとして挙げています。

関連する他の作業との関係

  • #6864 は 2026-08-23 に機械的な依存関係ゲーティングへと範囲を絞り込まれました。当初提案されていたオーケストレーターの移動は、ランタイムが所有するセッション作業に移りました。本提案はそのいずれとも重複しません。移動後のオーケストレーターが利用する機能コントラクトを提供するものです。
  • #11012 およびその RFC #9487 は受信コマンド経路（RuntimeIngress / InboundTurn）を担当します。本提案は、ターンが 何から構築されるか を担当します。両者は、受信ハンドラが保持する Runtime ハンドルで接続します。
  • #10998 (デフォルトランタイムではコアツールのみ) は ToolSource を利用しており、オプションのツールはアプリケーションの ToolSource の背後に移動され、ランタイムにはコアツールのみが残ります。

残っている依存関係と、その理由

この Issue は、保持される依存関係について、未使用の機能の背後に隠すのではなく、その理由を説明することを求めています。期待される最終状態は次のとおりです:

  • zeroclaw-tools: v0.9.0まで保持する、説明された例外。 Tier-1のコアツールは現在2つのクレートに分かれています。shellとfile_readはランタイムにあり、file_write、file_edit、glob_search、content_search、メモリツール、git_operations、web_fetchはzeroclaw-toolsにあります。tier-2のツールには、ToolRequestが保持していないランタイム内部（スケジューラ、キャンバスストア、ask-userハンドル、SOPエンジン、セッションバックエンド、ライブ設定）が必要です。どちらかを アプリケーションのToolSourceの背後に移すと、これらの内部が公開契約に漏れ出してしまいます。そのためステップ7ではtier 3のみを移動し、ratchetでこの例外を明記します。依存関係の削除はv1.0.0の作業です。
  • zeroclaw-providersとzeroclaw-memory: 当面は残存させる想定です。理由はターン構成以外にあります。doctor、quickstart、migration、およびvision routingは、プロバイダーやメモリを直接構築しており、現時点でこのクレートにホストされたままです。それぞれがホールディングクレート計画における個別の抽出候補です。ステップ7のratchetでは、これらの依存関係のみを許可して名前を明記し、新たな利用が発生した場合はチェックで失敗するようにすべきです。

Settled decisions

これらはこのページが最初に提案された時点では未解決でした。v0.9.0 のアーキテクチャレビューで両方とも決着しました。

  1. run_turn と RuntimeIngress の待機の比較。 run_turn は最小限の形で出荷され、session/prompt が使うものと同じセッションアクターのクライアントとして動作します。#11012 を待つことはありません。
  2. ProviderSource がリクエストの主体（principal）を受け取るかどうか。 受け取ります。最初の実装スライスから、capability を受け取るコンストラクタが導入される時点で、ProviderRequest に principal: Option<&PrincipalId> が追加されます。埋め込み側が実装するリクエスト型にフィールドを後から追加すると破壊的変更になるためです。このページのスケルトンにはまだこのフィールドは含まれていません。
