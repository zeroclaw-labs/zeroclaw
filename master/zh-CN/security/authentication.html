认证与主体

每个到 daemon 的 RPC 连接都会在 initialize 握手期间绑定一个 principal，并且每次方法调用都会根据当前配置为该 principal 分配的权限进行检查。本页介绍 provider 集合、本地用户列表、权限配置文件，以及最重要的：现有远程连接会发生哪些变化。

按一次处理完成

  1. provider 负责验证单个凭据：握手中显式提供的 auth_token 会选中由 auth_provider 指定的 provider（默认为 native，即网关配对令牌）；若未提供令牌，本地 Unix 套接字会将其内核对端 uid 提交给 peercred provider。被选中的 provider 一旦拒绝，该结论即为最终结果，凭据不会再尝试其他 provider。

  2. 共享解析器将已验证的身份映射为规范的主体 ID，以及配置为其分配的权限配置文件。OIDC 身份以已验证的 issuer + subject 作为键，本地名册身份则以其持久的 [users.<name>] 主体 ID 作为键。

  3. 每个 RPC 方法（除两个握手方法外）都被归类到所需的资源-动词授权，缺少该授权则拒绝访问。initialize 携带凭据本身，而 cert/renew 则通过提交它的双向 TLS 客户端证书进行身份验证，而非通过主体（principal）。细粒度选择器在此基础上叠加：

    • 配置写入会检查 config_write_paths;
    • session/new 和 session/prompt 会检查 agent 选择器，并将会话工作区限定在该 agent 策略允许读写的目录内，无论工作区是由请求指定的、随恢复的会话一同存储的，还是从持久化会话中恢复的。会话绑定到解析后的目录，而非请求中的写法，因此在准入之后重新指向符号链接形式的 cwd 不会改变会话的目录；以此类别名保持的活动会话会被拒绝。其他会话方法目前尚未检查 agent，详见此层尚未做的事情（待实现）；
    • 运行或批准 SOP 需要管理员授权。创建、保存或删除 SOP 需要该 SOP 所运行为的智能体的授权。未在步骤或流程上指定智能体的步骤，将按排序顺序取第一个已配置的智能体别名作为其智能体，这也是无头执行器的回退智能体。每个步骤都会计入，包括确定性流程中的步骤；
    • 附件、人格文件、指定了某个智能体的成本查询以及定时任务都会检查智能体选择器。通过本地路径发送的附件还必须指定一个目标智能体的策略允许其读取的绝对路径。舰队成本摘要的按智能体明细仅列出委托方的智能体，但其总计和按模型用量仍涵盖所有智能体；
    • daemon 范围的日志与事件读取（logs/subscribe、events/subscribe、events/history、logs/query 和 logs/get）仅向管理员和共享操作员开放。其记录来自所有主体的工作，其中包括其他主体的授权拒绝记录，且许多记录未指明所有者，因此即使拥有 Logs:Read 和 * 代理选择器，受限主体也会被拒绝。
    • fs/list_dir 仅列出启用的智能体（主体可使用的智能体）策略允许该智能体读取的绝对路径。它会拒绝相对路径、.. 组件，以及在 Windows 上的网络路径和设备路径。 这些根路径来自每个智能体解析后的策略：其风险配置文件、其 workspace.access 授予读取权限的同级工作区（对于会话工作区，还包括读写权限），以及只读的共享 skills 目录。非工作区限定的智能体（自治级别为 full、风险配置文件中设置了 workspace_only = false、使用 yolo 预设，或设置了 workspace.unrestricted_filesystem = true）可以读取任何不在禁止访问路径中的路径，因此有权使用此类智能体的主体，可以列出并打开该智能体能够访问的任意位置的会话。

    session/new 和 session/prompt 在等待会话队列之后会重复执行这些检查，因此在请求排队期间，如果其主体权限被收窄或凭证已过期，该请求轮到执行时会被拒绝。

通过守护进程的 RPC 配置方法（由 zerocode 的配置编辑器使用）以及其受监管网关的配置 API（由 Web 仪表板使用）进行的编辑，授权即时生效。两者共享守护进程当前代的实时配置、配置写入锁以及已接受的授权权威。通过任一接口编辑 [permission_profiles]、[users]、[oidc] 或 security.trust_daemon_uid，都会在保存时编译并发布策略，然后才返回写入成功。已建立的原生令牌连接和本地连接会在下一次操作时重新解析，无需重新连接或重启；OIDC 连接则必须重新初始化。仪表板的待重新加载标志仍然适用于需要重建的、由守护进程管理的子系统；它不会延迟此次授权发布。在守护进程外部进行的编辑，即直接修改 config.toml 或使用 zeroclaw config set，仍会在守护进程下一次重新加载或重启时生效。这些授权 CLI 写入只会保存到磁盘，不会发布到正在运行的守护进程，也不会触发其重新加载。通过网关的配对控制撤销网关配对令牌，会使使用该令牌认证的连接在其下一次操作前失效。通过编辑配置（无论是通过 RPC 还是在磁盘上）从 gateway.paired_tokens 中删除令牌，对正在运行的守护进程没有任何影响，使用该令牌的连接仍保持授权。此删除会在守护进程下一次重新加载或重启时生效，除非在此之前通过网关进行的配对变更将实时令牌集（包括该令牌）写回配置。请通过配对控制撤销令牌。

本地连接

在 Unix 套接字上，未提供令牌的连接通过其内核对端 uid 识别。当 security.trust_daemon_uid 为 true（默认值）时，守护进程的自身 uid 会以受信任的共享操作员身份连接，并拥有完全访问权限，无论是否配置了 [users] 名单。因此，未配置名单的安装对于运行守护进程的账户，其行为与之前保持一致。

运行守护进程的操作员拥有其配置文件，而仅限本地的锁定恢复依赖于这一权限。在 Unix 套接字上，将 security.trust_daemon_uid 设置为 false，要求每个本地对端（包括守护进程自身的 uid）都必须通过名册映射或提供令牌。该设置对 Windows 命名管道无效，详见下文。

任何其他 uid 都必须通过显式的 [users.<name>].uid 条目进行映射。未映射的 uid（包括 root）如果未提供令牌，则会被拒绝，无论是否存在 roster；不会回退到共享操作员访问权限。监听器以仅所有者可访问的方式创建套接字，因此目前只有守护进程自身的账户和 root 能够访问它；roster 条目决定了其他任何 uid 在获得访问权限后可以执行的操作。

Windows 命名管道不携带对端 uid。在没有名册时,管道的 ACL 即为凭据,本地连接即视为共享操作员。一旦存在 [users] 名册,本地客户端必须在此出示令牌,security.trust_daemon_uid 不再生效,守护进程自身的账户也没有受信任的本地途径。在策略编译期间,已配对的网关令牌仍会被认证为共享操作员,因此发送该令牌的客户端(无论通过 WSS 还是通过管道)都可以在线修复名册。zerocode 的本地管道连接不发送令牌,因此若没有此类客户端,锁定状态需通过编辑 config.toml 并重启来修复。

客户端可以在 initialize 中转发其 shell 环境，使守护进程的子进程能够看到其 PATH 和凭据套接字（参见 环境变量透传）。该快照仅保留给操作员级别的主体（共享操作员，或设置了 admin = true 的名册主体）在本地连接上使用。其他所有主体以及所有远程连接，则改用守护进程自身的环境。

每次构建或恢复会话时都会重新检查资格。如果现有会话保留了非空的转发环境，则只有当前已获授权的本地操作员才能恢复或向其发送提示。通过 WSS 重新连接，或在提示排队期间失去 admin 权限，都不会将该环境带入下一轮：请求会在执行前被拒绝。若要在不使用转发环境的情况下继续，请创建新会话。没有转发值的会话仍可正常恢复，但需满足其他授权检查。保留的环境在会话生命周期内不可变；拒绝后续请求不会在已运行的轮次下方改写它。恢复时，当前连接的已授权环境还必须与会话保留的环境一致。若两者不同，请创建新会话；不含环境的会话在移除 admin 权限后仍可恢复。

恢复

远程身份验证绕过功能从不提供：远程连接始终必须出示有效凭据。在授权策略仍可编译的情况下，持有已配对网关令牌或操作员级主体的客户端可以从任何位置修复锁定状态。若没有此类凭据，并且始终处于全部拒绝状态时，恢复路径需在运行守护进程的主机上执行。适用哪种本地恢复路径，取决于策略是否仍可编译。

无法修改已能编译的策略。 授权已生效，本地可信路径在 Unix socket 上保持完好；在 Windows 上，请参见上文的命名管道说明。以守护进程自身的 uid 进行本地连接：在 security.trust_daemon_uid = true（默认值）下，该账户即为受信任的共享操作员，无论名单中如何设置。通过该本地连接修复有问题的条目，例如在 zerocode 的配置编辑器中，或使用 RPC config/set 设置 users.alice.uid，更改会在保存时编译并发布。编辑 config.toml 或运行 zeroclaw config set 同样可以修复，但只有在守护进程重新加载或重启之后才会生效。

因已接受的全拒绝状态而被锁定。 策略未能编译，因此已接受的状态会在解析运行之前拒绝所有主体，包括守护进程自身的 uid 和共享操作员。没有任何 RPC 能修复它：config/set 和 config/reload 与其他所有操作一样被拒绝。请以 config.toml 的所有者身份直接编辑该文件，然后重启守护进程，以便编译并发布已修复的部分。守护进程会忽略 SIGHUP，因此需要重启才能使其重新加载。

如果将 security.trust_daemon_uid 设置为 false，受信任 UID 途径就会失效。能够通过编译的策略，仍可能被出示已配对网关令牌的客户端，或拥有管理员授权的名册主体在运行时修复。否则，两种状态下的修复方式相同：以 config.toml 的所有者身份编辑该文件，然后重启。仅在可以接受的场景下关闭此设置。

注册（获取用于出示的令牌）

守护进程仅负责验证令牌；客户端需从身份提供方（IdP）获取令牌。CLI 内置两种无浏览器流程：

# 通过设备授权许可（RFC 8628）进行交互式登录：
# prints a verification code to enter in any browser, waits for
授权后，将访问令牌写入标准输出。
export ZEROCLAW_AUTH_TOKEN="$(zeroclaw oidc login corp)"

# 同样通过系统浏览器：Authorization Code + PKCE（仅 S256）
# with an RFC 8252 one-shot loopback listener. The mechanisms never
# 相互融合。
export ZEROCLAW_AUTH_TOKEN="$(zeroclaw oidc login corp --browser)"

# 通过 client_credentials 使用无界面服务主体（需要
# entry的 client_secret）：
export ZEROCLAW_AUTH_TOKEN="$(zeroclaw oidc token corp)"

进度消息输出到 stderr，stdout 仅输出令牌，因此两个命令都可以与命令替换组合使用（oidc 命令会在任何可能输出内容的启动前置步骤之前运行，包括 OTP 种子披露）。不会存储任何内容：请在令牌过期前，将其作为 auth_token 在 RPC 握手中提交（或通过环境变量提供），然后重新注册。

客户端只信任条目中指定的颁发者，不信任其他任何颁发者。在使用发现文档中公布的任何端点之前，该文档必须明确声明恰好是该颁发者。所有接收凭据的端点必须满足与颁发者相同的 URL 策略（使用 https，或仅当主机为精确的回环地址时使用 http）。从不跟随重定向，响应正文有大小上限。只有当令牌响应包含非空的 Bearer 访问令牌时，才会接受该响应。机密客户端（带有 client_secret 的条目）在设备授权和 client_credentials 请求中使用 HTTP Basic 进行认证，在授权码交换（--browser、网关的浏览器流程以及仪表板登录）中则将密钥放在表单正文中发送。公共客户端则在表单中发送其 client_id。

--browser 在 macOS 和 Linux 上会为你自动打开系统浏览器，并且在所有平台上都会打印登录 URL，以便你在同一台机器的浏览器中手动打开（回调会发送到运行 CLI 的主机上的本地回环端口）。浏览器启动程序与 CLI 的标准流分离运行，因此启动程序自身写到 stdout 的任何内容都无法污染结果：stdout 仍然只输出令牌。

两个回调适配器（CLI 的回环监听器和网关回调）都会执行 RFC 9207 的 issuer 校验。如果响应中的 iss 参数与发起该流程的 issuer 不匹配，则在处理其中的 code 或 error 之前直接拒绝。如果响应中完全没有 iss，则予以接受，因为该参数是可选的，并非所有 issuer 都会发送它。当代码交换在返回访问令牌的同时返回了 id_token，该 id_token 会被完整校验（包括 issuer、audience、过期时间以及与本次流程绑定的 nonce），校验通过后随即丢弃。只有访问令牌会被提交给守护进程。注册客户端对发现过程本身同样保持怀疑：在使用其中列出的任何端点之前，它会拒绝 issuer 与所配置 issuer 不完全一致（包括末尾斜杠）的 .well-known/openid-configuration 文档（即 RFC 8414 校验），并且会限制所读取文档的大小，从而确保恶意或故障的 issuer 无法将流程重定向到其自选的端点，也无法返回无上限的响应体。

没有 IdP 凭据的客户端（网页仪表板、zerocode）改为通过网关完成注册。网关会使用已配置条目的客户端凭据代理相同的流程：GET /api/oidc/providers 列出别名，POST /api/oidc/{alias}/device/start 和 /device/poll 驱动设备授权流程，GET /oidc/login/{alias} 运行浏览器流程。其一次性回调页面通过 postMessage（仅限同源）将令牌交给打开它的窗口，并提供手动复制的备用方式。网关还会发送 Cross-Origin-Opener-Policy: same-origin，因此弹窗在经过身份提供方跳转后，会切断 window.opener。在当前浏览器中，该页面上的手动复制才是可用的交接方式。仪表板本身不使用该页面：其登录会将令牌保存在网关中，并通过会话 Cookie 进行关联（参见 仪表板登录）。这些路由出于必要是未经身份验证的（注册发生在身份验证之前），并受速率限制，且不授予任何权限：它们只是在用户批准后，转发 IdP 所授予的内容。设计原理和故障模式表请参见代码仓库中的 docs/security/oidc-browser-pkce-design-8289.md。

浏览器网关登录流程还需要一个短期有效的 HttpOnly 绑定 Cookie，该 Cookie 必须来自发起登录的那个浏览器。该 Cookie 不授予任何会话或 API 访问权限。若回调请求中没有匹配的 Cookie，则会在代码交换之前被拒绝，并使待处理的流程失效；此时应在目标浏览器中重新发起登录，而不要在不同浏览器之间转发回调 URL。每个标签页都有各自的流程 Cookie。若因中继容量不足而被拒绝，有效的流程和 Cookie 将保留，可在原有十分钟截止时间内重试。

绑定 Cookie 对身份提供方的顶层 GET 重定向使用 SameSite=Lax。这些 Cookie 不带 Domain 属性，并使用 Path=/，包括在网关路径前缀之后的情况；在 HTTPS 下还使用 Secure 和 __Host- 名称前缀。远程注册请通过 HTTPS 提供服务。纯 HTTP 下的 Cookie 作用域仍会跨越同一主机上的不同端口；这并不能将其与同一主机上的其他应用程序隔离。Cookie 被拦截会导致浏览器注册失败；设备流程仍然可用。

限流分为多个层级。发起流程的请求（POST /api/oidc/{alias}/device/start、GET /oidc/login/{alias} 和 GET /oidc/callback）会计入一个专用于设备注册的网关暴力破解限流器实例。该实例与处理错误配对令牌的限流器使用相同的阈值和锁定策略，但使用独立的计数账本。因此，因注册而被锁定的地址仍可进行配对或提交 webhook 签名，而因这两项操作触发的锁定也不会阻止注册。只有在回调无效时，才会计为一次尝试：回调携带的 state 没有对应的有效流程状态、issuer 不匹配、身份提供方返回错误、缺少授权码、流程进行期间别名已被删除，或代码交换失败。完成登录的回调不计费，网关因中继容量已满而拒绝的回调也不计费，这样大量用户同时登录时，不会导致他们共享的地址被锁定。因待处理流程存储已满而被拒绝的浏览器登录同样不计费，原因相同。提供方列表查询、设备轮询和登录发起请求，每个客户端每分钟有 20 次请求预算。这一预算高于 RFC 8628 规定的 5 秒最小轮询间隔（每分钟 12 次轮询），既留有余量，又能防止客户端高频轮询。当身份提供方返回 slow_down，或直接拒绝设备码时，该轮询会计为一次尝试，因此中继无效设备码的客户端会触发现有锁定机制，而不会无限轮询。网关与身份提供方之间的链路若发生传输故障，与调用方无关，不计入其预算。超出预算或被锁定的客户端会收到 HTTP 429 响应，并带有以秒为单位的 Retry-After 延迟值。zerocode 会至少等待该延迟时间，且不少于 RFC 规定的 5 秒递增间隔，然后才发起下一次轮询（仍受设备码剩余有效期限制），并且在任何情况下轮询间隔都不会短于 5 秒。所有客户端共享的、同时发往身份提供方的出站中继最多为 16 个，从而限制网关代所有客户端对 IdP 产生的负载。待处理流程存储最多可同时容纳 32 个浏览器登录，单个远程客户端最多可占用 8 个。因此，即使调用方发起登录后从不完成，也无法在这些流程存活的十分钟内占满存储，使其他人无法使用。回环客户端与网关的其他认证限制一样，豁免各客户端预算。因此，若同一主机上的反向代理需要让每客户端限制作用于其背后的真实调用方，必须启用 trust_forwarded_headers。启用该设置后，网关会取 X-Forwarded-For 中最右侧的地址（即直接代理添加的那一跳），若不存在则取 X-Real-IP。转发的回环地址会被跳过，以防其获得仅限本地的限流豁免。当转发链全部为回环地址时，网关会使用一个不享受豁免的键，而不是回环对端地址。配置代理时，应使用追加或覆盖的方式设置该头，而不是原样转发客户端提供的列表，例如 nginx 中的 proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;。如果只设置了 X-Real-IP，还需同时用 proxy_set_header X-Forwarded-For ""; 清除优先级更高的列表，并配合 proxy_set_header X-Real-IP $remote_addr; 使用；否则客户端提供的 X-Forwarded-For 仍会优先生效。每个注册响应都会在网关既有的 no-referrer 策略之上，附加 Cache-Control: no-store 和 Pragma: no-cache，因为设备码和访问令牌会通过这些响应体传输。

zerocode 通过相同的 API，依据其自身配置完成注册。[connection.wss] enroll_url 指定网关的 HTTP 源（origin），允许可选的路径前缀。除非指向回环地址（127.0.0.1、::1 或 localhost），否则它必须使用 https://，因为设备码以及随后的访问令牌都会经由该地址传输，且不会跟随重定向，因此无法在事后引入明文跳转。注册连接使用与 WSS 链路相同的 [connection.wss.tls] 信任材料：已配置的 CA、skip_verify 以及双向 TLS（mTLS）客户端证书。当该材料导致证书未经校验时，zerocode 会在设备码发出之前而非令牌到达之后进行询问，并且询问的是注册源本身，它可能并非会话随后连接的守护进程。回答 always 会将该源记录到 skip_verify_routes 中；非交互式运行无人可询问，因此注册会在此处停止。zerocode 会将每次轮询等待时间截断为设备码的剩余有效期，且在其过期后绝不再轮询；对于声明的有效期超过一小时或轮询间隔超过五分钟的情况，它会直接拒绝，而不是对恶意响应进行休眠等待。声明的间隔为 0 或 1 时，将被提升至 RFC 8628 规定的五秒默认值，因此网关响应无法使 zerocode 进入每秒一次的轮询（该频率只会被单客户端配额拒绝）。旧版自动注册路径仅将令牌保存在内存中，且仅限于该会话。该路径使用与 zerocode login 相同的设备授权辅助函数，因此同样会发送 S256 PKCE 挑战（code_challenge）；若提供方在其设备授权端点拒绝 code_challenge，此处同样会失败。若需基于 URL 范围的持久化登录，请使用 zerocode login <alias> <wss-url> --gateway-url <https-origin>；参见 远程设置。该命令从空的客户端目录开始：OIDC 登录通过网关授权签发其首个设备证书，无需预先创建设备、本地用户、守护进程配对码、SAS 或单独的注册监听器。守护进程通过与 RPC 相同的已接受 OIDC 策略校验 Bearer 令牌，要求持有 sessions:create 权限且具备允许代理的人类用户（或 system:execute / 管理员），仅对 CSR 的公钥进行签名，并将新设备记录到现有证书台账和审计日志中。静态客户端证书固定（pin）仍需通过带外方式配置。WSS 在每次 initialize 时仍要求同时具备 mTLS 与有效的 OIDC 访问令牌。该命令将已接受的访问令牌保存在仅限所有者访问的本地 zerocode-config.toml 中，并在启动需要新令牌时重新进行身份验证。

收窄权限绝不会向已有的 agent 重新添加工具。扩大授权之后，需要创建一个新会话，以接收扩展后的工具范围。agent 中不会存储新的配置快照，也不会存储独立的主体策略缓存。

延迟 MCP 指令源自剩余可加载的工具，且仅在暴露 tool_search 时显示。主体若要按需激活，需同时具备 tool_search 和指定的延迟 MCP 工具；该辅助工具绝不会被隐式授予。获准的 mode = "always" MCP 工具会被预激活，无需辅助工具即可保持可调用。

如果主体的工具选择器或智能体选择器中任一受到限制，则 delegate（有界且独立）、spawn_subagent 和 execute_pipeline 将不可用，包括封装这些工具的技能别名。这些嵌套路径尚未同时承载当前主体的两项上限；普通的父级对话轮次仍可正常使用。

某些工具执行的操作不携带调用方的主体（principal），因此没有 admin 的主体无论其选择器指定了什么（包括 "*"），都无法在其会话中使用这些工具：

  • sessions_list、sessions_history 和 sessions_send 会在不检查归属的情况下列出、读取并追加其他会话的内容；如果某个智能体注册了 sessions_reset 和 sessions_delete，它们也会如此。仅报告调用方自身会话的 sessions_current 保持不变。
  • cron_add、cron_update、cron_run、cron_list、cron_runs、cron_remove 和 schedule：定时任务的执行不携带调用方的限制，并且 cron 记录与运行输出按 agent 共享，而不是归调用方主体所有。
  • send_message_to_peer，其对话轮次在另一个代理上运行。
  • sop_execute、sop_advance、sop_approve 和 sop_workshop：SOP 步骤会以该流程对应的智能体身份在无界面模式下运行，已应用的研讨会提案会成为共享流程，之后同样以这种方式运行。只读的 SOP 工具则遵循常规工具选择器。
  • model_routing_config 和 proxy_config，它们保存守护进程配置，所有智能体后续的运行都会使用该配置。通过 RPC 进行同样的更改需要 config:update。
  • spawn_subagent 和 execute_pipeline，其嵌套运行会重新获得使用上述工具的权限。

这些工具都会报告 requires_unrestricted_principal，因此其技能别名也会一并被排除。当两个选择器均为 "*" 时，直接的 delegate 工具会保留，因为会话持有其句柄：每个有界、独立、后台、并行和嵌套的子代理都会排除同样的工具。它还会在构建每个子代理时解析发起凭据的当前权限，因此在该凭据失去 admin 之后构建的子代理同样会排除这些工具。其技能别名也会被排除，因为它们捕获的目标无法被识别为所绑定的句柄。

在会话创建时、会话重新水合时、每次提示之前，以及已接受的转向内容被消费时（包括内存写入后的复查），都会应用这一工具访问限制。会话中途被降级的管理员，会在下一次提示或已接受的转向内容处理时失去工具。与选择器收窄一样，它从不会把工具归还给正在运行的会话。管理员主体和共享操作员保留其智能体的既定工具，现有的定时任务继续运行。

排队中的提示会在提供方协调以及 Agent 和任务的等待结束后，在实际执行该轮次的 Agent 上重新解析权限。同一准入检查还会应用工具访问限制，并在存储争用之后保护提示检查点或运行状态的写入。准入被拒绝时，不会调用提供方，也不会持久化已结束的轮次。这是轮次的准入边界，并不会持续撤销已经运行的轮次的权限。

RPC cron/patch 和 cron/trigger 同样会拒绝非管理员的 agent 任务，包括通配符选择器。这些任务无法携带调用方的会话限制；检查会在查询任务后使用当前权限进行。Shell 任务保留其现有的授权和命令策略检查。Cron 读取、删除操作，以及操作员已调度的任务均保持不变。

sops/run 和 sops/decide 这两个 RPC 需要管理员授权，即使非管理员拥有通配符工具与代理选择器也是如此。无头步骤不携带调用方的主体限制。这包括 deny、amend 和 revise 决策。在决策模型与引擎等待结束后，该 RPC 通过其同步存储副作用持有当前授权。SOP 存储忙碌时会立即拒绝请求；待争用解除后重试即可。后台 SOP 处理保留其常规存储超时。SOP 编写保留其独立的代理选择器检查。

在会话数据工具完成所有权检查之前，由管理员或触发器启动的定时代理任务、SOP 运行和对等轮次仍可调用这些工具。要同样将它们从这些运行中移除，请在这些运行所使用的每个代理的风险配置文件的 excluded_tools 中列出 sessions_list、sessions_history 和 sessions_send，以及任何针对它们的技能工具。这样即可将它们从这些代理的所有运行中移除，包括管理员的会话。

现有的八参数 Rust 构造函数 Agent::from_live_config_with_tui_env 仍然可用。RPC 使用新增的 from_live_config_with_tui_env_and_principal_tools 构造函数，并在提示词准入时重新应用共享解析器的授权。

那种组合并未覆盖通往代理工具的每一条路径。Cron 任务和 SOP 编写只检查代理选择器。持有 cron 授权的受限主体可以通过 RPC cron/add 和 cron/patch 为其代理创建或编辑 shell 任务。该命令在此处同样要经过代理的审批策略检查，与从 CLI 和仪表板操作时一致，因此在 supervised 自治级别下，需要审批的命令会被拒绝而不会被存储。如上所述，代理任务对其同样被拒绝。持有 SOP 创建或更新授权的主体可以保存一个流程，由其触发器在之后运行。应将 cron 和 SOP 编写授权视为代理工具的授权。

这些检查在任务写入时会再次执行，而不仅仅是在请求到达时执行。如果在定时任务写入等待数据库期间撤销了授权或取消了已配对设备，该写入会被中止，或者等待其完成后才生效。

从 pipeline 步骤或通过技能别名调用的工具从不继承批准。运行时只批准它自己分派的调用，因此在受监督的自主模式下，需要批准的命令会在此处被拒绝；请直接调用该工具，以便系统向你请求批准。

主体拥有的会话可以在授权允许的情况下使用同步和并行委派。后台委派及其 check_result、list_results、cancel_task 和 await_sessions 操作会被拒绝，包括通过技能别名和嵌套委派调用的情况。这些任务记录和结果文件目前使用智能体别名可见性，无法保护一个主体的私有输出不被另一个使用同一智能体的主体访问。此拒绝规则同样适用于管理员拥有的会话；其私有记忆仍然是私有的。共享的运营者委派仍然可用。现有的共享结果产物不会因此项限制而迁移或删除。

破坏性变更：远程 WSS 需要身份验证

从本次变更起，远程 WSS 连接必须在 initialize 中提供 auth_token。不存在未经身份验证的远程回退方案。

一个启用了 [wss] 的监听器，如果不存在任何可用的凭证路径（既没有 [oidc.<alias>]，也没有已配对的令牌，且 gateway.require_pairing = false），会被配置校验拒绝，因此没有任何受支持的途径能够保存这种配置。已经存在于磁盘上、呈现此形态的配置仍然可以启动：守护进程会正常运行，而该监听器会拒绝所有远程握手。它不会拒绝加载，因为操作人员必须能够启动守护进程，才能修复该配置。

无效的 [oidc.<alias>]、[users] 或 [permission_profiles] 配置段属于另一种情况。此时授权策略本身无法编译，因此守护进程会安装全部拒绝的接受状态，并记录日志说明其正在这样做，直到修复这些配置段并重新加载为止。在该状态下，所有主体都会被拒绝，无论远程还是本地连接，包括守护进程自身的 uid。因此，修复方法是上文「Recovery」一节所述的磁盘端修复。

迁移现有远程 zerocode 用户：

  1. 与网关配对，以获取 Bearer 令牌。

  2. Give zerocode the token, either in its config:

    [connection.wss]
uri = "wss://daemon.example.com:9443"
auth_token = "zc_..."

    或者通过 ZEROCLAW_AUTH_TOKEN 环境变量进行设置，该变量会覆盖配置文件中的值，并使凭据不必写入文件中。

    或者通过指定包含它的文件：

    [connection.wss]
uri = "wss://daemon.example.com:9443"
auth_token_file = "/etc/zeroclaw/zerocode-bearer"

    优先级依次为 ZEROCLAW_AUTH_TOKEN、auth_token_file、auth_token。在支持 Unix 权限位的平台上，如果被引用的文件可被其他任何账户读取，则会跳过该文件并发出警告，而不是使用它，随后按该顺序应用下一个来源。在其他平台上，文件的 ACL 是唯一的防护措施。

    环境变量是推荐的方式。如果改为将令牌保存在配置文件中，zerocode 会将该文件设置为仅所有者可访问（0600，位于权限为 0700 的配置目录中），并修复早于此行为生成的文件的权限模式，前提是平台支持 Unix 权限位。在不支持权限位的平台上，目录 ACL 是唯一的保护措施，因此应将该文件视为机密信息。

OIDC 访问令牌的工作方式相同,配置方式为 auth_provider = "oidc.<alias>"。

网关 HTTP API

网关的配置与引导路由（/api/config*、/api/quickstart/*、/api/channels/bind）在结构上强制执行身份验证：由一个路由层中间件统一守护整个路由组，因此没有任何单独的处理函数需要自行携带（或可能遗漏）鉴权检查。该中间件采用与 RPC 路径相同的主体（principal）模型，并通过相同的提供方注册表和解析器工作：

  • 已配对的 bearer 令牌（Authorization: Bearer zc_...）会解析为拥有完整权限的共享操作员，与之前的行为一致。拒绝访问时仍保持原有的 401 响应格式。
  • 使用 X-ZeroClaw-Auth-Provider: oidc.<alias> 请求头提交的 OIDC bearer 由该提供方验证，并解析为一个限定范围的主体（principal）。提供方的选择是显式的，与 RPC 握手中的 auth_provider 字段保持一致：被指定提供方的拒绝结果具有最终效力，且在不同提供方之间永不回退。
  • CORS 预检请求（OPTIONS）与以往一样无需认证即可通过。除 GET、HEAD、POST、PUT、PATCH 和 DELETE 之外的其他方法均会被拒绝。

对 OIDC Bearer 令牌的验证是未经认证的调用方迫使网关执行的工作。使用 validation = "introspection" 时，每次验证都会以守护进程自身的客户端凭据，向身份提供方发起一次经过认证的往返请求。两项限制约束这一开销。被拒绝的凭据会计入每个客户端的计数账本，阈值与配对令牌错误相同（一分钟内 10 次，然后锁定 5 分钟，回环地址豁免）。该账本独立于配对账本，因此客户端重放已过期的令牌不会把其运维人员锁定在配对之外，配对锁定也不会阻止 Bearer 令牌。Bearer 令牌账本会在每个请求时从运行中的配置读取 gateway.trust_forwarded_headers，因此保存的代理信任变更无需重建路由器即可生效。网关与身份提供方之间的链路传输失败，以及已验证但策略不授予任何权限的身份，都不能说明调用方的情况，因此不计入该调用方的账本。所有客户端（包括回环地址）同时进行的 Bearer 令牌验证至多 16 个，这一上限约束了网关代所有调用方对身份提供方所做的操作。该并发槽位仅在验证期间占用，不会在其所放行的请求处理期间持续占用。被锁定的客户端将收到 HTTP 429 响应，因容量不足而被拒绝验证的请求将收到 HTTP 503 响应，两者均附带 Retry-After 头，以秒为单位标明等待时长。仪表盘会话由其专属层验证，不与这些限制竞争。

受限主体的 Config 授权分两步执行。路由层按 HTTP 方法设置粗粒度下限：读取操作需要 read，其他操作至少需要 create、update 或 delete 之一，因此只读主体永远无法到达变更类处理器。随后，每个变更类处理器在执行第一个副作用之前，都会授权其完整写入集合：该变更将持久化的每个配置路径，按其对配置的影响分类（为新建路径为 create，为删除路径为 delete，其他情况为 update），并与配置档中的 config_write_paths 选择器进行匹配。分类依据的是操作本身，而非 HTTP 方法：通过 POST /api/config/map-key 创建映射键，或通过 PUT 在新别名下隐式创建，都需要 create；JSON Patch 的 remove 和 DELETE /api/config/map-key 需要 delete；重命名需要源路径的 delete 和目标路径的 create；删除或重命名级联改写到其他位置的引用同样属于写入集合。只要有一个成员未获授权，整个变更（包括批量操作或级联操作）就会被拒绝，且不写入任何内容。对于无法预先枚举写入集合的操作（例如文件的 schema 迁移、Quickstart 应用），则必须具备 * 选择器。持久化边界会将即将写入的路径与处理器已授权的路径重新核对，因此处理器无法持久化超出其授权范围的内容。

策略仅在持久化边界处变更：写入配置的处理程序会将由此编译出的授权状态发布为下一个已接受的修订版本，每个请求都会依据当前已接受的快照进行验证和解析。请求路径上不会重新编译策略，因此在并发持久化之前读取配置的请求，不可能用旧策略覆盖新策略。提供方验证设置、成员名单或配置档案的已持久化变更，将在下一个请求时生效。在受监管运行中，网关和 RPC 接口共享同一份实时配置、写锁和已接受的策略权威，因此通过任一接口保存都会同时发布到两者。独立网关拥有自己的权威，不会将变更发布到单独运行的守护进程。其他网关接口仍按处理程序执行配对检查，并将在后续版本中采用该层。当账户为管理员时，仪表板登录会话同样满足该配对检查。

控制台登录

Web 控制台可以通过已配置的 OIDC 提供方提供登录功能,可替代配对码,也可与其同时使用。该功能默认关闭:未配置 [gateway.dashboard_sign_in] 的安装会照常显示配对对话框,发送给它的会话 Cookie 会被忽略。

[gateway]
require_pairing = true

[gateway.dashboard_sign_in]
oidc = ["corp"]                # 登录界面上提供的 [oidc.<alias>] 条目
session_lifetime_secs = 28800  # 单次会话的可选上限（300..=604800，默认 8 小时）

开启此功能需要：

  • gateway.require_pairing = true。关闭配对后，任何能访问 Gateway 的人都可以打开所有控制面板路由，因此该配置会被拒绝。官方 Docker 镜像在默认配置中写入了 require_pairing = false；请在那里将其设置为 true，或使用 ZEROCLAW_gateway__require_pairing=true。
  • HTTPS（[gateway.tls]、带有 trust_forwarded_headers 的反向代理，或由中继提供服务且带有 [relay.dashboard] 的仪表板，后者由中继终止：参见 secure transport, 3e）。除非浏览器运行在网关所在的机器上，否则拒绝通过 HTTP 明文进行登录。由中继提供服务的仪表板仅提供登录：中继会看到配对码或令牌，因此在此处拒绝配对和已配对令牌。以管理员身份通过中继登录，会赋予中继管理员级权限，包括进行持久性更改的能力，因此请通过直接连接或使用 zerocode 管理守护进程。
  • 在反向代理之后，浏览器的 Host 会原样透传（例如 nginx 中的 proxy_set_header Host $host;）。回调 URI 和仪表板自身的源（origin）都取自该值，因此如果代理将 Host 改写为内部名称，就会导致登录失败，并且所有已登录状态下的更改都会因被判定为来自其他源而被拒绝。
  • 一个使用带 PKCE（S256）的授权码流程的身份提供方客户端，其重定向 URI 为 <dashboard origin><path_prefix>/oidc/callback（与上文浏览器注册中继所用的 URI 相同）。请注册该精确 URI，不要使用通配符或前缀模式：在网关根据已配置的仪表盘源（#12048）校验该 URI 之前，它是根据请求的 Host 构建的，而身份提供方的精确匹配正是防止登录授权码被发送到其他地址的保障。通过中继提供的仪表盘访问时，该地址始终是该仪表盘自身的地址，守护进程会在启动时记录该地址。其客户端必须列在 interactive_clients 中（或通过 actor_claim 进行分类），并且其访问令牌必须携带已配置的 audience。身份提供方列出了已测试的提供方及每个提供方所需的设置。
  • 访问令牌的有效期应适合一次工作会话，例如一到八小时。该控制台不使用刷新令牌：令牌过期后，用户需要重新登录。

当用户选择一个提供方时，网关会运行浏览器授权流程，并通过一个短期有效的 Cookie 将该流程绑定到当前浏览器，因此在其他地方发起的登录无法在此处完成。ID 令牌是必需的，仅用于验证登录凭据（校验 issuer、audience、authorized party、过期时间和 nonce），验证通过后即被丢弃。访问令牌由提供方按照验证 RPC Bearer 令牌的方式进行校验，账户以其解析出的结果为准。由于两者来自同一次后端通道（back-channel）交换，因此不会将 ID 令牌的 subject 与之比对。服务客户端永远不会获得控制台会话。令牌随后仅保存在网关的内存中。浏览器只持有一个不透明的 HttpOnly、SameSite=Strict 会话 Cookie（在 HTTPS 下还会带上 Secure），任何令牌都不会进入浏览器存储或脚本可访问的范围。

每个携带该 Cookie 的请求都会再次按照 RPC 所使用的同一权威进行检查，包括令牌的过期时间、内省重新验证的截止时间，以及账户在当前生效策略下持有的授权。配置文件映射的变更、提供方的移除，或从 gateway.dashboard_sign_in.oidc 中删除别名，都会在下一次请求时生效。会改变状态的请求还必须在 X-ZeroClaw-CSRF 中携带会话的 CSRF 令牌；携带该 Cookie 的请求和 WebSocket 升级请求，必须来自仪表板自身的源。带有 Authorization 标头的请求仅依据该标头进行判断。

在已登录账户中，可执行的操作取决于其权限配置：

  • profile 中设置了 admin = true 的账户等同于操作员，可访问所有仪表板页面，与已配对的浏览器相同。每次登录都会记录其解析到的主体。该账户在仪表板聊天中发起的对话归属于共享操作员，与已配对浏览器发起的对话相同。
  • 其他账户只能访问其 Config 授权所允许的配置页面。其余页面返回 403，并附带 "reason": "operator_required"，且仪表板会隐藏这些页面。
  • 当网关在守护进程内运行时，未拥有 admin 权限的账户也可以在仪表板中聊天，使用其授权允许的智能体，前提是其配置文件授予了 sessions 的创建、读取、执行和更新权限。智能体仅使用配置文件授予的工具（allowed_tools，配合 tools = ["execute"]）。已禁用的智能体不接受新的聊天，已打开的与该智能体的聊天会对每条消息返回错误，直到该智能体重新启用为止。这些对话归该账户所有：守护进程以该账户身份、在其授权范围内运行它们，其他任何人的仪表板都不会列出这些对话。不提供图片上传功能。每个聊天对应一次对话，且对话的存续时间仅与聊天本身相同。
    • 关闭或刷新页面、离开聊天、连接中断都会结束对话，并停止正在生成的回复。退出登录、会话过期以及守护进程重新加载或重启也会结束对话。新建聊天会开始一个新的对话，不会重新打开任何已结束的对话。
    • 一个登录会话最多同时打开四个聊天（例如四个标签页），一个账户在其所有登录会话中最多可有 32 个聊天。正在创建中或聊天结束后尚未关闭的对话同样计入上限，因此退出后再登录并不会释放名额，必须先关闭这些对话。超出任一上限的聊天会被拒绝，直到有聊天关闭为止。
    • 每个聊天会话都会将令牌提交给签发该令牌的身份提供方所绑定的守护进程。如果期间该提供方的配置被更改为其他签发方或客户端，该聊天会话将被拒绝，且令牌不会被发送到新的签发方。
    • 如果账户在登录状态下被撤销访问权限，其打开的会话将无法凭借该账户自身的权限关闭，而其他人也无法访问它们。守护进程会在此类会话的聊天已消失 wss.orphaned_session_timeout_secs（默认 30 分钟）后关闭该会话，前提是会话处于空闲状态、没有待处理的回复或审批，且其已保存的记录是最新的。将超时设置为 0 即可禁用此功能，此时仪表板无法关闭的会话将保持活动状态，直到守护进程重启。
    • 如果守护进程创建聊天的会话超过十分钟，该聊天会放弃等待，但仪表板仍会继续等待守护进程的响应，并且在响应到达之前，此次创建会占用账户的 32 个会话上限。若会话最终仍被创建，则会在响应到达时被关闭，此后不再计入上限，与上述超时无关。仪表板无法关闭的会话，或在收到响应前其创建过程与守护进程失去连接的会话，会一直计入上限，直到下一次守护进程重新加载或重启，因为仪表板无法判断守护进程何时释放该会话。
    • 关闭的对话其记录仍会保留，但仪表板无法打开它。当账户需要保留超出其聊天周期的历史记录时，请使用 zerocode。

在此 ZeroClaw 中，退出登录会结束当前会话并删除其 Cookie，即使该会话此前已结束也是如此；它不会让用户退出身份提供方。当会话结束（退出登录、过期或检查失败）或失去页面所需的访问权限时，该页面的套接字和事件流会立即关闭。在同一浏览器中再次登录会结束该浏览器此前持有的会话，无论其属于哪个账户，因此之后的退出登录不会让该浏览器中留下任何已登录状态。即使两个标签页同时登录，这一点也成立：浏览器标记 Cookie（zc_browser_<tag>，或在 HTTPS 下位于根路径的 __Host-zc_browser_<tag>；为随机值、带有 HttpOnly、SameSite=Lax，且绝不是凭据）会将该浏览器的会话关联在一起。每个标记都有各自的名称，因此启动后较晚才得到响应的登录会新增一个标记，而不是替换已有标记。较晚完成的登录会结束另一个会话，而退出登录会结束与该浏览器共享某个标记的所有会话。会话结束之前已被接受、但尚未生效的请求（例如请求体仍在传输中的配置更改）会被拒绝。已在运行的聊天轮次会在无人值守的情况下继续完成，就像查看者离开时一样（但作用域受限账户的聊天轮次会改为停止，因为其对话已被关闭）；等待中的工具审批会被拒绝；已关闭套接字在此之后发送的任何内容都不会被执行。页面重新加载也会关闭会话所打开的套接字，仪表板会在新配置下重新连接它们。若请求仍到达了正在被替换的网关代际，且所用连接保持打开，则会返回 503 与 "reason": "gateway_restarting"，仪表板会重试该请求。

会话保存在内存中，会话结束时其令牌会被清除。过期会话每分钟清理一次，即使没有任何请求到达也是如此。守护进程重启会使所有用户退出登录，而重新加载则会保留会话，并在下次使用前依据新配置对每个会话重新验证。同时最多保存 256 个会话，每个账户最多 8 个。达到上限时，新的登录会被拒绝，而不会把其他人挤出登录状态。

在启用之前，需要了解以下事项：

  • 配对功能可与登录并行使用；当身份提供方无法访问时，配对仍是重新进入的途径。桌面应用继续使用配对方式。
  • 管理员可以像普通操作员一样，从仪表板配对设备。在身份提供方移除其访问权限并不会撤销其已配对的设备；请在配对页面撤销这些设备。
  • 对于登录前创建的对话和记忆，归共享操作员所有。没有 admin 权限的账户永远看不到这些内容。
  • 在网关所在的机器上通过纯 HTTP 访问时，浏览器不会按端口隔离 Cookie，因此浏览器访问的其他本地 Web 服务器也会收到会话 Cookie。请使用 HTTPS，或仅在不用于其他本地开发服务器的浏览器中登录。
  • 将提供方从 gateway.dashboard_sign_in.oidc 中移除或清空，会终止其签发的会话：在下一次请求时终止；若一分钟内没有任何请求，则在一分钟内终止（若重新加载使变更生效，则立即终止）。重新添加该提供方不会恢复这些会话，但若在一分钟内重新添加且期间没有任何请求，则例外。若 [oidc.<alias>] 条目改为指向其他颁发方或客户端，其会话同样会被终止，且其令牌不会被发送至新的提供方。
  • session_lifetime_secs 会限制在其设置之后开始的会话；已登录的会话保留其开始时的上限。若要更快结束这些会话，请将该提供方从 gateway.dashboard_sign_in.oidc 中移除。
  • 当身份提供方在会话令牌被再次验证时无法访问，或返回错误，该会话会被终止（故障关闭，fail closed）。这会在每个内省重新验证截止时间发生；在任一验证模式下，只要配置重新加载，或 OIDC、用户或权限配置文件发生变更，也会发生。仪表盘会将该会话显示为已过期，待提供方恢复后，用户需重新登录（#12096）。

凭据生命周期

  • 过期会在截止时间结束连接的授权；客户端需使用新的令牌重新初始化。
  • 内省重新验证：OIDC 内省身份带有重新验证截止时间；超过该时间后，下一次操作会被拒绝，直到客户端重新初始化（重新初始化会与 IdP 重新核验）。
  • 配对撤销会在该连接的下一次操作之前生效。
  • 日志订阅：已打开的 logs/subscribe 或 events/subscribe 流会在每次推送时重新校验，并在其凭据过期、配对被撤销，或其主体失去 Logs:Read 或管理员权限后的第一次推送时结束。
  • 策略变更：保存配置时，若 [oidc]、[users]、[permission_profiles] 和 security.trust_daemon_uid 保持不变，则所有绑定保持原样。对其中任一项的修改都会发布新策略。原生令牌连接和本地连接会就地依据新策略重新解析，但守护进程不保存 OIDC 承载令牌，因此在客户端重新初始化之前，OIDC 连接的下一次操作会被拒绝。
  • tui_id/tui_sig 重连机制仅用于保持连续性：它保留 TUI 的注册表身份，但不授予任何权限。每次 initialize 都需要重新提交凭证。

会话隔离

每个由受限主体创建的会话，都会在运行时存储和磁盘上（聊天后端与 ACP 存储）标记该主体的 ID。受限主体只能看到和操作自己的会话：列表结果会被过滤；读取和修改操作统一返回“未找到或无所有权“的拒绝响应，不会探测会话是否存在；破坏性删除通过以所有者为条件的存储语句执行；进行中的审批请求仅能由其所属会话的所有者处理。此次变更之前创建的会话（或由非受限连接创建的会话）没有所有者：它们对非受限连接保持完全可见，对受限主体则不可见。

每个已认证的主体都获得 PRIVATE 记忆：其记忆操作读写一个按主体划分的 plane，该 plane 的所有者（owner）会出现在每条存储语句中，并与 agent、namespace 和 tenant 维度组合（同一个 key 在两个 agent 下对应两行记录）。plane 跟随主体的身份，而非管理员旁路：具名管理员的记忆就是其自身的私有 plane，因此提升或降级用户都不会隐藏其笔记，也不会改变其写入的目标。只有未认证的共享操作员默认位于共享 plane 上；持有管理员旁路的调用方可以在 memory/* 请求上显式指定 plane = "shared"，此操作会被审计，而受限范围（scoped）的主体则不能这样做。

两个平面在两个方向上都互不干扰：共享写入既不能指定私有行的存储键，也不能覆盖私有行；私有写入不会转换共享行；普通导出和 markdown 快照只包含共享行；旧版批量清除也只作用于共享行。私有行则通过携带所有者信息的操作进行导出和清除。

会话由某个主体（principal）创建时，其内存句柄会在该会话的整个生命周期内绑定到该主体的私有平面，无论之后由谁发起提示。管理员恢复已回收的会话时，同样会在持久所有者的平面上恢复。因此，作用域会话中的内存工具和每轮召回从不访问共享平面。不存在任何授权可以向作用域会话开放共享平面。私有写入与共享写入经过相同的内容扫描和策略检查。启用内存审计后，私有操作会连同完整作用域一并记录审计日志。在尚不支持主体的内存后端（目前包括 markdown、lucid、postgres 和 qdrant）上，私有内存会以明确的拒绝信息失败关闭，而不会静默地取消作用域。对于作用域会话而言，这意味着其内存工具会拒绝执行。

从 [security.nevis] 迁移

Nevis IAM 集成已被移除。它从未接入任何身份验证路径，因此启用它从未对任何人进行过身份验证；移除它不会改变任何实际运行行为。[security.nevis] 不再是配置键：Schema V4 已将其废弃。只要配置中仍保留该表，每个命令都会输出一条警告并指出该表，且其中的任何值都不会被加载。该表会通过 zeroclaw config migrate 从 config.toml 中移除，也会在编辑之后的下一次保存时移除，无论是完整保存，还是 CLI、仪表盘和 RPC 用于单次编辑的增量保存。增量保存仅在有内容被编辑时才会执行，因此未经修改的配置会保留该表，直到发生上述任一操作为止。移除操作仅影响该表；注释和其他章节保持其原有字节内容不变。不会自动转换任何内容：替代方案所需的值（受众、配置文件授权）是旧表从未包含的。

ZeroClaw 会保留原始文件的两份副本。 首次有任何操作重写 V3 文件时（zeroclaw config migrate，或者 CLI、仪表板、RPC 或快速入门中的首次保存），它会将文件复制为 config.toml.v3.backup。该副本仅限当前用户读取，且不会被替换，是回退到旧版 ZeroClaw 的依据。config migrate 还会写入 config.toml.backup，下一次迁移时会被替换。两份副本都保留已废弃的表，包括其中的明文 client_secret。每次保存时，都会在写入期间生成 config.toml.bak，并在写入持久化后删除它，因此 .bak 不是备份。

升级后，请将 config.toml.v3.backup、config.toml.backup 以及您自行保存的任何副本视为机密材料。在不再需要降级时将其删除，并在身份提供方（IdP）处吊销 Nevis 客户端凭据。

这一层目前不做的事情（暂未实现）

整合与治理会派生共享平面的行，且不会为私有会话运行。对另一主体私有记忆的管理员访问尚无可用路径（默认拒绝）。会话数据工具尚无感知主体的视图，因此对不具备 admin 的主体予以隐藏（参见 权限配置文件），而不是限定为调用方自己的会话。定时代理任务、SOP 运行和对等轮次在代理的风险配置文件未排除这些工具时，仍可调用它们。持有 Sops:Read 的主体可通过 sops/runs 和 sops/run-detail 查看所有流程的运行历史，无论其以哪个代理运行，这与 cron 历史不同。配置分组之外的网关 HTTP 路由保留其现有的配对检查，仪表板登录仅对管理员满足这些检查；渠道身份尚未映射到此主体模型中。

当 security.trust_daemon_uid = true（默认值）且策略编译通过时，守护进程自身的 uid 在 Unix 套接字上保留完全访问权限。因此，对于没有 [users] 名单、认证配置段有效的单操作员安装，其行为与之前保持一致。

权限配置文件用于限制主体通过 RPC 可以执行的操作，但它们并不能隔离主体促使智能体运行的代码。会话轮次、定时任务和 SOP 步骤均以守护进程账户身份运行。在 Unix 上，这些代码可以以守护进程的 uid 连接本地套接字：当 security.trust_daemon_uid = true（默认值）时，该 uid 即为共享操作员；否则，它将获得映射到该 uid 的名册条目所拥有的权限。在没有名册的 Windows 上，命名管道会使其成为共享操作员。这些代码还可以编辑 config.toml，守护进程会在下一次重新加载或重启时应用这些修改。设置 security.trust_daemon_uid = false 并不会改变这两种情况。仅将会话、定时任务或 SOP 的执行或编写权限授予您愿意赋予操作员访问权限的主体。只有能够使智能体进程无法访问套接字和 config.toml 的操作系统级约束，才能隔离这些代码。

有些配置路径本身就带有权限，因此除非 config_write_paths 的授权仅涵盖经过审核的叶子配置项，否则应将其宽泛授权视为运维人员访问权限。例如：

  • 一个能够写入 permission_profiles、users、oidc、security 或 gateway.paired_tokens 的主体可以授予自己任何权限;
  • 一个能够写入 agents、risk_profiles、cron、channels 或 provider 设置的主体，可以改变哪些 agent 运行、使用哪些工具，以及它们可以读写的位置；
  • 能够写入 mcp、mcp_bundles 或 tunnel.custom.start_command 的用户，可以选择由守护进程账户启动的程序。

Config:Update 还会授予 config/reload,它会应用磁盘上 config.toml 中的当前内容。

zerocode 的远程目录选择器会在守护进程的文件系统根目录处打开。没有运营方授权的主体，只有通过策略允许读取 / 的已启用代理（例如非仅限工作区的代理）才能列出该目录。对于其他此类主体，选择器会在该位置报告拒绝访问，直到其在允许的根目录内打开为止。

Keycloak 访问令牌客户端归属

JWKS 验证在以下情况下接受已签名的 azp 作为 OAuth 客户端标识符：类型化访问令牌没有 client_id，且已配置的客户端声明或 actor_claim 能够确定人类actor。签发者、签名、令牌用途、受众、有效期以及 actor 分类检查仍然适用。仅包含 azp 的令牌无法对服务进行身份验证，包括通过 actor_claim 分类的服务；服务 actor 仍需要 client_id。client_id 为空、client_id 与 azp 相互矛盾，或客户端既没有声明也没有已配置的 actor-claim 证据时，都会失败关闭。内省仍然要求其响应字段中包含 client_id。
