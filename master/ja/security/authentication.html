認証とプリンシパル

すべての RPC 接続は initialize ハンドシェイク中に プリンシパル をバインドし、各メソッド呼び出しは、現在の設定がそのプリンシパルに付与している権限と照合されます。このページでは、プロバイダーセット、ローカルユーザーの一覧、パーミッションプロファイル、そして最も重要な既存のリモート接続に生じる変更点について説明します。

1パスでのモデル

  1. provider は認証情報を 1 つ検証します。ハンドシェイクで明示的な auth_token が指定されると、auth_provider で指定された provider（既定値は native、ゲートウェイのペアリングトークン）が選択されます。トークンがない場合、ローカルの Unix ソケットはカーネルのピア uid を peercred provider に提示します。選択された provider による拒否は最終的なものであり、認証情報が別の provider で再試行されることはありません。

  2. 共有リゾルバーは、検証済みの ID を正規のプリンシパル ID と、設定によってその ID に割り当てられたパーミッションプロファイルへ対応付けます。OIDC の ID は、検証済みの issuer と subject の組で識別され、ローカルのロスター ID は、永続的な [users.<name>] のプリンシパル ID で識別されます。

  3. RPCメソッドのうち、2つのハンドシェイクメソッドを除くすべては、必要なリソース動詞の権限に分類され、その権限がなければ拒否されます。initializeは認証情報そのものを伴い、cert/renewは、プリンシパルではなく、それを提示する相互TLSクライアント証明書によって認証されます。きめ細かなセレクタは、この上に組み合わさって適用されます:

    • config writes check config_write_paths;
    • session/new と session/prompt は、エージェントのセレクタを確認し、そのエージェントのポリシーで読み取りと書き込みの両方が許可されたディレクトリにセッションのワークスペースを限定します。これはワークスペースがリクエストで指定された場合、再開されたセッションに保存されていた場合、永続セッションから復元された場合のいずれにも適用されます。セッションは要求されたパスの表記ではなく、解決後のディレクトリに紐付けられるため、許可後にシンボリックリンクされた cwd の参照先を変更してもセッションは移動しません。また、そのようなエイリアス経由で保持されているライブセッションは拒否されます。他のセッションメソッドは、What this layer does not do (yet) で説明されているとおり、まだエージェントをチェックしません;
    • SOP を実行または承認するには管理者権限が必要です。作成、保存、削除には、その SOP が実行されるエージェントの権限が必要です。ステップにもプロシージャにもエージェントが指定されていない場合、そのステップは設定済みのエージェントエイリアスのうちソート順で最初のものとみなされ、これがヘッドレス実行器がフォールバックするエージェントになります。決定的なプロシージャのステップを含め、すべてのステップが対象です。
    • 添付ファイル、パーソナリティファイル、エージェントを指定するコスト照会、cron ジョブは、いずれもエージェントセレクターを確認します。ローカルパスで送信される添付ファイルは、宛先エージェントのポリシーで読み取りが許可されている絶対パスも指定しなければなりません。フリートのコスト概要は、エージェント別の内訳にはプリンシパルのエージェントのみを表示しますが、その合計値とモデル別の使用量は引き続きすべてのエージェントを対象とします;
    • デーモン全体のログおよびイベントの読み取り（logs/subscribe、events/subscribe、events/history、logs/query、logs/get）は、管理者と共有オペレーターにのみ提供されます。これらのレコードはすべてのプリンシパルの作業から生成され、他のプリンシパルの認可拒否も含まれ、多くは所有者を特定しないため、スコープ付きプリンシパルは Logs:Read と * エージェントセレクターを持っていても拒否されます。
    • fs/list_dir は、呼び出し元のプリンシパルが利用できる有効なエージェントのポリシーで、そのエージェントに読み取りが許可されている絶対パスのみを一覧表示します。相対パス、.. コンポーネント、そして Windows では、ネットワークパスおよびデバイスパスを拒否します。 これらのルートは、各エージェントの解決済みポリシーに由来します。ポリシーには、そのリスクプロファイル、workspace.access が読み取りアクセス（セッションワークスペースの場合は読み取りと書き込み）を付与する兄弟ワークスペース、そして読み取り専用の共有スキルディレクトリが含まれます。ワークスペース限定ではないエージェント（自律性が full のもの、workspace_only = false を持つリスクプロファイル、yolo プリセット、または workspace.unrestricted_filesystem = true のもの）は、禁止パス以外の任意のパスを読み取れます。そのため、そのようなエージェントを利用できるプリンシパルは、そのエージェントが到達できる任意の場所にあるセッションを一覧表示したり開いたりできます。

    session/new と session/prompt は、セッションのキューで待機した後にこれらのチェックを再度実行します。そのため、主体が権限を縮小される前、または認証情報が期限切れになる前にキューへ入ったリクエストは、順番が来た時点で拒否されます。

認可は、デーモンのRPC設定メソッド（zerocodeの設定エディタで使用）と、デーモンが管理するゲートウェイの設定API（Webダッシュボードで使用）を経由した編集について、即時反映されます。両者は、デーモン世代のライブ設定、設定書き込みロック、および受理済みの認可権限を共有します。どちらの経路でも [permission_profiles]、[users]、[oidc]、または security.trust_daemon_uid を編集すると、保存時にポリシーがコンパイルされて公開され、書き込みが成功を返す前に完了します。既存のネイティブトークン接続およびローカル接続は、次の操作時に再解決されます。再接続やリスタートは不要です。OIDC接続は再度初期化する必要があります。ダッシュボードの保留中リロードフラグは、再構築が必要なデーモン管理のサブシステムを引き続き対象とします。ただし、この認可の公開を遅らせることはありません。

デーモン外で行われた編集（config.toml を直接編集する場合、または zeroclaw config set を使用する場合）は、次回のデーモンのリロードまたは再起動時に適用されます。これらの認可に関するCLIの書き込みはディスクに保存されますが、実行中のデーモンへの公開やリロードのトリガーは行われません。

ゲートウェイのペアリング管理機能を通じてゲートウェイのペアリングトークンを失効させると、そのトークンで認証された接続は、次の操作の前に無効になります。gateway.paired_tokens からトークンを削除する場合、設定の編集（RPC経由またはディスク上での編集）では、実行中のデーモンには影響せず、そのトークンを使用している接続は認可されたままです。この削除は、次回のデーモンのリロードまたは再起動時に適用されます。ただし、それまでにゲートウェイ経由で行われたペアリング変更により、そのトークンを含む現在のライブトークンセットが設定に書き戻された場合は除きます。トークンの失効は、必ずペアリング管理機能を通じて行ってください。

ローカル接続

Unixソケット上で、トークンを提示しない接続は、カーネルが報告するピアのuidによって識別されます。security.trust_daemon_uid が true（デフォルト）の間は、デーモンの自身のuidによる接続が、[users] の名簿の有無にかかわらず、信頼された共有オペレーターとしてフルアクセスで扱われます。そのため、名簿のないインストールでも、デーモンを実行しているアカウントについては従来どおりに動作します。

デーモンを実行するオペレーターは設定ファイルを所有しており、ローカルのみでのロックアウト復旧はこの権限に依存しています。Unix ソケットでは、security.trust_daemon_uid を false に設定すると、デーモン自身の UID を含むすべてのローカルピアが、ロスターを経由するか、トークンを提示する必要があります。この設定は、後述する Windows 名前付きパイプには効果がありません。

他の uid はすべて、明示的な [users.<name>].uid エントリによって対応付けられている必要があります。対応付けられていない uid（root を含む）がトークンを提示しない場合、ロスターの有無にかかわらずアクセスは拒否されます。共有オペレーターアクセスへのフォールバックはありません。リスナーはソケットを所有者専用として作成するため、現時点では、デーモン自身のアカウントと root だけがソケットに到達できます。ロスターのエントリは、他の uid が到達できるようになった後に何を行えるかを決定します。

Windowsの名前付きパイプはpeer uidを伝送しません。ロスターが存在しない場合は、パイプのACLが認証情報となり、ローカル接続は共有オペレーターとして扱われます。[users] ロスターが存在すると、ローカルクライアントはトークンを提示する必要があり、security.trust_daemon_uid は効果を持たず、デーモン自身のアカウントには信頼されたローカル経路がありません。ポリシーのコンパイル中も、ペアリング済みのゲートウェイトークンは共有オペレーターとして認証されるため、それを送信するクライアントは、WSS経由でもパイプ経由でも、ロスターをライブで修復できます。zerocodeのローカルパイプ接続はトークンを送信しないため、そのようなクライアントがない場合、ロックアウトはconfig.tomlを編集して再起動することで修復されます。

クライアントは initialize でシェル環境を転送できます。これにより、デーモンのサブプロセスがクライアントの PATH と認証情報ソケットを参照できます（環境変数の受け渡しを参照）。このスナップショットは、ローカル接続上のオペレーターレベルのプリンシパル（共有オペレーター、または admin = true が設定されたロースターのプリンシパル）に対してのみ保持されます。それ以外のプリンシパルおよびすべてのリモート接続には、代わりにデーモン自身の環境が提供されます。

セッションの作成または復元時に、資格が再度確認されます。転送された環境が空でないものを保持している既存のセッションは、現在認可されているローカルオペレーターだけが再開またはプロンプトを送信できます。WSS 経由で再接続した場合や、プロンプトのキュー待ち中に admin を失った場合、その環境は次のターンに引き継がれず、リクエストは実行前に拒否されます。転送された環境なしで続行するには、新しいセッションを作成してください。転送された値を持たないセッションは、他の認可チェックの対象となりますが、通常どおり再開できます。保持された環境は、そのセッションの存続期間中は変更できません。後続のリクエストを拒否しても、実行中のターンの下で保持された環境が書き換えられることはありません。再開には、現在の接続で認可された環境が、セッションの保持された環境と一致することも必要です。一致しない場合は、新しいセッションを作成してください。環境を持たないセッションは、admin が削除された後でも再開できます。

リカバリー

リモート認証のバイパスは提供されません。リモート接続では、必ず有効な認証情報を提示する必要があります。認可ポリシーがまだコンパイルできる間は、ペアリング済みのゲートウェイトークンまたはoperatorレベルのプリンシパルを保持するクライアントであれば、どこからでもロックアウトを修復できます。そのような認証情報がない場合、また deny-all 状態にある場合は、復旧経路は常にデーモンを実行しているホスト上で行われます。どのローカル経路が適用されるかは、ポリシーがまだコンパイルできるかどうかによって決まります。

ポリシーがコンパイルできず、ロックアウトされています。 認可は有効で、ローカルの信頼済みパスは Unix ソケット上で維持されています。Windows の場合は、上記の名前付きパスに関する注記を参照してください。デーモン自身の uid としてローカル接続してください。security.trust_daemon_uid = true（デフォルト）の場合、そのアカウントはロスターの内容に関係なく、信頼された共有オペレーターとして扱われます。その口経由で問題のあるエントリを修復できます。例えば zerocode の設定エディタで行うか、RPC の config/set で users.alice.uid を指定します。変更は保存時点でコンパイルされ、公開されます。config.toml を編集する、または zeroclaw config set を実行しても修復できますが、その場合はデーモンが設定を再読み込みするか再起動された後にのみ反映されます。

deny-all の承認済み状態によりロックアウトされています。 ポリシーがコンパイルされなかったため、承認済み状態は解決処理の前にすべてのプリンシパルを拒否します。デーモン自身の uid と共有オペレーターも含まれます。どの RPC でも修復できません。config/set と config/reload も、他のすべてと同様に拒否されます。所有者として config.toml を直接編集し、その後デーモンを再起動して、修復したセクションがコンパイル・公開されるようにしてください。デーモンは SIGHUP を無視するため、再読み込みには再起動が必要です。

security.trust_daemon_uid を false に設定すると、信頼された UID によるルートは無効になります。コンパイルは通るものの不適切なポリシーは、ペアリング済みのゲートウェイトークンを提示するクライアント、または管理者権限を持つ名簿上のプリンシパルによってライブで修復できます。それ以外の場合、どちらの状態でも修復方法は同じです。config.toml をその所有者として編集し、再起動してください。この設定をオフにするのは、それが許容できる場合に限ってください。

OIDC

ID プロバイダーには、ZeroClaw でテスト済みのプロバイダー、各プロバイダーの要件、および現在の制限事項が記載されています。

各[oidc.<alias>]エントリは、1つの発行者(issuer)との間の1つの信頼関係を表します。トークンの検証(オフラインのJWKSまたはRFC 7662のイントロスペクション)、クレームマッピング、有効期間の上限については、セクションリファレンスに記載されています:

actor_claim string · default ""

発行者が、いずれか一方のアクター種別のトークンにのみ付与するクレーム（存在し、null でないもの）へのドット区切りのパス。例：client-credentials トークンに付与される Auth0 の gty、またはユーザートークンに付与される Okta の uid。actor_claim_marks は、そのクレームが存在することで証明されるアクター種別を指定します。存在しない場合は、もう一方の種別が証明されます。人間向けトークンと機械向けトークンの両方を発行し、どちらのクライアントリストにも宣言されていないクライアントには必須です。宣言済みのクライアントに対しても検証され、矛盾する証拠がある場合は拒否されます。空の場合はクレームによる分類を行わないため、受け入れるすべてのクライアントを宣言する必要があります。

登録中（提示用のトークンを取得中）

デーモンはトークンを検証するだけで、クライアントはトークンを IdP から取得します。CLI には、ブラウザを使用しない 2 つのフローが同梱されています:

# Device Authorization Grant（RFC 8628）を使ったインタラクティブなサインイン:
# prints a verification code to enter in any browser, waits for
# 承認後、アクセストークンを標準出力に書き込みます。
export ZEROCLAW_AUTH_TOKEN="$(zeroclaw oidc login corp)"

# 同じ方法をシステムブラウザ経由で実行: 認可コード + PKCE（S256のみ）
# with an RFC 8252 one-shot loopback listener. The mechanisms never
# 互いに逆戻りしてしまう。
export ZEROCLAW_AUTH_TOKEN="$(zeroclaw oidc login corp --browser)"

# ヘッドレスサービスプリンシパルの client_credentials 方式（要件：
# entryの client_secret):
export ZEROCLAW_AUTH_TOKEN="$(zeroclaw oidc token corp)"

進捗メッセージは標準エラー出力に出力され、標準出力にはトークンのみが出力されるため、どちらのコマンドもコマンド置換と組み合わせて使えます(oidc コマンドは、出力を行う可能性のある起動時の前処理より前に実行されます。OTPシードの開示も含みます)。トークンは保存されません。期限切れになる前に、RPCハンドシェイクで(または環境変数経由で)auth_token として提示し、その後で再登録してください。

クライアントは、エントリに記載された issuer のみを信頼し、それ以外は信頼しません。ディスカバリドキュメントは、そのissuerを正確に示している必要があり、広告されたエンドポイントは、その確認後にのみ使用されます。資格情報を受け取るすべてのエンドポイントは、issuerと同じURLポリシーを満たす必要があります（https、または完全一致するループバックホストに対してのみhttp）。リダイレクトは一切追従されず、レスポンスボディにはサイズ上限が設けられています。トークンレスポンスは、空でない Bearer アクセストークンを含む場合にのみ受け入れられます。機密クライアント（client_secret を持つエントリ）は、デバイスグラントおよび client_credentials リクエストにおいて HTTP Basic で認証します。認可コード交換では、フォームボディにシークレットを含めて送信します（--browser、ゲートウェイのブラウザフロー、およびダッシュボードのサインイン）。パブリッククライアントは、フォーム内に client_id を送信します。

--browser は macOS と Linux ではシステムのブラウザを自動で開き、すべてのプラットフォームでサインイン URL も表示します。そのため、CLI を実行しているのと同じマシン上のブラウザで手動に開くこともできます（コールバックは CLI を実行しているホストのループバックポートに届きます）。ブラウザ起動ツールは CLI の標準入出力から切り離された状態で実行されるため、起動ツールが自身の stdout に出力した内容が結果を汚染することはありません。stdout に出力されるのはトークンのみです。

両方のコールバックアダプター（CLI のループバックリスナーとゲートウェイのコールバック）は、RFC 9207 の issuer チェックを強制します。iss パラメーターがフローを開始した issuer と一致しないレスポンスは、その code や error が処理される前に拒否されます。iss を含まないレスポンスは、このパラメーターが任意であり、すべての issuer がこれを送信するわけではないため、受け入れられます。コードの交換でアクセストークンと一緒に id_token が返される場合、その id_token は（issuer、audience、有効期限、このフローに紐づく nonce）をすべて検証された後、破棄されます。デーモンに提示されるのはアクセストークンのみです。エンロールメントクライアントは、ディスカバリー自体にも同様の警戒を適用します。設定された issuer と完全一致しない issuer（末尾のスラッシュを含む）を持つ .well-known/openid-configuration ドキュメントは、そこに記載されたいかなるエンドポイントも使用する前に拒否されます（RFC 8414 のチェック）。また、読み取るドキュメントのサイズには上限を設けています。これにより、悪意のある、あるいは壊れた issuer がフローを任意のエンドポイントへ誘導したり、上限のないボディを返したりすることはできません。

IdP の認証情報を持たないクライアント(Web ダッシュボードや zerocode)は、代わりにゲートウェイ経由で登録します。ゲートウェイは、設定済みエントリのクライアント認証情報を使って同じフローを中継します。GET /api/oidc/providers でエイリアスを一覧取得し、POST /api/oidc/{alias}/device/start と /device/poll でデバイスグラントを実行し、GET /oidc/login/{alias} でブラウザフローを実行します。このブラウザフローのワンタイムコールバックページは、postMessage(同一オリジンのみ)でトークンを開いたウィンドウに渡し、手動コピーをフォールバックとして用意しています。また、ゲートウェイは Cross-Origin-Opener-Policy: same-origin を送信するため、ポップアップが ID プロバイダーを経由して遷移すると window.opener が切断されます。そのため、現在のブラウザではこのページの手動コピーが実際に機能する引き渡し方法です。ダッシュボード自体はこのページを使用しません。ダッシュボードのサインインでは、トークンはセッション Cookie の背後にあるゲートウェイに保持されます(ダッシュボードのサインインを参照)。これらのルートは、登録が認証より前に行われるため認証不要で、レート制限が適用されます。また、何も付与せず、ユーザーが承認した後に IdP が付与したものを中継するだけです。設計の根拠と障害モードの一覧は、リポジトリ内の docs/security/oidc-browser-pkce-design-8289.md にあります。

ゲートウェイのブラウザフローでは、フローを開始したブラウザから送られる、有効期間の短い HttpOnly バインディング Cookie も必要です。この Cookie によってセッションや API へのアクセスが許可されることはありません。対応する Cookie のないコールバックは、コード交換の前に拒否され、保留中のフローを消費します。コールバック URL をブラウザ間で転送するのではなく、目的のブラウザで新しいログインを開始してください。タブごとに独自のフロー Cookie があります。リレー容量の上限による拒否の場合、元の10分間の期限内で再試行できるよう、有効なフローと Cookie は保持されます。

バインディング Cookie は、ID プロバイダーからのトップレベル GET リダイレクトのために SameSite=Lax を使用します。Domain 属性を持たず、ゲートウェイのパスプレフィックス配下でも Path=/ を使用します。HTTPS では Secure と __Host- の名前プレフィックスも使用します。リモートの登録ページは HTTPS 経由で公開します。平文 HTTP では Cookie のスコープが同じホスト上の複数のポートにまたがるため、同じホスト上で動作する別のアプリケーションからは分離されません。Cookie がブロックされるとブラウザーでの登録はできませんが、デバイスフローは引き続き利用できます。

レート制限は階層的に動作します。フローを開始するリクエスト（POST /api/oidc/{alias}/device/start、GET /oidc/login/{alias}、GET /oidc/callback）は、ゲートウェイのブルートフォース対策リミッターのうち、エンロールメント専用のインスタンスにカウントされます。これは不正なペアリングトークンに適用されるものと同じしきい値と同じロックアウトですが、独立した台帳で管理されます。そのため、エンロールメントからロックアウトされたアドレスでもペアリングや Webhook 署名の提示は可能であり、ペアリングや署名検証で発生したロックアウトがエンロールメントをブロックすることもありません。コールバックは、非生産的な場合にのみ試行としてカウントされます。具体的には、state に対応する有効なフロー状態が存在しない場合、issuer が一致しない場合、IdP からエラーが返された場合、認可コードがない場合、フローの途中でエイリアスが削除された場合、またはコード交換が失敗した場合です。サインインを完了させるコールバックはコストがかからず、ゲートウェイがリレー容量の使用中を理由に拒否したコールバックもカウントされません。これにより、同時にサインインする多数のユーザーが共有アドレスからロックアウトされることを防ぎます。ペンディングフローストアが満杯のために拒否されたブラウザサインインも、同じ理由で呼び出し元のコストにはなりません。プロバイダー一覧、デバイスポーリング、サインイン開始には、クライアントごとに1分あたり20リクエストの予算が適用されます。これは RFC 8628 が定める最小ポーリング間隔5秒（1分あたり12回のポーリング）に対して余裕を持たせつつ、クライアントが過剰にリクエストを連打できないようにするものです。IdP が slow_down を返した場合、またはデバイスコードを明示的に拒否した場合、そのポーリングは試行としてカウントされます。これにより、デバイスコードを無意味に中継するクライアントは既存のロックアウトに到達し、無限にポーリングし続けることができなくなります。ゲートウェイ自身と IdP の間のトランスポート障害は呼び出し元に起因しないため、呼び出し元には課金されません。クライアントが予算を超過した場合、またはロックアウトされている場合、HTTP 429 が返され、遅延秒数を示す Retry-After が付与されます。zerocode は次のポーリングまでに、この遅延以上、かつ RFC の5秒増分以上待機します（ただし、デバイスコードの残り有効期間を上限とします）。いかなる場合でも、5秒に1回より頻繁にポーリングすることはありません。全クライアントを通じて、IdP への同時送信リレーは最大16件に制限されます。これにより、ゲートウェイが全クライアントの代理として IdP に対して行う負荷に上限が設けられます。ペンディングフローストアは同時に32件のブラウザサインインを保持でき、リモートクライアント1つが保持できるのは最大8件です。そのため、サインインを開始したまま完了させないクライアントが、フローが存続する10分間ストアを独占し、他のすべてのユーザーを締め出すことはできません。ループバッククライアントは、他のゲートウェイ認証制限と同様に、クライアントごとの予算から除外されます。そのため、同一ホスト上にあるリバースプロキシでは、背後にいる実際の呼び出し元にクライアントごとの制限を適用するために trust_forwarded_headers を有効にする必要があります。この設定が有効な場合、ゲートウェイは X-Forwarded-For の最右端のアドレス（直前のプロキシが追加したホップ）を使用します。該当するものがなければ X-Real-IP を使用します。プロキシは、クライアントから送信されたリストをそのまま転送するのではなく、追記または上書きするように設定してください。例として、nginx では proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; を使用します。X-Real-IP のみを設定する場合は、優先度の高いリストをクリアするために proxy_set_header X-Forwarded-For ""; を proxy_set_header X-Real-IP $remote_addr; と併用してください。そうしないと、クライアントから送られた X-Forwarded-For が優先されてしまいます。転送されたループバックアドレスはスキップされるため、ローカル専用リミッターの除外措置を不正に取得することはできません。チェーン全体がループバックのみの場合、ゲートウェイはループバックのピアアドレスではなく、除外されないキーを使用します。すべてのエンロールメントレスポンスには、ゲートウェイの no-referrer ポリシーに加えて Cache-Control: no-store と Pragma: no-cache が付与されます。これは、デバイスコードやアクセストークンがこれらのレスポンスボディで送信されるためです。

zerocode は、独自の設定を使って同じ API 経由で登録（enroll）を行います。[connection.wss] enroll_url はゲートウェイの HTTP オリジンを指定し、任意でパスプレフィックスを付けられます。ループバックアドレス（127.0.0.1、::1、localhost）を指している場合を除き、https:// である必要があります。デバイスコード、そしてその後のアクセストークンがこの経路を流れるうえ、リダイレクトは追従されないため、事後に平文の経路を差し込むことはできないからです。

登録用の接続は、WSS 経路と同じ [connection.wss.tls] の信頼情報を使用します。すなわち、設定された CA、skip_verify、および相互 TLS のクライアント証明書です。この信頼情報によって証明書の検証が行われない場合、zerocode はトークンを受け取った後ではなく、デバイスコードを送信する前に確認を求めます。確認の対象は登録オリジン自体であり、これは後でセッションが接続するデーモンとは異なる可能性があります。always と回答すると、そのオリジンが skip_verify_routes に記録されます。非対話型の実行では確認する相手がいないため、登録はそこで停止します。

zerocode は、ポーリングの待機時間をすべてデバイスコードの残りの有効期間に制限し、期限切れ後はポーリングしません。有効期間が 1 時間を超える場合、またはポーリング間隔が 5 分を超える場合は、攻撃者が制御しうる応答でスリープしないよう、拒否します。アドバタイズされた間隔が 0 または 1 の場合は、RFC 8628 の既定値である 5 秒に切り上げられます。これにより、ゲートウェイの応答によって zerocode が 1 秒ごとのポーリングに陥ることはなく、クライアントごとの予算によって拒否されることもありません。

従来の自動登録経路は、トークンをそのセッションの間だけメモリ上に保持します。この経路は zerocode login と同じデバイスグラントヘルパーを使用するため、S256 の PKCE チャレンジも送信します。したがって、デバイス認可エンドポイントで code_challenge を拒否するプロバイダーでは、ここでも失敗します。

URL 単位で永続的なログインを行うには、zerocode login <alias> <wss-url> --gateway-url <https-origin> を使用します。詳細は リモート設定 を参照してください。このコマンドは空のクライアントディレクトリから開始します。OIDC サインインにより、ゲートウェイを通じて最初のデバイス証明書の発行が承認されるため、事前に作成されたデバイス、ローカルユーザー、デーモンのペアリングコード、SAS、個別の登録リスナーは不要です。デーモンは、RPC と同じ受け入れ済みの OIDC ポリシーでベアラートークンを検証し、sessions:create と許可されたエージェントを持つ人間（または system:execute / 管理者）であることを要求します。その上で、CSR の公開鍵のみに署名し、新しいデバイスを既存の証明書台帳と監査証跡に記録します。静的なクライアント証明書のピン留めは、依然として帯域外でのプロビジョニングが必要です。WSS は、すべての initialize で依然として相互 TLS と有効な OIDC アクセストークンの両方を要求します。このコマンドは、受け入れられたアクセストークンを所有者のみが読み書きできるローカルの zerocode-config.toml に保存し、起動時に新しいトークンが必要になると再認証します。

プロファイルはデフォルト拒否です。リストにないリソースは拒否され、空のセレクターリストはインスタンスを一切許可せず、広範なアクセスには明示的な "*" セレクターまたは admin = true が必要です。複数のプロファイルは和集合でマージされます。cronジョブ、添付ファイル、パーソナリティファイル、エージェントごとのコスト照会、SOP作成では、allowed_agents = ["*"] は設定で定義されたエージェントのみを対象とし、リクエストで指定されたエイリアスは対象になりません。

ツールセレクタは、エージェントの組み立て時に、粗い粒度の権限付与の上で積集合として合成されます。モデルから利用するツール実行は tools = ["execute"] です。この権限を持たないプリンシパルは、allowed_tools に何が指定されていても（"*" を含む）、ツールのないセッションを受け取ります。この権限を保持している場合、制約付きプリンシパルが作成したセッションは、allowed_tools で指定されたツールのみを受け取ります（空のリストの場合はツールのないセッションになります）。これはエージェント自身のリスクプロファイルで許可されている範囲の上で適用されます。キューに入ったプロンプトが受理された後、認証情報の有効期限や失効を含めて、共有リゾルバーに対して認可が再チェックされます。現在のプリンシパルのセレクタは、静的ツール、遅延検索レジストリ、既にアクティブ化されたツール、およびピン留めされた MCP リソースコンテンツを絞り込みます。各ピン留めブロックは <server>__<uri> という名前で受理され、セレクタがその名前を指定しなくなると後続のプロンプトから取り除かれます。削除されたツールは再アクティブ化できません。再利用されたセッションは次のターンの前に絞り込まれ、再水和されたセッションは現在の権限で再構築されます。エージェントのセレクタは、ターンの前と再水和の前にチェックされます。

絞り込みによって既存のエージェントにツールが戻されることはありません。権限付与を拡大した後は、拡大されたツールの範囲を受け取るために新しいセッションを作成してください。エージェントには、新しい設定スナップショットや独立したプリンシパルポリシーのキャッシュは保存されません。

Deferred MCP指示は、残りの読み込み可能なツールから導出され、tool_search が公開されている場合にのみ表示されます。プリンシパルがオンデマンドで有効化するには、tool_search と指名された遅延MCPツールの両方が必要です。ヘルパーが暗黙的に付与されることはありません。許可された mode = "always" のMCPツールは事前有効化され、ヘルパーなしでも引き続き呼び出し可能です。

delegate（境界付きかつ独立）、spawn_subagent、execute_pipeline は、プリンシパルのツールセレクターまたはエージェントセレクターのいずれかが制約されている場合、利用できません。これにはそれらのツールをラップするスキルのエイリアスも含まれます。これらのネストされたパスは、現時点では現在のプリンシパルに適用される両方の上限をまだ引き継いでいません。通常の親ターンは引き続き利用できます。

呼び出し元のプリンシパルを引き継がずに処理するツールがあるため、admin を持たないプリンシパルは、セレクターに何を指定していても（"*" を含め）、それらのツールをセッションで保持できません：

  • sessions_list、sessions_history、sessions_send は、所有者を確認せずに他のセッションを一覧表示、読み取り、追記します。エージェントがこれらを登録した場合、sessions_reset と sessions_delete も同様になります。呼び出し元自身のセッションのみを報告する sessions_current は残ります。
  • cron_add、cron_update、cron_run、cron_list、cron_runs、cron_remove、および schedule: スケジュールされたターンは呼び出し元の制限を引き継がず、cron の行と実行出力は呼び出し元のプリンシパルではなく、エージェント単位で共有されます。
  • send_message_to_peer、そのターンは別のエージェント上で実行されます。
  • sop_execute、sop_advance、sop_approve、sop_workshop: SOPのステップは、その手順のエージェントとしてヘッドレスに実行されます。適用されたワークショップの提案は共有手順となり、以降も同じ方法で実行されます。読み取り専用のSOPツールは通常のツールセレクターに従います。
  • model_routing_config および proxy_config は、すべてのエージェントの以後の実行で使用されるデーモン設定を保存します。RPC では、同じ変更に config:update が必要です。
  • spawn_subagent と execute_pipeline。これらのネストされた実行は、上記のツールを再び保持することになります。

これらのツールはいずれも requires_unrestricted_principal を報告するため、そのスキルエイリアスも一緒に除外されます。直接の delegate ツールは、両方のセレクタが "*" の場合に残ります。セッションがそのハンドルを保持しているためです。境界付き、独立、バックグラウンド、並列、ネストされたものを含め、構築されるすべての子は同じツールを除外します。また、子を構築する際には元の認証情報の現在の権限を解決するため、その認証情報が admin を失った後に構築された子も、それらのツールを除外します。スキルエイリアスは、捕捉されたターゲットを束縛されたハンドルとして特定できないため、除外されます。

セッションの作成時、再ハイドレーション時、プロンプトの送信前、そして承認済みのステアリングを消費する時(メモリ書き込み後の再確認を含む)に、この制限が適用されます。セッション中に管理者の権限が降格された場合、次のプロンプトまたは承認済みステアリングの時点でツールが失われます。セレクターによる絞り込みと同様に、稼働中のセッションにツールが戻されることはありません。管理者プリンシパルと共有オペレーターは、エージェントに設定されたツールを引き続き利用でき、既存の cron ジョブも引き続き実行されます。

キュー内のプロンプトは、プロバイダーの整合処理と Agent およびタスクの待機が終わった後、そのターンを実際に実行する Agent 上で権限を再解決します。同じ受け入れ判定で対象ツールの除外も適用し、ストレージ競合後にプロンプトのチェックポイントや実行中状態を書き込む処理も保護します。受け入れが拒否された場合、プロバイダーは呼び出されず、ターンの終了状態も永続化されません。これはターン開始時の受け入れ境界であり、すでに実行中のターンの権限を継続的に取り消す仕組みではありません。

RPC cron/patch と cron/trigger も、非管理者によるエージェントジョブを拒否します（ワイルドカードセレクターを含む）。これらのジョブは呼び出し元のセッション制限を引き継ぐことができません。そのため、ジョブを参照した後に現在の権限を用いてチェックを行います。シェルジョブは既存の権限付与およびコマンドポリシーのチェックをそのまま維持します。cron の読み取り、削除、およびオペレーターによって既にスケジュールされているジョブは変更されません。

sops/run と sops/decide の RPC では、ワイルドカード指定のツールおよびエージェントセレクタを持つ非管理者が利用する場合でも管理者権限が必要です。ヘッドレスステップは呼び出し元のプリンシパルの制限を引き継ぎません。これは deny、amend、revise の判断にも適用されます。決定モデルおよびエンジンの待機が完了した後も、RPC は同期的なストア処理の間、現在の権限を保持します。使用中の SOP ストアはリクエストを直ちに拒否するため、競合が解消されてから再試行してください。バックグラウンドの SOP 処理は、通常のストレージタイムアウトを維持します。SOP の作成は、個別のエージェントセレクタのチェックを引き続き実施します。

セッションデータツールがオーナーシップを検証するようになるまで、管理者またはトリガーによって開始された、スケジュール済みエージェントジョブ、SOP実行、ピアターンからも、これらのツールを引き続き呼び出せます。それらの実行からも削除するには、sessions_list、sessions_history、sessions_send に加え、それらを対象とするスキルツールを、その実行で使用される各エージェントのリスクプロファイルの excluded_tools に列挙してください。これにより、管理者のセッションを含む、そのエージェントのすべての実行からそれらが削除されます。

既存の8引数Rust コンストラクタ Agent::from_live_config_with_tui_env は引き続き利用できます。RPC は追加の from_live_config_with_tui_env_and_principal_tools コンストラクタを使用し、プロンプトの受け付け時に共有リゾルバの権限付与を再適用します。

その構成では、エージェントのツールに至るすべての経路を網羅できません。cron ジョブと SOP の作成では、エージェントセレクターのみを確認します。cron 権限を持つ制約付きプリンシパルは、RPC cron/add および cron/patch を使って、そのエージェント向けのシェルジョブを作成または編集できます。このコマンドは、CLI やダッシュボードからの場合と同様に、ここでもエージェントの承認ポリシーに照らして評価されます。そのため、supervised autonomy では、承認を必要とするコマンドは保存されず拒否されます。エージェントジョブは、上記のとおりこのプリンシパルには拒否されます。SOP の作成または更新権限を持つプリンシパルは、後でトリガーによって実行される手順を保存できます。cron および SOP の作成権限は、エージェントのツールに対する権限として扱ってください。

これらのチェックは、リクエストの到着時だけでなく、ジョブが書き込まれる時点でも再度実行されます。cron の書き込みがデータベースを待っている間に権限の撤回やペアリング済みデバイスの失効が行われる場合、その撤回・失効処理は、書き込みを阻止するか、書き込みの完了を待ってから実行されます。

pipeline のステップやスキルのエイリアスを経由して呼び出されたツールは、承認を継承しません。ランタイムが承認するのは、自らディスパッチした呼び出しだけです。そのため、監督付き自律動作では、承認が必要なコマンドはその場で拒否されます。承認を求めてもらうには、ツールを直接呼び出してください。

主体(principal)が所有するセッションは、権限(grants)で許可されている場合に限り、同期および並列の委譲を利用できます。バックグラウンド委譲と、その check_result、list_results、cancel_task、await_sessions アクションは、スキルのエイリアス経由や入れ子になった委譲先からの呼び出しを含めて拒否されます。これらのタスク行と結果ファイルは現在、エージェントのエイリアス単位の可視性を使用しており、同じエージェントを使用する別の主体から、ある主体の非公開の出力を保護することができません。この拒否は管理者が所有するセッションにも適用されます。管理者のプライベートメモリも引き続き非公開です。共有オペレーターによる委譲は引き続き利用できます。既存の共有結果アーティファクトは、この制限によって移行されたり削除されたりすることはありません。

破壊的変更: リモートのWSSには認証が必要になりました

リモートのWSS接続では、今後、initialize で auth_token を提示する必要があります。認証なしのリモートフォールバックはありません。

[wss] リスナーが有効で、認証情報の経路が存在しない設定（[oidc.<alias>] がなく、ペアリング済みトークンもなく、gateway.require_pairing = false の状態）は、設定の検証で拒否されるため、サポートされているどのインターフェースでも保存できません。この形の設定がすでにディスク上にある場合でも、起動は成功します。デーモンは起動しますが、リスナーはリモートからのすべてのハンドシェイクを拒否します。オペレーターが設定を修復するにはデーモンを起動できる必要があるため、この設定の読み込みは拒否されません。

[oidc.<alias>]、[users]、[permission_profiles] セクションが無効な場合は別のケースです。この場合は認可ポリシー自体がコンパイルできないため、デーモンは全拒否の accepted 状態をインストールし、セクションが修復されてリロードされるまでその旨をログに記録します。この状態では、リモート接続とローカル接続のどちらでも、デーモン自身の uid を含むすべてのプリンシパルが拒否されます。そのため、修復は上記の Recovery で説明しているディスク上の修復作業で行う必要があります。

既存のリモート zerocode ユーザー向けの移行:

  1. ゲートウェイとペアリングして、ベアラートークンを取得してください。

  2. 設定ファイルで zerocode にトークンを指定する場合:

    [connection.wss]
uri = "wss://daemon.example.com:9443"
auth_token = "zc_..."

    またはシェルのZEROCLAW_AUTH_TOKEN環境変数で指定できます。この環境変数は設定ファイルの値より優先され、認証情報をファイルに残さずに済みます。

    または、それを含むファイルを指定して:

    [connection.wss]
uri = "wss://daemon.example.com:9443"
auth_token_file = "/etc/zeroclaw/zerocode-bearer"

    優先順位は ZEROCLAW_AUTH_TOKEN、auth_token_file、auth_token の順です。Unix のパーミッションビットを持つプラットフォームでは、他のアカウントが読み取れる参照先ファイルは使用されず、警告を出してスキップされます。その場合、同じ順序で次のソースが適用されます。それ以外の環境では、ファイルの ACL だけが唯一の保護手段となります。

    環境変数の使用を推奨します。トークンを代わりに設定ファイルに保存する場合、zerocode はそのファイルを所有者のみ読み書き可能（0700 の設定ディレクトリ内で 0600）にして書き込み、以前に作成されたファイルのパーミッションも修正します。これは Unix のパーミッションビットを持つプラットフォームの場合です。パーミッションビットがないプラットフォームでは、ディレクトリの ACL だけが保護手段となるため、そのファイルは機密情報として扱ってください。

OIDCアクセストークンも、auth_provider = "oidc.<alias>" を使って同じように動作します。

ゲートウェイの HTTP API

ゲートウェイの設定およびオンボーディング用ルート（/api/config*、/api/quickstart/*、/api/channels/bind）は、認証を構造的に強制しています。ルートレイヤーのミドルウェアが1つでルートグループ全体を保護するため、個々のハンドラーが認証チェックを持つことも、そのチェックを忘れることもありません。このミドルウェアは、同じプロバイダーレジストリとリゾルバーを通じて、RPC経路と同じプリンシパルモデルを扱います:

  • ペアリング済みベアラー (Authorization: Bearer zc_...) は、従来どおり完全なアクセス権を持つ共有オペレーターに解決されます。拒否時は従来の 401 形式を維持します。
  • OIDC ベアラー を X-ZeroClaw-Auth-Provider: oidc.<alias> ヘッダーとともに提示すると、そのプロバイダーによって検証され、スコープ付きのプリンシパルに解決されます。プロバイダーの選択は明示的に行われ、RPC ハンドシェイクの auth_provider フィールドと同じ仕組みです。指定されたプロバイダーによる拒否が最終的な判断となり、プロバイダー間のフォールバックは一切行われません。
  • CORSのプリフライトリクエスト（OPTIONS）は、これまでと同様に認証なしで通過します。GET、HEAD、POST、PUT、PATCH、DELETE以外のメソッドはすべて拒否されます。

OIDC ベアラーの検証は、認証されていない呼び出し元がゲートウェイに実行させる処理です。validation = "introspection" を使用すると、検証のたびにデーモン自身のクライアント資格情報で、ID プロバイダーへの認証済みのラウンドトリップが 1 回発生します。これを制限する仕組みは 2 つあります。拒否された資格情報は、クライアントごとの台帳で集計されます。閾値はペアリングトークンの不正使用と同じ（1 分間に 10 回で、その後 5 分間のロックアウト。ループバックは除外）で、ペアリング用とは別の台帳で管理されます。そのため、有効期限切れのトークンを再送するクライアントがいても、オペレーターがペアリングからロックアウトされることはなく、ペアリングのロックアウトがベアラーをブロックすることもありません。ベアラー台帳は、リクエストごとに稼働中の設定から gateway.trust_forwarded_headers を読み取るため、保存されたプロキシ信頼の変更は、ルーターを再構築せずに適用されます。ゲートウェイ自身の ID プロバイダーへの経路でのトランスポート障害や、ポリシーが何も許可しない検証済みの ID は、呼び出し元について何も示さないため、その呼び出し元に課金されません。すべてのクライアント（ループバックを含む）を合わせて、同時に実行中のベアラー検証は最大 16 件です。これにより、全員に代わってゲートウェイが ID プロバイダーに対して行える処理量が制限されます。このスロットは検証そのものの間だけ保持され、それが許可したリクエストの処理中は保持されません。ロックアウト中のクライアントには HTTP 429 が返され、容量不足で拒否された検証には HTTP 503 が返されます。どちらも、待機時間を秒単位で示す Retry-After が付きます。ダッシュボードのセッションは専用のレイヤーで検証され、これらの制限と競合することはありません。

スコープ付きプリンシパルの Config 権限は2段階で適用されます。ルートレイヤーは HTTP メソッドごとに粗い下限を設けており、読み取りには read が必要で、それ以外には create、update、delete のいずれか少なくとも1つが必要です。そのため、読み取り専用のプリンシパルが変更系のハンドラに到達することはありません。各変更系ハンドラは、最初の副作用が発生する前に書き込みセット全体を認可します。書き込みセットとは、その変更によって永続化されるすべての設定パスであり、各パスは設定に対する作用によって分類されます（新たに作成するパスは create、削除するパスは delete、それ以外は update）。そのうえでプロファイルの config_write_paths セレクタと照合されます。分類は HTTP メソッドではなく操作に従います。POST /api/config/map-key によるマップキーの作成や、新しいエイリアスの下での PUT による暗黙的な作成には create が必要です。JSON Patch の remove と DELETE /api/config/map-key には delete が必要です。名前の変更には、移動元に対する delete と移動先に対する create が必要です。削除やリネームのカスケードによって他の場所で書き換えられる参照も、書き込みセットに含まれます。書き込みセットの中に1つでも未認可のメンバーがあれば、バッチやカスケードを含む変更全体が拒否され、何も書き込まれません。書き込みセットを事前に列挙できない操作（ファイルのスキーマ移行や Quickstart の適用など）には * セレクタが必要です。永続化の境界では、書き込まれようとしているパスをハンドラが認可したものと照合し直すため、ハンドラが認可された範囲を超えて永続化することはできません。

ポリシーが変更されるのは、永続化の境界においてのみです。設定を書き込むハンドラーは、その設定からコンパイルした認可状態を次の受理済みリビジョンとして公開し、すべてのリクエストは、現在の受理済みスナップショットに対して検証と解決が行われます。リクエスト処理の経路ではポリシーを再コンパイルしないため、並行する永続化の前に設定を読み込んだリクエストが、古いポリシーで新しいポリシーを上書きすることはありません。プロバイダーの検証設定、名簿、プロファイルに対する永続化済みの変更は、次のリクエストから有効になります。監視下での実行では、ゲートウェイとRPCサーフェスがライブ設定、書き込みロック、受理済みポリシーの管理主体を共有するため、いずれのサーフェスから保存しても両方に公開されます。スタンドアロンのゲートウェイは独自の管理主体を持ち、別途実行中のデーモンに変更を公開することはありません。その他のゲートウェイサーフェスは、ハンドラーごとにペアリングチェックを維持し、この仕組みへの対応はフォローアップで行います。ダッシュボードのサインインセッションは、そのアカウントが管理者である場合、このペアリングチェックも満たします。

ダッシュボードへのサインイン

Web ダッシュボードは、ペアリングコードの代わり、またはそれと並行して、設定済みの OIDC プロバイダーを通じたサインインを提供できます。この機能はデフォルトで無効です。[gateway.dashboard_sign_in] が設定されていないインストールでは、ペアリングダイアログがこれまでと全く同じように表示され、そこに送信されたセッション Cookie は無視されます。

[gateway]
require_pairing = true

[gateway.dashboard_sign_in]
oidc = ["corp"]                # サインイン画面に表示される [oidc.<alias>] エントリ
session_lifetime_secs = 28800  # 1 セッションあたりの上限時間（任意、300..=604800、デフォルトは 8 時間）

有効にするには、以下が必要です:

  • gateway.require_pairing = true。ペアリングを無効にすると、ゲートウェイに到達できる誰もがすべてのダッシュボードルートにアクセスできてしまうため、この設定は拒否されます。公式 Docker イメージはデフォルト設定に require_pairing = false を書き込んでいます。そこで、その値を true に変更するか、ZEROCLAW_gateway__require_pairing=true を指定してください。
  • HTTPS（[gateway.tls]、trust_forwarded_headers を設定したリバースプロキシ、または [relay.dashboard] で配信されるリレー終端のダッシュボード。詳細は secure transport, 3e を参照）。ゲートウェイ自身のマシン上でブラウザを実行している場合を除き、プレーンな HTTP 経由のサインインは拒否されます。リレーが配信するダッシュボードではサインインのみ提供されます。リレーがペアリングコードやトークンを参照できてしまうため、そこではペアリングおよびペア済みトークンは拒否されます。リレー経由で管理者としてサインインすると、永続的な変更を行う権限も含め、リレーに管理者権限を与えてしまうため、デーモンの管理は直接接続するか zerocode を使って行ってください。
  • リバースプロキシの背後では、ブラウザーのHostがそのまま渡される必要があります（nginxの場合は例えばproxy_set_header Host $host;）。コールバックURIとダッシュボード自身のオリジンはどちらもこの値から取得されるため、プロキシがHostを内部名に書き換えると、サインインが失敗し、サインイン済みの変更はすべて別のオリジンからのものとして拒否されます。
  • 認可コードフローと PKCE (S256) を使用する ID プロバイダーのクライアント。リダイレクト URI には <dashboard origin><path_prefix>/oidc/callback を指定します(上記のブラウザ登録リレーと同じ URI です)。この URI は正確に登録してください。ワイルドカードやプレフィックスによるパターンは使用しないでください。ゲートウェイが設定済みのダッシュボードオリジンに対して URI を検証するようになるまで(#12048)、URI はリクエストの Host から構築されます。サインインコードが別のアドレスに送られないようにしているのは、ID プロバイダーによる完全一致です。リレーで提供されるダッシュボードの場合、URI は常にそのダッシュボード自身のアドレスになり、デーモンが起動時にそのアドレスをログに出力します。このクライアントは interactive_clients に記載するか(または actor_claim で分類する)必要があり、そのアクセストークンには設定された audience が含まれている必要があります。テスト済みのプロバイダーと、各プロバイダーに必要な設定については ID プロバイダー を参照してください。
  • セッション作業に適したアクセストークンの有効期間（例：1時間から8時間）。このダッシュボードはリフレッシュトークンを使用しません。トークンの有効期限が切れると、ユーザーは再度サインインする必要があります。

ユーザーがプロバイダーを選択すると、ゲートウェイはブラウザーフローを実行し、短命の Cookie でそのブラウザーに紐付けます。そのため、別の場所で開始されたサインインを、そこで完了させることはできません。ID トークンは必須であり、サインインの証跡として検証されます（issuer、audience、authorized party、有効期限、nonce）。検証後は破棄されます。アクセストークンは RPC のベアラートークンと同様にプロバイダーによって検証され、アカウントはそのトークンが解決するアカウントになります。ID トークンの subject はこれと比較しません。両者は同じバックチャネルでの交換から得られるためです。サービスクライアントにダッシュボードセッションが発行されることはありません。トークンはその後もゲートウェイのメモリ上に留まります。ブラウザーが保持するのは、不透明な HttpOnly、SameSite=Strict のセッション Cookie（HTTPS 上では Secure）のみで、トークンがブラウザーのストレージやスクリプトに渡ることはありません。

すべての Cookie 付きリクエストは、RPC が使うのと同じ認可判定の仕組みで改めて検証されます。検証対象は、トークンの有効期限、introspection の再検証期限、そしてアカウントが現在有効なポリシーのもとで保有しているグラントです。プロファイルのマッピングが変更された場合、プロバイダーが削除された場合、または gateway.dashboard_sign_in.oidc からエイリアスが削除された場合、その変更は次のリクエストから有効になります。状態を変更するリクエストでは、セッションの CSRF トークンを X-ZeroClaw-CSRF ヘッダーで送信する必要があります。また、Cookie を伴うリクエストと WebSocket アップグレードは、ダッシュボード自身のオリジンから送られたものでなければなりません。Authorization ヘッダーを伴うリクエストは、そのヘッダーのみで判定されます。

サインイン済みのアカウントができることは、その権限プロファイルに従います:

  • プロファイルに admin = true が設定されているアカウントはオペレーターと同等であり、ペアリング済みブラウザーと同様にすべてのダッシュボードページにアクセスできます。サインインのたびに、解決されたプリンシパルとともにログが記録されます。そのアカウントがダッシュボードのチャットで開始した会話は、ペアリング済みブラウザーの会話と同様に、共有オペレーターに帰属します。
  • それ以外のアカウントがアクセスできるのは、自分の Config 権限で許可された設定ページです。その他のページは "reason": "operator_required" を伴う 403 を返し、ダッシュボードではそれらのページが非表示になります。
  • ゲートウェイがデーモン内で実行されている場合、admin を持たないアカウントも、そのgrantが許可するエージェントに対して、プロファイルで sessions の create、read、execute、update が付与されていれば、ダッシュボードでチャットできます。エージェントは、プロファイルが付与するツールのみを使用します（allowed_tools、tools = ["execute"] を指定）。無効化されたエージェントでは新しいチャットを開始できず、既に開いているチャットでは、エージェントが再び有効になるまで、各メッセージに対してエラーが返されます。会話はそのアカウント専用です。デーモンはそのアカウントの権限のもとで会話を実行し、他のユーザーのダッシュボードには一覧表示されません。画像のアップロードは提供されません。各チャットは1つの会話であり、会話はチャットが続く間だけ有効です:
    • ページを閉じる、再読み込みする、チャットから離れる、接続が切れる、といった操作によって会話は終了し、進行中の返信も停止します。サインアウト、セッションの有効期限切れ、デーモンの再読み込みや再起動も同様に会話を終了させます。新しいチャットを開始すると新しい会話が始まります。既存の会話が再開されることはありません。
    • 1 つのサインインで同時に開けるチャットは最大 4 件（たとえばタブ 4 つ）、1 つのアカウントで全サインインを合わせて最大 32 件です。作成中の会話や、チャット終了後にまだクローズされていない会話もこの数に含まれます。そのため、サインアウトして再度サインインしても、会話がクローズされるまで枠は解放されません。いずれかの上限を超えるチャットは、どれか 1 つがクローズされるまで拒否されます。
    • 各チャットは、トークンを発行した ID プロバイダーにひも付くデーモンにトークンを提示します。その間にプロバイダーの設定が別の発行者またはクライアントに変更された場合、チャットは拒否され、トークンは新しい設定先には送信されません。
    • アカウントのアクセス権が、サインイン中に取り消された場合、そのアカウントが開いている会話は、アカウント自身の権限では閉じられず、他の誰もアクセスできなくなります。デーモンは、チャットが wss.orphaned_session_timeout_secs（デフォルトは30分）の間存在しない状態が続いた会話を、その会話がアイドル状態で、返信や承認が保留になっておらず、保存済みのトランスクリプトが最新である場合に閉じます。タイムアウトを 0 に設定するとこの機能は無効になり、その場合ダッシュボードから閉じられなかった会話は、デーモンが再起動するまで稼働したままになります。
    • デーモンによるチャットの会話の作成に10分を超える時間がかかる場合、チャットはタイムアウトで中止されますが、ダッシュボードはデーモンからの応答を待ち続けます。その間、この作成はアカウントの32件の上限にカウントされ続けます。作成された会話が後から届いた場合は、受信時に閉じられ、上記のタイムアウトに関係なくカウントされなくなります。ダッシュボードが閉じられなかった会話、またはデーモンからの応答が届く前にデーモンとの接続が失われた作成は、ダッシュボードがデーモンがいつそれを解放するかを判断できないため、次回のデーモンのリロードまたは再起動までカウントされ続けます。
    • 閉じた会話の記録は保持されますが、ダッシュボードから開くことはできません。アカウントでチャット終了後も使える履歴が必要な場合は、zerocode を使用してください。

サインアウトすると、この ZeroClaw 内のセッションが終了し、そのCookieが削除されます。セッションがすでに終了していた場合も同様です。ID プロバイダーからユーザーがサインアウトされることはありません。セッションが終了した場合（サインアウト、有効期限切れ、または失敗したチェック）や、ページが必要とするアクセス権を失った場合は、そのページのソケットとイベントストリームが直ちにクローズされます。同じブラウザで再度サインインすると、そのブラウザが以前保持していたセッションは、どのアカウントのものであっても終了します。そのため、後でサインアウトすると、そのブラウザにサインイン状態のものは何も残りません。2 つのタブで同時にサインインした場合も同様です。ブラウザマーカー Cookie（zc_browser_<tag>、またはルートパスで HTTPS を使用する場合は __Host-zc_browser_<tag>。ランダムな値で、HttpOnly と SameSite=Lax が設定され、認証情報になることは決してありません）が、そのブラウザのセッション同士を紐付けます。マーカーにはそれぞれ固有の名前があるため、開始の応答が遅れたサインインは、既存のマーカーを置き換えるのではなく、マーカーを追加します。後から完了したサインインは、もう一方のセッションを終了させます。また、サインアウトは、そのブラウザとマーカーを共有するすべてのセッションを終了させます。セッションが終了する前に受理され、まだ有効になっていないリクエスト（例：本文がまだ送信中の設定変更）は拒否されます。すでに実行中のチャットのターンは、閲覧者が離脱した場合と同様に、ユーザーの操作なしで完了します（スコープ付きアカウントの場合は、会話がクローズされるため、代わりに停止します）。また、そのターンが待機していたツール承認は拒否されます。クローズされたソケットが後から送信した内容は、いっさい処理されません。リロードによっても、セッションが開いたソケットはクローズされ、ダッシュボードは新しい構成でそれらに再接続します。置き換え中のゲートウェイ世代に、接続を維持したまま到達したリクエストには、503 と "reason": "gateway_restarting" で応答し、ダッシュボードはそのリクエストを再試行します。

セッションはメモリ上に保持され、セッションが終了するとそのトークンは消去されます。期限切れのセッションは、リクエストが届いていない場合でも1分ごとに削除されます。デーモンを再起動するとすべてのユーザーがサインアウトされますが、リロードではセッションは維持され、次回使用前に新しい設定に対して各セッションが再検証されます。同時に保持できるセッションは最大256件で、アカウントごとに8件までです。上限に達している場合、新しいサインインは他のユーザーをサインアウトさせるのではなく拒否されます。

設定を有効にする前に知っておくべきこと:

  • ペアリングはサインインと並行して引き続き機能し、IDプロバイダーに到達できない場合の再接続手段として残ります。デスクトップアプリでもペアリングは引き続き利用できます。
  • 管理者は、ほかのオペレーターと同様にダッシュボードからデバイスをペアリングできます。ID プロバイダーでその管理者のアクセス権を削除しても、ペアリング済みのデバイスは失効しません。それらのデバイスはペアリングページで失効させてください。
  • 会話とメモリのうち、サインイン前に作成されたものは共有オペレーターに帰属します。admin を持たないアカウントには、これらは表示されません。
  • ゲートウェイ自身のマシン上で平文のHTTPを使用する場合、ブラウザはポート番号によってCookieを区別しないため、ブラウザがアクセスする他のローカルWebサーバーにもセッションCookieが送信されます。HTTPSを使用するか、他のローカル開発サーバーに使用していないブラウザからのみサインインしてください。
  • gateway.dashboard_sign_in.oidc からプロバイダーを削除する、または空にすると、そのプロバイダーが発行したセッションは終了します。終了のタイミングは、次のリクエスト時、またはリクエストが届かない場合は1分以内です（リロードで変更が適用される場合は即時）。同じプロバイダーを再度設定しても、セッションは復元されません。ただし、1分以内にリクエストが届く前に再度設定した場合は例外です。[oidc.<alias>] エントリが別の発行者またはクライアントを指すように変更された場合も、そのエントリのセッションは終了します。その際、トークンが新しいプロバイダーに送信されることはありません。
  • session_lifetime_secs は、設定後に開始されたセッションに上限を適用します。すでにサインインしているセッションは、開始時の上限を維持します。それより早く終了させるには、プロバイダーを gateway.dashboard_sign_in.oidc から外してください。
  • ご利用の ID プロバイダーに到達できない場合、またはエラーを返した場合、セッションのトークンを再検証する際にそのセッションは終了されます（フェイルクローズ）。これは、各 introspection 再検証の期限ごとに発生し、どちらの検証モードでも、設定の再読み込み後や、OIDC、ユーザー、または権限プロファイルの設定が変更された後に発生します。ダッシュボードにはセッションが期限切れと表示され、プロバイダーが復旧した後にユーザーは再度サインインします (#12096)。

認証情報のライフサイクル

  • 有効期限切れは、期限の時点で接続の認可を終了します。クライアントは新しいトークンで再初期化します。
  • イントロスペクションの再検証: OIDCイントロスペクションのIDには再検証の期限があり、期限を過ぎると、クライアントが再初期化(IdPに対して再検証を行う)するまで、次の操作は拒否されます。
  • ペアリングの取り消しは、接続の次の操作の前に適用されます。
  • ログのサブスクリプション: 開いている logs/subscribe または events/subscribe ストリームは、配信のたびに再チェックされ、資格情報の有効期限切れ、ペアリングの取り消し、またはプリンシパルの Logs:Read 権限や管理者権限の喪失が発生すると、その後最初の配信時に終了します。
  • ポリシーの変更: 設定の保存時に [oidc]、[users]、[permission_profiles]、security.trust_daemon_uid のいずれも変更されていない場合、すべてのバインディングはそのまま維持されます。これらのいずれかが変更されると、新しいポリシーが公開されます。ネイティブトークン接続およびローカル接続は、その新しいポリシーに対してその場で再解決されます。ただし、デーモンは OIDC ベアラートークンを保持しないため、OIDC 接続での次の操作は、クライアントが再初期化されるまで拒否されます。
  • tui_id/tui_sig による再接続の仕組みは継続性のみを担います。TUI のレジストリ上の ID を保持しますが、いかなる権限も付与しません。すべての initialize は認証情報を再提示します。

セッション分離

すべてのスコープ付きプリンシパルが作成するセッションは、ライブストアとディスク上(チャットバックエンドおよびACPストア)の両方で、そのプリンシパルのIDが刻印されます。スコープ付きプリンシパルは、自身のセッションのみを閲覧・操作できます。一覧は絞り込まれ、読み取りと変更操作では、「存在しないか、所有されていない」という単一の統一された拒否応答が返されるため(存在の有無を探ることはできません)、破壊的な削除は所有者条件付きのストレージ文として実行されます。また、進行中の承認は、それが発生したセッションの所有者に対してのみ解決されます。この変更以前に作成されたセッション、またはアンスコープ接続によって作成されたセッションには所有者がありません。これらは、アンスコープ接続からは引き続き完全に閲覧可能であり、スコープ付きプリンシパルからは不可視のままです。

認証済みのすべてのプリンシパルは PRIVATE メモリを持ちます。メモリ操作はプリンシパルごとの plane を読み書きし、その plane の所有者はすべてのストレージ文に含まれて、agent、namespace、tenant の各次元と組み合わされます（同じキーでも、2つの agent の下では2つの行になります）。plane はプリンシパルのアイデンティティに従い、管理者バイパスには従いません。名前付き管理者のメモリは、その管理者自身の private plane です。そのため、ユーザーを昇格または降格しても、そのユーザーのノートが見えなくなったり、書き込み先が変わったりすることはありません。デフォルトで shared plane に属するのは、未認証の共有オペレーターだけです。管理者バイパスを持つ呼び出し元は、memory/* リクエストで plane = "shared" を明示的に指定できます。この指定は監査されます。スコープ付きプリンシパルはこれを指定できません。

この2つのプレーンは双方向で互いに干渉できません。共有書き込みはプライベート行のストレージキーを指定することも、プライベート行を上書きすることもできません。プライベート書き込みが共有行を変換することはありません。通常のエクスポートとMarkdownスナップショットには共有行のみが含まれます。従来の一括パージの対象も共有行のみです。プライベート行のエクスポートとパージは、所有者情報を伴う操作を通じて行われます。

principal が作成したセッションのメモリハンドルは、そのセッションの生存期間中ずっと、その principal のプライベートプレーンに固定されます。後からセッションをプロンプトするのが誰であっても同様です（管理者が回収済みのセッションを復元する場合も、耐久性のあるオーナーのプレーン上で復元されます）。そのため、スコープ付きセッション内のメモリツールとターンごとのリコールは、共有プレーンに一切アクセスしません。スコープ付きセッションに共有プレーンを開放するグラントは存在しません。プライベートへの書き込みは、共有への書き込みと同じコンテンツスキャンおよびポリシーゲートを通過します。メモリ監査が有効な場合、プライベート操作はスコープ全体を含めて監査されます。principal をサポートしないメモリバックエンド（現時点では markdown、lucid、postgres、qdrant）では、プライベートメモリはスコープを黙って解除するのではなく、明確な拒否によってフェイルクローズします。スコープ付きセッションの場合、これはそのメモリツールが拒否されることを意味します。

[security.nevis] からの移行

Nevis IAM 連携は削除されました。どの認証経路にも組み込まれていなかったため、有効化しても誰も認証されることはありませんでした。廃止しても実際の動作は一切変わりません。[security.nevis] はもう設定キーではありません。スキーマ V4 で廃止されました。設定にこのテーブルが残っている間は、すべてのコマンドがそれを名指しした警告を表示し、その値は一切読み込まれません。このテーブルは zeroclaw config migrate によって config.toml から削除されるほか、編集後の次回保存時にも削除されます。これは全体保存でも、CLI・ダッシュボード・RPC が単一の編集に使用する増分保存でも同様です。増分保存は何かが編集された場合にのみ実行されるため、編集されていない設定では、上記のいずれかが行われるまでテーブルが残ります。削除対象はそのテーブルのみで、コメントや他のセクションはバイト列をそのまま保持します。自動変換は行われません。置き換え先のスタックには、旧テーブルが保持していなかった値（audience、プロファイルの権限付与など）が必要だからです。

ZeroClaw は元ファイルのコピーを 2 つ保持します。 V3 形式のファイルが初めて書き換えられるとき（zeroclaw config migrate の実行時、または CLI、ダッシュボード、RPC、Quickstart からの最初の保存時）、そのファイルは config.toml.v3.backup にコピーされます。このコピーはご自身のみが読み取り可能な状態で作成され、置き換えられることはなく、古いバージョンの ZeroClaw に戻るための手段となります。config migrate は config.toml.backup も書き出し、次回のマイグレーション時にこのファイルは置き換えられます。どちらのコピーにも廃止されたテーブルが残り、平文の client_secret も含まれます。すべての保存処理では、書き込みの間だけ config.toml.bak が作成され、書き込みが永続化された後に削除されます。したがって .bak はバックアップではありません。

アップグレード後は、config.toml.v3.backup、config.toml.backup、および自分で保管した複製をすべて機密情報として扱ってください。ダウングレードの必要がなくなったら削除し、IdP で Nevis クライアント認証情報を失効させてください。

リモート接続で認証情報が提示されない場合は、すべて拒否されます。どちらの経路でも接続は開かれません。

ロールバックは設定データの操作であり、コードの巻き戻しとは異なります。バイナリを元に戻すと古い型は復元されますが、config.toml から既に削除されたテーブルは、どの操作によっても復元されません。アップグレード前に取得した保護済みのコピーを戻すか、テーブルを手動で再追加してください。今回の廃止ではスキーマバージョンは変わらないため、ダウングレードしたバイナリは移行手順なしで復元後のファイルを読み込めます。

この層がまだ行わないこと

統合（consolidation）とガバナンスは共有プレーンの行を導出するもので、プライベートセッションに対しては実行されません。他のプリンシパルのプライベートメモリへの管理者アクセスは、まだ公開された経路がありません（デフォルト拒否）。セッションデータツールはまだプリンシパルを考慮したビューがないため、呼び出し元自身のセッションに限定するのではなく、adminを持たないプリンシパルには提供されていません（権限プロファイルを参照）。スケジュール済みエージェントジョブ、SOP実行、ピアターンは、エージェントのリスクプロファイルで除外されていない限り、これらのツールを引き続き呼び出せます。Sops:Readを持つプリンシパルに対し、sops/runsとsops/run-detailは、実行したエージェントに関係なく、すべての手順の実行履歴を返します。cron履歴とは異なります。設定グループ外のゲートウェイHTTPルートは既存のペアリングチェックをそのまま維持します。ダッシュボードへのサインインで満たされるのは管理者の場合のみです。また、チャネルIDはこのプリンシパルモデルには解決されません。

security.trust_daemon_uid = true（デフォルト）であり、ポリシーがコンパイルされる場合、Unix ソケット上のデーモン自身の uid は完全なアクセス権を保持します。そのため、[users] ユーザー一覧がなく、認証セクションが有効な単一オペレーター構成のインストールは、従来どおり動作します。

権限プロファイルは、プリンシパルが RPC 経由で実行できる操作を制限します。ただし、プリンシパルがエージェントに実行させるコードを隔離するものではありません。セッションのターン、cron ジョブ、SOP のステップはデーモンのアカウントで実行されます。Unix では、そのコードはデーモンの uid としてローカルソケットに接続できます。security.trust_daemon_uid = true（デフォルト）の間、この uid は共有オペレーターとして扱われます。それ以外の場合は、その uid に対応付けられたロスターのエントリが適用されます。ロスターがない Windows では、パイプを介して共有オペレーターとして扱われます。また、そのコードは config.toml を編集でき、デーモンは次回の再読み込みまたは再起動時にその変更を適用します。security.trust_daemon_uid = false を設定しても、これらの動作は変わりません。セッション、cron、または SOP の実行や作成は、オペレーターアクセスを委ねても信頼できるプリンシパルにのみ許可してください。エージェントプロセスがソケットと config.toml に触れられないようにする OS レベルの隔離だけが、このコードを実際に分離できます。

一部の設定パス自体が権限を持つため、広範な config_write_paths の付与は、検証済みの末端設定のみを対象とする場合を除き、オペレーターアクセスとして扱ってください。例えば:

  • permission_profiles、users、oidc、security、または gateway.paired_tokens に書き込める権限を持つプリンシパルは、あらゆる権限を自分自身に付与できてしまいます;
  • agents、risk_profiles、cron、channels、またはプロバイダー設定に書き込める者は、どのエージェントが実行されるか、どのツールを使うか、どこを読み書きできるかを変更できます;
  • mcp、mcp_bundles、または tunnel.custom.start_command に書き込める者は、デーモンアカウントが起動するプログラムを選択できます。

Config:Update は、ディスク上の config.toml の内容を適用する config/reload も付与します。

zerocode のリモートディレクトリピッカーは、デーモンのファイルシステムルートで開きます。オペレーター権限を持たないプリンシパルは、/ の読み取りを許可するポリシーを持つ有効なエージェント（ワークスペース限定ではないエージェントなど）を経由する場合にのみ、そこを一覧表示できます。それ以外のそのようなプリンシパルに対しては、許可されたルート内で開かれるまで、ピッカーがそこでの拒否を報告します。

Keycloakアクセストークンのクライアント帰属

JWKS検証は、型付きアクセストークンにclient_idがなく、設定されたクライアント宣言またはactor_claimによって人間のアクターが確立されている場合、署名済みのazpをOAuthクライアント識別子として受け入れます。発行者、署名、トークンの用途、オーディエンス、有効期間、およびアクター分類のチェックは引き続き適用されます。azp-のみのトークンでは、actor_claimによって分類されたものを含め、サービスを認証することはできません。サービスアクターには引き続きclient_idが必要です。空のclient_id、client_idとazpの矛盾、または宣言も設定済みのactor-claimの根拠もないクライアントは、フェイルクローズ（安全側に失敗）します。イントロスペクションでは、引き続きclient_idレスポンスフィールドが必要です。
