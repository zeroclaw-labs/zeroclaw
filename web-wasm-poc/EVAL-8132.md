## Phase 1 report: Dioxus Skills page prototype (#11355)

Prototype: `web-wasm-poc/` in #11355, at `b817c960e` (the commit named in the measurement report). It is one standalone page, the Skills page. It reuses the existing gateway API without changes. React remains the authoritative client. Nothing here changes the default build.

This report covers the evidence list from the August 4 note. Measured items say how they were measured. Everything else is marked **not measured**. That avoids implying conclusions this prototype cannot support.

### 1. Build time, dependencies, cache behavior

Measured by `sh web-wasm-poc/measure.sh`, which anyone can rerun from a checkout using only podman and git. Both builds use the same image (pinned by digest): rustc 1.99.1, node 24.22.2, wasm-bindgen 0.2.129. Each build starts with empty cargo and npm caches. Downloads run online, and the builds run with `--network=none`. Host: AMD EPYC, 28 threads, 99 GiB RAM.

| Step (seconds, wall clock) | WASM PoC | React |
|---|---|---|
| Download dependencies | 11.4 | 39.5 |
| Cold build (`build.sh` / `cargo web build`) | 34.0 | 240.1 |
| One-line edit, rebuild (`build.sh` / `npm run build`) | 7.7 | 10.1 |

How to read this:
- **The cold build comparison** Almost all of React's 240 s goes to compiling `xtask` and the gateway, which generate the API client. Vite itself takes 0.58 s. The PoC skips that step because its API types are written by hand (see section 3). So the gap shows the cost of generating the client, not React versus Dioxus.
- **The edit-loop numbers are production rebuilds, not dev-server hot reload.** React's 10.1 s is mostly `tsc -b`. The PoC has no hot reload set up. Vite HMR is likely much faster than either number. **Not measured.**
- **One gap found in the current React path:** after a `web/src` edit, rerunning `cargo web build` makes the gateway `build.rs` run `npm ci`. That needs the network, so the step cannot run offline.

Dependency counts:
- PoC: `web-wasm-poc/Cargo.lock` lists 319 crates (295 distinct names), but most are never built. Cargo records every optional feature and every platform. Only 109 crates compile for `wasm32-unknown-unknown` (`cargo tree --target wasm32-unknown-unknown -e normal,build`), and many of those are proc-macro crates that run only at build time. Across all targets the tree reaches 142. The other 157 names belong to optional features this crate does not enable, mostly in Dioxus (for example `dioxus-fullstack` and `axum`).
- React: `web/package-lock.json` lists 297 npm packages, 150 of them non-dev. Every one of the 297 is installed by `npm ci`.
- Neither count includes the toolchain. The PoC still ships 5 small JS snippets generated by wasm-bindgen and Dioxus.

**Docker and cross-platform impact: not measured.** Nothing here changes the repo Dockerfile.

### 2. Artifact size, load time, memory

Sizes in bytes, raw / gzip -9. Images and fonts are excluded from both.

| Payload | Bytes |
|---|---|
| WASM PoC page (html, css, js glue, wasm, snippets) | 760,978 / 229,156 |
| React Skills page (index.html, entry assets, Skills chunk and its static imports) | 1,098,401 / 271,257 |
| React whole dashboard | 3,816,204 / 845,491 |

The React Skills page payload is mostly the shared app shell, which every page loads. The Skills chunk alone is 7,592 / 2,524 bytes. If more pages moved to WASM, the size would depend on how Dioxus code is split. That was not tested.

**Load time and runtime memory: not measured.**

### 3. API client, routing, auth, streaming, errors

- **API client:** the PoC uses hand-written serde types for the 3 endpoints it calls. They are not generated from `openapi.json`. Before any migration, the generated client would need a Rust equivalent, or the types would need to be shared from the gateway crates.
- **Routing:** none. The PoC is a single page.
- **Auth:** it takes an existing paired bearer token, checks it against `/api/config/agent-options`, and stores it under the React key `zeroclaw_token`. The pairing-code exchange is not implemented.
- **Errors:** blank, rejected (401/403), unavailable (502) and malformed responses each show an error. Errors from loading skills appear inline, and Reload stays available.
- **Streaming:** not covered. The Skills page has no streaming.

### 4. Accessibility, browsers, testing, debugging, contributor workflow

- **Browsers:** `browser_auth_check.py` passes all 14 checks in both Chromium and Firefox, with no JavaScript errors. That covers token entry, rejection, reload, disconnect, blocked storage, agent switching, search, skill expansion and reload. Safari and mobile browsers were not tested.
- **Accessibility:** the search box and agent picker have `aria-label` and `title`. Tab focus and a visible focus outline were checked. **A full accessibility audit was not done.**
- **Testing:** there are Rust unit tests, Python HTTP boundary tests for `serve.py`, and Playwright browser checks. There are no component-level tests comparable to the React test setup.
- **Debugging and hot reload:** not evaluated. Release WASM gives stack traces with no names. `dx serve` hot reload was not tried.
- **Contributor workflow:** the steps were followed by one person. No other contributor has tried them.

### 5. CodeMirror and JavaScript interop

**Not evaluated.** The Skills page does not use the editor. The editor (CodeMirror via `MarkdownEditor`, 614 KB raw) is the largest single React chunk. Embedding it would need JavaScript interop, which would keep part of the npm supply chain.

### 6. SBOM, provenance, advisories, reproducibility

**Not evaluated.** Replacing npm packages with crates moves the supply-chain exposure rather than removing it. The PoC compiles 109 crates for one page, while React installs 297 npm packages for the whole dashboard. A full port would add crates for the editor, routing and forms, and that growth was not measured. Advisory handling for the PoC would join the repo's existing Rust checks (`deny.toml`, run in CI and in `daily-audit.yml`) instead of `npm audit`. Release reproducibility of the WASM output was not checked.

### 7. Feature parity (one page)

Works the same against the real gateway: agent switching, search, the dropped-skill warning banner, expanding a bundle skill (document fetched from the gateway), Reload, and per-agent counts that match the gateway response.

Not implemented: the bundle editor (`SkillsBundleEditor`, 1,028 lines in React), the Edit flow (the PoC only has a plain link), localized strings (English only), and the dashboard layout and navigation.

The PoC is 789 Rust lines, including token entry and its own API client. The matching React files `Skills.tsx` and `SkillCard.tsx` total 418 lines.

### Decision rule outcome

The August 4 rule asks whether there is "a clear net maintenance, security, and release-engineering benefit large enough to justify rewriting the current frontend". This evidence does not show that:

- **Build time:** the apparent advantage comes from skipping API-client generation, not from the framework.
- **Size:** the page is about 15% smaller gzipped (229 KB vs 271 KB). That's modest, and it shrinks or grows depending on code splitting, which was not tested.
- **Supply chain:** exposure moves rather than shrinks, and the editor would keep JavaScript interop.
- **Parity:** a single read-only page is cheap. The hard parts (editor, streaming chat, config forms) are untested.
