ZeroClaw Docs

Configuration distante (WSS)

Connectez zerocode sur votre poste de travail à un daemon s’exécutant sur une autre machine (Raspberry Pi, serveur domestique, VPS, etc.).

Pour le guide complet, option par option, couvrant les trois topologies (directe, démon vers relais et client via relais), voir Transport sécurisé (configuration de bout en bout).

Le plan WSS est authentifié mutuellement (mTLS). Chaque client présente un certificat ; il n’existe aucun mode avec authentification du serveur uniquement / sans authentification. Le moyen le plus simple d’obtenir un certificat client est l’enrôlement (ci-dessous) : vous n’avez pas à gérer manuellement les certificats. Si vous préférez en générer un vous-même, consultez les étapes d’utilisation de votre propre certificat dans « Sur votre poste de travail » plus bas. --tls-skip-verify assouplit uniquement la vérification du certificat serveur pour un certificat auto-signé du démon ; le certificat client reste obligatoire dans tous les cas.

Il vous faut deux éléments : un certificat et un jeton de porteur. Le certificat client sécurise le transport : il prouve quel appareil se trouve à l’autre extrémité de la connexion TLS. Il ne dit pas qui vous êtes. Chaque connexion distante doit aussi présenter un jeton de porteur dans la poignée de main initialize, et c’est ce jeton qui vous identifie (voir Jeton de porteur ci-dessous). L’enrôlement ne vous fournit que le certificat. Un client disposant d’un certificat mais sans jeton complète la poignée de main TLS, puis est refusé avec AUTH_REQUIRED (-32010).

Se connecter avec OIDC (recommandé pour les déploiements OIDC)

Un administrateur doit d’abord configurer une relation [oidc.<alias>] et des correspondances de permissions sur le daemon, activer le device authorization grant auprès du fournisseur d’identité, activer WSS et exposer la passerelle via HTTPS. Un profil de permissions humain doit accorder sessions:create avec au moins un agent autorisé pour l’auto-amorçage de l’appareil en libre-service ; system:execute ou admin permet également cette opération. Il s’agit d’une politique basée sur l’émetteur et les groupes, et non de l’enregistrement d’un utilisateur ou d’un appareil individuel. Aucune entrée locale [users], aucun jeton apparié, aucun code en attente, aucun certificat client existant et aucun écouteur [enroll] séparé n’est nécessaire. L’alias ci-dessus est l’alias côté daemon, et non une marque ou une URL d’émetteur du fournisseur d’identité. Exécutez la passerelle dans le cadre de zeroclaw daemon, qui gère l’autorité de certification et l’autorité d’audit partagée ; une passerelle démarrée séparément n’émet pas de certificats d’appareil.

zerocode login corp wss://daemon.example.com:9781 \
  --gateway-url https://gateway.example.com
zerocode

Pour les ports standard, zerocode login corp daemon.example.com utilise le port WSS 9781 et la passerelle à l’adresse https://daemon.example.com:42617. La passerelle elle-même ne fournit pas HTTPS par défaut : utilisez --gateway-url pour indiquer son proxy de terminaison TLS. Un préfixe de chemin de passerelle est pris en charge. Le HTTP en clair n’est accepté que sur loopback.

Chaque grant d’appareil effectué par zerocode envoie un challenge PKCE S256, y compris pour zerocode login et le chemin d’enrôlement automatique hérité ([connection.wss] avec auth_provider = "oidc.<alias>", un enroll_url et sans jeton). Le vérificateur correspondant n’est envoyé que lors de l’interrogation pour obtenir le jeton, ne vit que pour ce grant, n’est jamais persisté et ne fait pas partie de la réponse de démarrage de l’appareil renvoyée par la passerelle. Un fournisseur qui rejette code_challenge sur son point de terminaison d’autorisation d’appareil fera échouer les deux chemins ; les fournisseurs qui ignorent les paramètres non reconnus, comme l’exige la section 3.1 de la RFC 8628, continuent de fonctionner.

Le lancement de la connexion fonctionne depuis un répertoire de configuration client entièrement vide :

  1. Vérifiez le certificat HTTPS de la passerelle. Un certificat public ne nécessite aucune invite ; utilisez --gateway-ca-cert <pem> pour une autorité de certification de passerelle privée. Un certificat non approuvé propose une confirmation explicite pour ignorer la vérification ; un refus ou une fin de fichier (EOF) interrompt l’opération avant l’échange des identifiants OIDC.
  2. Afficher l’URL de vérification et le code du fournisseur d’identité. Approuvez la connexion dans votre navigateur. Il s’agit du code d’autorisation d’appareil du fournisseur d’identité, et non d’un code de jumelage ou d’enrôlement de daemon. Aucun secret client n’est nécessaire sur votre poste de travail.
  3. Générez une nouvelle clé et une CSR localement. Le daemon vérifie le jeton d’accès OIDC et le mapping de permissions actuel, crée l’appareil auparavant inconnu, et signe sa CSR via POST /api/oidc/<alias>/certificate sur cette même connexion passerelle authentifiée. La clé privée ne quitte jamais le client. La passerelle renvoie la CA du daemon, donc aucun SAS ni code hors bande n’est nécessaire. Le service d’enrôlement séparé sur le port 9782 n’est jamais contacté.
  4. Vérifiez WSS à l’aide de l’autorité de certification (CA) renvoyée (ou --tls-ca-cert <pem> si elle est configurée explicitement), puis initialisez avec le nouveau certificat et le jeton d’accès OIDC. WSS reste authentifié mutuellement. Sa confiance TLS demeure distincte de celle de la passerelle : un contournement délibéré sur un pair n’entraîne jamais implicitement le contournement de l’autre.
  5. Enregistrer la connexion fonctionnelle et sélectionner cette URL comme valeur par défaut uniquement après que le daemon a accepté la poignée de main RPC. Un échec ne remplace pas une connexion enregistrée.

--tls-skip-verify demande toujours une confirmation pour chaque pair TLS. Choisir always ne mémorise que cette URL exacte, et non chaque URL de l’hôte. Privilégiez HTTPS vérifié : un certificat obtenu via une passerelle explicitement non vérifiée hérite du risque de confiance que vous avez accepté pour cette passerelle.

Ensuite, zerocode sans argument utilise la connexion sélectionnée. Pour sélectionner une autre connexion enregistrée pour une seule exécution, utilisez zerocode --connect wss://other.example.com:9781. Chaque URL WSS normalisée, port et chemin inclus, possède sa propre connexion ; se connecter à une seconde URL n’écrase pas les identifiants de la première. Une URL wss:// complète sans port explicite désigne le port WSS standard 443 ; un simple nom d’hôte sans port désigne le port WSS 9781 de ZeroClaw.

Les jetons et les métadonnées d’expiration sont stockés dans [connection.logins."wss://daemon.example.com:9781/"] dans le fichier local zerocode-config.toml. Ils sont enregistrés en clair, ne sont jamais affichés par la commande de connexion, et sont écrits de manière atomique avec des permissions réservées au propriétaire (0600, répertoire 0700 sous Unix ; protégez l’ACL du répertoire sur les autres plateformes). Les enregistrements de ce fichier, y compris le renouvellement au démarrage, sont sérialisés : deux connexions partageant un même répertoire de configuration ne peuvent donc pas effacer mutuellement leur URL. Traitez ce fichier comme un identifiant secret : ne le validez pas dans un dépôt et ne le partagez pas. Les certificats d’appareil et les clés privées sont isolés sous <config-dir>/connections/<url-sha256>/generations/<generation>/tls/ et utilisent le writer de credentials existant, capable de récupérer après un crash. Le chemin de certificat enregistré sélectionne la génération active ; les anciens caches tls/ propres à l’URL restent lisibles. Une nouvelle génération est validée avec WSS avant que la configuration ne bascule dessus. Une connexion refusée supprime uniquement ses fichiers candidats, jamais la clé précédente ni l’ancre de confiance. Les générations précédemment acceptées sont conservées ; une erreur lors de l’enregistrement de la configuration peut laisser un candidat non sélectionné plutôt que de risquer la suppression d’une clé référencée. Protégez ces répertoires comme des credentials également.

Avant de démarrer l’interface TUI, zerocode vous demande de vous reconnecter si le jeton enregistré a expiré, si le certificat de l’appareil est absent, mal formé, expiré ou pas encore valide, ou si le daemon rejette son authentification. La durée de validité du certificat est lue directement dans le certificat X.509 réel, indépendamment de l’expiration du jeton ou des métadonnées de profil en cache. Le remplacement est enregistré automatiquement. Il n’existe ni cache de jetons de rafraîchissement ni rafraîchissement silencieux en arrière-plan : si un jeton expire pendant une session TUI active, redémarrez zerocode pour vous reconnecter. Vous pouvez aussi relancer explicitement zerocode login corp <url>. Une URL de passerelle personnalisée enregistrée est réutilisée si elle est omise lors d’une connexion ultérieure.

Le login délivre un certificat client d’appareil valide 30 jours. cert/renew est authentifié par le certificat client présenté, et non par un principal OIDC. Les 30 jours ne constituent donc pas une durée de vie absolue de l’appareil : zerocode renouvelle le certificat environ à mi-parcours, et un appareil non révoqué peut continuer à le renouveler. Supprimer le mappage OIDC d’un utilisateur interrompt les opérations autorisées par principal, mais ne retire pas l’appareil et n’empêche pas le renouvellement.

La révocation de l’appareil est une étape distincte à effectuer par l’opérateur :

  1. Exécutez zeroclaw security list-client-certs. Le certificat émis à la connexion possède un actor qui commence par oidc: et désigne l’émetteur et le sujet de l’utilisateur. Notez son device.
  2. Exécutez zeroclaw security revoke-client-cert --device <id>. Cela révoque tous les certificats actifs détenus par l’appareil.

Révoquer par appareil, et non par empreinte. Un certificat renouvelé est enregistré avec l’acteur renew, donc seul l’identifiant de l’appareil le relie à l’utilisateur, et révoquer une seule empreinte laisse les autres certificats de l’appareil capables de se renouveler. Chaque connexion qui émet un certificat crée un nouvel identifiant d’appareil, si bien qu’un même utilisateur peut en avoir plusieurs. La CRL est vérifiée lors de la prochaine négociation TLS, donc une révocation n’interrompt pas une connexion déjà établie.

Un jeton d’accès divulgué peut être utilisé pour obtenir un certificat d’appareil, et cet appareil peut continuer à renouveler ce certificat jusqu’à sa révocation. Le certificat seul n’autorise que le renouvellement : toute autre opération nécessite toujours un jeton d’accès valide.

Le renouvellement au démarrage et la nouvelle tentative après un jeton rejeté respectent les choix actuels de --tls-ca-cert, --tls-client-cert, --tls-client-key et --tls-skip-verify. Ces options valables pour une seule exécution ne sont pas copiées dans la connexion enregistrée lors du renouvellement automatique ; utilisez une invocation explicite de zerocode login pour enregistrer de nouveaux paramètres TLS.

ZEROCLAW_AUTH_TOKEN remplace toujours le jeton sélectionné pour une exécution ponctuelle ; la connexion affiche un avertissement si cette variable d’environnement masquerait le jeton qui vient d’être enregistré.

Les identifiants [connection.wss] configurés manuellement (un jeton, un fournisseur, des fichiers TLS ou un relais) continuent de fonctionner, avec des limitations dès qu’une connexion par URL est enregistrée :

  • Sans identifiants enregistrés, ils sont utilisés pour l’URL sélectionnée, y compris lors d’une connexion --connect vers un autre daemon, comme auparavant.
  • Une fois un identifiant de connexion créé, il n’est utilisé que pour l’URL définie dans [connection.wss] uri. Aucune autre URL passée à --connect n’en bénéficie, même sur le même hôte avec un port ou un chemin différent. Deux écritures d’une même URL, par exemple avec et sans barre oblique finale, sont considérées comme la même URL.
  • zerocode login fait de l’URL à laquelle il s’est connecté la valeur par défaut en réécrivant [connection.wss] uri. Si les identifiants manuels concernaient un autre daemon, ils ne sont plus utilisés après cela, et zerocode --connect vers ce daemon s’exécute sans eux. Pour continuer à les utiliser, rétablissez uri sur ce daemon et atteignez celui auquel vous êtes connecté avec --connect, ou exécutez également zerocode login pour ce daemon.

Utilisez --config-dir pour sélectionner un répertoire de configuration client distinct. --enroll force l’obtention d’un nouveau certificat d’appareil autorisé via OIDC, sans aucune invite d’appairage. --enroll-host et --enroll-port concernent le flux distinct basé sur l’appairage, et non la connexion OIDC. Si un certificat a été fourni hors bande, passez plutôt --tls-client-cert et --tls-client-key. La connexion cible actuellement une URL WSS directe ; elle ne se connecte pas via un tableau de bord servi par le relais.

Inscription par appairage (clients non OIDC)

La première fois que vous connectez interactivement un client sans certificat, zerocode l’inscrit automatiquement :

zerocode --connect wss://<remote-host>:9781

Il demande le code d’appairage à usage unique du daemon (affiché dans le journal du daemon au démarrage), affiche une chaîne d’authentification courte (SAS) à comparer avec la console du daemon (ce qui permet de détecter une autorité de certification d’interception, ou « homme du milieu »), puis récupère et met en cache un certificat client sous <config-dir>/tls. Les exécutions suivantes réutilisent ce certificat sans demander à nouveau, et il est renouvelé automatiquement à environ 50 % de sa durée de validité. Pour effectuer l’enrôlement de manière non interactive, utilisez zerocode --enroll --connect wss://<remote-host>:9781.

L’inscription ne vous fournit pas de jeton d’accès (bearer token). Le code d’appairage d’inscription est distinct du code d’appairage de la passerelle, et il est consommé par l’inscription. Vous avez tout de même besoin d’un jeton avant que le daemon accepte une session ; voir Bearer token.

Un client sans certificat qui atteint le plan WSS sans s’être inscrit reçoit un message exploitable « enroll first » (et le démon journalise le client non migré rejeté) — jamais de blocage silencieux. Un certificat révoqué est refusé lors de la négociation (sur la base du registre des certificats émis), de sorte que la révocation d’un appareil perdu prend effet dès sa prochaine connexion.

allow_unpaired_enrollment dans la section [enroll] est réservé à un futur flux de migration sans code. Cette version rejette toute valeur non vide au démarrage du démon ; laissez-la vide et utilisez le code d’association affiché.

Sur l’hôte distant (côté daemon)

  1. Activez WSS. Définissez la configuration wss dans le volet Config (ou via la passerelle / zeroclaw config set) :

    [wss]
enabled = true

    Laissez cert_path / key_path vides (la valeur par défaut) : le démon génère automatiquement son propre CA et son certificat serveur dans <data_dir>/tls/ au premier démarrage ; vous n’avez donc pas besoin d’exécuter vous-même openssl. Renseignez-les uniquement pour utiliser votre propre certificat serveur, et utilisez des chemins absolus dans les deux cas ; la configuration ne développe pas ~.

  2. Ouvrez le port du pare-feu :

    sh

    sudo ufw allow 9781/tcp

    Le port WSS par défaut est 9781. Modifiez-le avec port = <number> dans la section [wss].

  3. Démarrer (ou redémarrer) le daemon :

    sh

    zeroclaw daemon

    Vous devriez voir une ligne de journal confirmant que l’écouteur WSS a démarré sur 0.0.0.0:9781.

Sur votre poste de travail (côté zerocode)

L’enrôlement (ci-dessus) est le moyen le plus rapide d’obtenir un certificat client. Si vous préférez utiliser votre propre certificat client plutôt que de procéder à un enrôlement interactif :

  1. Émettez un certificat client sur l’hôte du démon, à partir de l’autorité de certification mTLS du démon :

    zeroclaw security issue-client-cert --name my-laptop --out-dir /tmp/my-laptop-tls

    Cela écrit ca.crt, client.crt et client.key dans --out-dir. Ajoutez --force pour remplacer un certificat existant portant ce nom.

  2. Copiez les trois fichiers dans <config-dir>/tls/ du poste de travail (ensuite, zerocode --connect wss://<remote-ip>:9781 les trouve automatiquement), ou indiquez-les explicitement :

    sh

    zerocode --connect wss://<remote-ip>:9781 \
  --tls-ca-cert     /path/ca.crt \
  --tls-client-cert /path/client.crt \
  --tls-client-key  /path/client.key

    Comme ca.crt est la même AC qui a signé le certificat serveur du daemon, cela vérifie également le serveur ; --tls-skip-verify est uniquement nécessaire si vous omettez --tls-ca-cert avec un certificat auto-signé du daemon que vous n’avez pas épinglé.

Quoi qu’il en soit, le certificat ne vous permet de passer que la couche TLS. Ajoutez ensuite un jeton Bearer.

Jeton Bearer (obligatoire pour chaque connexion)

Le démon refuse tout initialize distant qui ne contient pas de auth_token, même lorsque le certificat client est valide. Une fois que vous fournissez un jeton à zerocode, celui-ci le présente à chaque connexion et à chaque reconnexion.

  1. Associez-vous à la passerelle pour obtenir un jeton. Utilisez la page Pairing du tableau de bord ou, sur l’hôte du démon (la passerelle écoute sur 127.0.0.1:42617 par défaut), envoyez en POST le code d’association de la passerelle figurant dans le journal du démon vers /pair :

    curl -X POST http://127.0.0.1:42617/pair -H 'X-Pairing-Code: <code>'

    La réponse contient un jeton zc_.... Utilisez ici le code d’appairage de la passerelle, et non le code d’inscription que vous avez fourni à zerocode plus haut.

    Un daemon compilé sans la passerelle (la version CLI uniquement issue de install.sh --cli-only) n’a ni /pair ni page d’appairage, il ne peut donc pas émettre ce jeton. Connectez-vous plutôt avec un jeton OIDC (ci-dessous), ou exécutez zerocode directement sur le serveur (ssh -t <remote-host> zerocode) : un zerocode sur l’hôte du daemon communique avec le socket local et ne nécessite pas de jeton bearer.

  2. Donnez le jeton à zerocode. La variable d’environnement est la méthode recommandée, car elle garde le secret hors du fichier de configuration :

    export ZEROCLAW_AUTH_TOKEN=zc_...
zerocode --connect wss://<remote-host>:9781

    Ou définissez-la dans la configuration de zerocode, soit comme chemin vers un fichier que vous seul pouvez lire, soit directement en ligne :

    [connection.wss]
uri = "wss://<remote-host>:9781"
auth_token_file = "/abs/path/zerocode-bearer"   # ou : auth_token = "zc_..."

    Ordre de priorité : ZEROCLAW_AUTH_TOKEN, puis auth_token_file, puis auth_token. Un fichier de jeton lisible par d’autres comptes est ignoré et un avertissement est affiché.

Pour utiliser un jeton d’accès OIDC au lieu d’un jeton d’appairage, définissez également auth_provider = "oidc.<alias>" sous [connection.wss]. Pour les règles de permissions de fichiers, OIDC et le traitement du jeton par le daemon, consultez Authentification et principaux.

Après cela, zerocode --connect wss://<remote-host>:9781 (ou simplement zerocode avec uri dans la configuration) ne nécessite plus aucun autre indicateur, et zerocode se reconnecte automatiquement si la connexion est interrompue.
