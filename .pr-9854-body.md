## Summary

- **Base branch:** `master`
- **What changed and why:**
  - `fetch_context_window` chose which providers to ask by matching a hand-written list of eight names living in `lib.rs`, nowhere near the family definitions. A family that also serves this catalog was only discovered if someone remembered to come edit that list; nothing failed to compile to say otherwise, and the operator silently kept the unconfigured 32,000-token fallback. The fact now lives beside the family spec, resolved through `for_each_model_provider_slot!` — the same macro that defines the typed slots and generates provider dispatch.
  - Eligibility is **explicit per-family opt-in, defaulting to `false`**, and is deliberately *not* inferred from `CompatFamilySpec`. Speaking the OpenAI-compatible chat wire proves the chat wire and nothing else — it says nothing about whether `{base}/models` exists, what shape it returns, or whether the stored credential can be presented to it as-is.
  - **The eligible set is unchanged**: the same eight families, each now declaring it for itself. What changed is *where the fact lives* and *what it takes to add one* — a one-line declaration in the family's own spec, paired with evidence.
  - Discovery stops applying credentials by hand. It previously called `bearer_auth()` on whatever was stored; it now resolves the family's declared `AuthStyle` from the registry and applies it through `compatible::apply_auth_to_request`, the same function the chat path uses.
  - `apply_auth_to_request` now **fails closed**. Its `AuthStyle::ZhipuJwt` arm previously fell back to sending the stored credential as a plain bearer token when JWT minting failed; it now returns an error and builds no request. See *Behavior change* below.
- **Scope boundary:** This does **not** widen the set of probed families, does not change `factory::get_default_url`, does not change the OpenRouter path, and does not add catalog declarations for Crusoe or ZeroRouter. Providers implemented outside `compatible.rs` have their own auth paths and are untouched.
- **Blast radius:** `fetch_context_window` runs only in explicit config-writing flows (`doctor`, `quickstart`, `api_config`), never on the request path. The fail-closed change touches every credential-bearing entry point of `OpenAiCompatibleModelProvider`, but only alters behavior for `AuthStyle::ZhipuJwt` (Z.AI, GLM) with a credential that is not in `id.secret` form.
- **Linked issue(s):** Related #9338, Related #9645, Related #9747
- **Labels:** `bug`, `provider`, `provider:compatible`, `risk:high`, `size:S`, `distinguished contributor`

## Problem

`fetch_context_window` picked which providers to ask by matching a hand-written list of eight names:

```rust
"together" | "groq" | "fireworks" | "deepinfra" | "hyperbolic"
| "anyscale" | "novita" | "nebius" => fetch_openai_compatible_context_window(...),
_ => None, // anthropic, openai, ollama, bedrock, etc. don't expose it
```

A provider added anywhere else in the codebase falls through to `None`. `doctor` and `quickstart` then never offer to populate `providers.models.<type>.<alias>.context_window`, and every agent on that provider silently runs against `UNCONFIGURED_CONTEXT_WINDOW_FALLBACK` — 32,000 tokens — no matter what the model actually supports. Nothing fails to compile to say so.

It has already happened twice, to OpenAI-compatible families that serve a live `/v1/models` catalog:

- **Crusoe** (#9338) — reported, still unfixed
- **ZeroRouter** (#9645) — a router whose models run 200k–1.05M; an agent turn on a 1M-context model reported `ctx: 11,070 / 32,000`

This PR fixes the mechanism. **It does not fix either of those two families.** Each still needs its own one-line catalog declaration:

```rust
const SERVES_MODEL_CONTEXT_CATALOG: bool = true;
```

on its `CompatFamilySpec` impl, landing in **#9338** and **#9645** respectively, paired with the evidence that the family really serves `GET {base}/models` with `data[].id` and a per-model `context_length`. Before this PR that was a change in `lib.rs`, far from the family; after it, it is a change in the family's own spec block. That relocation is the entire fix.

## Change

Two consts, both defaulting to "not eligible":

- `CompatFamilySpec::SERVES_MODEL_CONTEXT_CATALOG` (default **`false`**) — the family's assertion that `GET {DEFAULT_URL}/models` really returns `data[].id` with a per-model `context_length` (or the sibling `context_window` spelling).
- `FamilyProviderFactory::MODEL_CONTEXT_CATALOG_AUTH` (default **`None`**) — eligibility and authentication as a single fact, resolved through `for_each_model_provider_slot!`.

The blanket `impl<T: CompatFamilySpec> FamilyProviderFactory for T` derives the second from the first:

```rust
const MODEL_CONTEXT_CATALOG_AUTH: Option<AuthStyle> = if T::SERVES_MODEL_CONTEXT_CATALOG {
    Some(T::AUTH)
} else {
    None
};
```

There is no second place to declare the auth style, so discovery cannot drift away from the request path.

**Eligibility is not inferred from `CompatFamilySpec`.** NEAR AI is the in-tree counter-example: a compat *chat* family whose catalog is at `/v1/model/list` in a `models[].modelId` shape with no context field at all. A blanket opt-in would have pointed a credential-bearing probe at an endpoint this repository never claims exists.

The eligible set is therefore **unchanged** — `together`, `groq`, `fireworks`, `deepinfra`, `hyperbolic`, `anyscale`, `novita`, `nebius`. Groq builds its compat provider by hand rather than through `CompatFamilySpec`, so it declares `MODEL_CONTEXT_CATALOG_AUTH` directly; a test pins that against the `AuthStyle` its `create_provider` actually uses.

OpenRouter keeps its dedicated path — different catalog, different shape.

## Behavior change: malformed Zhipu credentials now fail closed

`compatible::apply_auth_to_request` is where a stored credential becomes an outbound header for every request this module builds and for every context-window discovery probe. Its `AuthStyle::ZhipuJwt` arm minted a short-lived HMAC JWT from the stored `id.secret` — and, when minting failed, fell back to:

```rust
Err(_) => req.header("Authorization", format!("Bearer {credential}")),
```

That put the long-lived stored secret on the wire verbatim, which is the exact leak class the discovery exclusion above exists to prevent, surviving inside the shared helper. It also produced a request that could only ever be rejected upstream.

The helper now returns `anyhow::Result<RequestBuilder>` and refuses: no header, no request, an error naming the provider and stating that nothing was sent, and an `ERROR` log with `error_key: provider_credential_unusable`. The error text is built only from the static failure reason — never from the credential.

**What an operator sees change:** with a malformed Z.AI or GLM key (anything without a `.` separator), a chat request now fails immediately and locally with

```
Z.AI: stored credential cannot be converted into a request token
(Zhipu API key must be in 'id.secret' format); no request was sent
```

instead of a round trip ending in an upstream 401 that reads like a rejected-but-well-formed credential. A well-formed `id.secret` is unaffected. Streaming paths surface the same refusal as the stream's first item rather than an empty stream.

All ten credential-bearing entry points on `OpenAiCompatibleModelProvider` propagate it: `list_models`, `list_models_with_pricing`, `chat_with_system`, `chat_with_history`, `chat_with_tools`, `chat`, `warmup`, `stream_chat`, `stream_chat_with_system`, `stream_chat_with_history`. Context-window discovery maps the refusal to `None` — the context window is genuinely unknown, and the refusal itself is logged where it happens.

## Security & Privacy Impact (required)

- New permissions, capabilities, or file system access scope? **No**
- New external network calls? **No** — the probed set is unchanged; discovery still runs only in operator-invoked config flows.
- Secrets / tokens / credentials handling changed? **Yes**
- PII, real identities, or personal data in diff, tests, fixtures, or docs? **No** — test credentials are literals such as `keyid.longlivedsecret`.
- Prompt injection or untrusted model-visible text introduced/changed? **No**

**Risk and mitigation.** Two credential-handling changes, both narrowing:

1. Discovery no longer applies `bearer_auth()` to whatever is stored; it applies the family's own declared `AuthStyle` through the same helper the chat path uses. Z.AI and GLM remain excluded from the generic path, so no request is built for them at all.
2. Malformed `ZhipuJwt` credentials no longer fall back to sending the stored secret as a plain bearer token; the request is refused. The residual risk is availability, not disclosure: an operator with a malformed key now gets a local error instead of an upstream 401. That is the intended trade and is the point of the change.

Scope of what is proven: excluded Zhipu families make no discovery request; a valid `id.secret` is transformed into a minted token before it reaches the wire; a malformed one now fails closed. Providers implemented outside `compatible.rs` carry their own auth and are outside this PR's scope.
